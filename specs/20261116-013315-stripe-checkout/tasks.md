# Tasks: Stripe Checkout for Paid Courses

**Input**: Design documents from `/specs/20261116-013315-stripe-checkout/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: The Discava constitution (principle IV) requires them, so they are included: unit tests for every helper, procedure, the webhook handler and the stand-in; invariant checks (new and widened) with tests that break them; component tests for both portals; a `packages/e2e` scenario for each flow and a concurrency test for the webhook race. Write each phase's tests first and see them fail. Never weaken an existing test to make it pass (constitution IV). Two existing invariants are deliberately widened (T012, T013): the widened checks keep every existing breaking test, and the PR description says why.

**Who runs what**: an automated agent implements these tasks without `pnpm dev` or Docker. It runs unit and component tests, lint, typecheck, `build` and `synth` locally. The e2e scenarios and the concurrency test are written by the agent but run on PR CI (`pr-checks.yml`'s `E2E tests` job); a CI failure is the feedback for those. Tasks marked **(human)** need a running local stack, a Stripe account or people, and are done by a reviewer before merge.

**Organization**: Grouped by user story, in the order the code needs them (a price comes before a purchase, the refusal before the checkout), each phase one agent PR, merged in order; each phase leaves `main` green and working. Paths are relative to the repository root. Only the last PR closes #284; earlier PRs say "Part of #284" and must not use a closing keyword. Do not set a real price on a deployed stage until Phase 6 has shipped.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 buy and start learning (P1), US2 unpaid users cannot get paid content (P1), US3 instructor sets a price (P1), US4 refund takes access away (P2), US5 abandoned and failed payments (P2)

## Implementation strategy

- **MVP**: Phases 1 to 6: a student can buy a priced course and be enrolled exactly once, unpaid users are refused, and instructors can set prices. Abandoned checkouts (Phase 7) close themselves when their order lapses even before Phase 7 ships, since a pending order past its expiry is treated as closed; refunds (Phase 8) can be done by an operator by hand in the interim, so Phases 7 and 8 are reviewable follow-ups.
- Each phase is one agent PR and leaves `main` green: Phase 2 changes no behaviour, Phase 3 shows prices nobody can pay, Phase 4 refuses the free route for priced courses, and the purchase arrives with Phases 5 and 6. Keep prices at zero on deployed stages until Phase 6 is merged.
- The riskiest pieces are the exactly-once transaction (T007) and the widened invariants (T011, T012): land and verify them before building on them. Every phase runs `pnpm nx affected --target build` before it is opened and stays within its phase's files.
