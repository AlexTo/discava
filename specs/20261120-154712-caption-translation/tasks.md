# Tasks: Machine-Translated Caption Tracks

**Input**: Design documents from `/specs/20261120-154712-caption-translation/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: The Discava constitution (principle IV) requires tests, so they're included: unit tests for the track rules, the planner, the WebVTT helper, the Translate client, the handler and every procedure; invariants extended and added in `core-table`'s `helpers/invariants/`, each with a test that breaks it; portal and player component tests; and an e2e scenario file plus a concurrency test in `packages/e2e`. Write each phase's tests first and watch them fail. Never weaken an existing test to make it pass. The two intended test changes (the caption output's shape in core-api, T029, and the dialog's badge text, T035) are named in their tasks and must be repeated in those PRs' descriptions.

**Who runs what**: An automated agent implements these tasks without `pnpm dev` or Docker. It runs unit and component tests, lint, typecheck, `build` and `synth` locally. The agent writes the e2e and concurrency tests, but PR CI runs them (`pr-checks.yml`'s `E2E tests` job). Tasks marked **(human)** need a running local stack, a deployed stage or people, and a reviewer does them before merging.

**Organization**: Seven phases, each one agent PR, merged in order. Each leaves `main` green and working, so no phase needs a later one to pass. Nothing a user sees changes until Phase 3.

| Label | Story | Priority |
|-------|-------|----------|
| US1 | Read captions in my own language | P1 |
| US2 | Choose a course's caption languages once | P1 |
| US3 | My own captions always win | P1 |
| US4 | Translations follow the source | P2 |
| US5 | A failed translation never gets in the way | P2 |
| US6 | See and bound what translation costs | P3 |

US4 and US6 have no phase of their own. US4's behaviour comes from the track rules (Phase 1) and the handler (Phase 2), and its end-to-end test sits in Phase 5 beside US3's. US6's metrics are in the handler (T017), its stage settings in T012 and T020, and its limit is enforced in T023.

Paths are relative to the repository root. Only the last PR says "Closes #593"; earlier PRs say "Part of #593" and must not use a closing keyword.

## Implementation strategy

- **MVP**: Phases 1 to 3, three PRs. An instructor chooses languages and every video gets translated tracks that students can pick. This already meets the issue's first acceptance criterion, and the track rules of Phase 1 already keep the second (an upload is never replaced) and the third (a failure leaves the source and the video alone).
- **Then**: Phase 4 labels the tracks as the issue asks. It is small and should follow at once: until it lands, a translated track is named in its own language but not marked as machine-made.
- **Then**: Phase 5 (the upload paths clean up after themselves, the dialog tells the tracks apart, and the orderings are tested end to end) and Phase 6 (status and retry).
- **Finally**: Phase 7's docs, and the reviewer's checks on a deployed stage. Production keeps `captionTranslation.enabled` at whatever T050 decides.
