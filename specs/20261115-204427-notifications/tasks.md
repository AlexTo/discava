# Tasks: In-App and Email Notification Pipeline

**Input**: Design documents from `/specs/20261115-204427-notifications/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: The Discava constitution (principle IV) requires them, so they are included: unit tests for each helper, procedure, handler and sender; an invariant check, with a test that breaks it, for each rule that spans records; portal component tests; and a `packages/e2e` scenario plus a concurrency test for racing duplicate publishes. Write each phase's tests first and see them fail. Never weaken an existing test to make it pass (constitution IV).

**Who runs what**: an automated agent implements these tasks without `pnpm dev` or Docker. It runs unit and component tests, lint, typecheck, `build` and `synth` locally. The e2e scenario and the concurrency test are written by the agent but run on PR CI (`pr-checks.yml`'s `E2E tests` job). Tasks marked **(human)** need AWS account access, a running local stack or people, and are done by a reviewer before merging.

**Organization**: Grouped into phases, each sized for its own agent PR and mergeable in order. Each phase lists the user stories it serves (US1 bell, US2 producer contract, US3 email, US4 preferences and unsubscribe, US5 course audience, US6 local inbox). Paths are relative to the repository root. Use the `ts#lambda-function` generator through the `nx-plugin-for-aws` MCP server (`generator-guide`) for new Lambda wrappers; the license headers are generator-managed.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 to US6, as above

## Phase 2: Producer helpers, read state, email transitions, invariants (PR 2)

**Purpose**: every write of the notification records goes through helpers in core-table, each with an invariant. Serves US1, US2, US3, US5.

- [x] T004 [US2] Test first, then implement `packages/databases/core-table/src/helpers/notification.ts` (exported from `src/index.ts`): `notificationWrites`, `publishNotification` and `notifyCourseStudents` per [contracts/producer-helpers.md](./contracts/producer-helpers.md) and the "Writes by case" table in [data-model.md](./data-model.md). The id is the first 16 hex characters of `sha256(type + "\0" + dedupeKey)`, the sort key `<occurredAt>#<id>`; the first publish for a user creates `notificationState` (`unreadCount` 1, `version` 1) in the same transaction; later ones update it with condition `version = <read>`; a publish whose position is at or before `readThrough` is created with `readAt` set and leaves `unreadCount` alone; the broadcast id is the first 16 hex characters of `sha256(type + "\0" + courseId + "\0" + dedupeKey)`. `publishNotification` retries a state-version conflict up to 3 times and returns `'duplicate'` only when the notification create is the cancelled item (use the transaction's cancellation reasons). Tests in `notification.test.ts`: validation throws before any write (unknown type, missing param, empty `dedupeKey`, invalid `occurredAt`); one notification and count 1 for a first publish; count and state version for a second distinct publish; the same key twice gives one notification and one increment; concurrent identical publishes give one notification (use the repo's DynamoDB-local-free mocking pattern from `assignment-submission.test.ts`); a late publish at or before `readThrough` is created read and not counted; items returned by `notificationWrites` compose into another transaction, and a cancelled outer transaction leaves nothing; `notifyCourseStudents` returns one not-exists create and rejects a missing key.
- [x] T005 [US1] Test first, then add to `helpers/notification.ts` (or a sibling `helpers/notification-read.ts` if it grows past one topic) `markNotificationRead(service, userId, position)` and `markNotificationsRead(service, userId, through)`, per the "Writes by case" table: mark one is a no-op success when the notification is already read (`readAt` set or position at or before `readThrough`), otherwise patches `readAt` and decrements `unreadCount`, conditioned on the state's `version`; mark all queries `notification` for `userId` with sort key after `readThrough` up to and including `through`, at most 500 items, counts those without `readAt`, and moves `readThrough` and decrements in one transaction conditioned on `version` and the old `readThrough`, returning `{ unreadCount, more }`; both retry up to 3 times on a version conflict, then throw a `CONFLICT`-mappable error from `helpers/errors.ts`. Tests: count after mark one, idempotent mark one, mark all leaves a newer notification unread, mark all after some were marked individually does not double-decrement, `more` true past 500 items, a publish landing mid-mark-all (version conflict) retries and ends consistent, a position of another user or a missing one throws not-found.
- [x] T006 [P] [US3] Test first, then add `packages/databases/core-table/src/helpers/notification-email.ts` with the transition functions from [data-model.md](./data-model.md)'s state machine: `skipEmail(reason)`, `claimEmail` (pending to sending, condition `state = pending`), `markEmailSent(messageId)`, `markEmailFailed(reason)`, `releaseEmailClaim` (sending to pending), `markEmailUnknown`, each a conditional patch on the previous state, plus `readEmailState`. Tests in `notification-email.test.ts`: every legal transition; every illegal one is refused (a `sent` cannot become `sending`, a second claim is refused, `released` only from `sending`); a duplicate `markEmailSent` after `sent` does not overwrite the first `messageId`.
- [x] T007 [US1] Add the invariants in `packages/databases/core-table/src/helpers/invariants.ts` and register them in `checkTableInvariants` and the invariant-name list: add `notifications`, `notificationStates`, `notificationPreferences` and `notificationBroadcasts` to `TableSnapshot` and its scan, then the five checks from the impact check in [data-model.md](./data-model.md): `notification-unread-count-matches` (a user's `unreadCount` equals their notifications with no `readAt` and a position after `readThrough`), `notification-shape` (sort key equals `<occurredAt>#<id>`; `link.path` starts with `/`; `type` registered; `sent` has `sentAt` and `messageId`; `skipped` and `failed` carry a `reason`; no `sending` claimed over an hour ago; no `pending` email on a notification created over an hour ago), `notification-state-exists` (a user with notifications has a state, `unreadCount >= 0`, a valid `readThrough`), `notification-preference-shape` (registered type, not `required`), `notification-broadcast-done-complete` (a `done` broadcast has `completedAt`; a `pending` one over an hour old is stuck). Test first in `invariants.test.ts`: one breaking test per rule (a count too high, a count too low, a notification with a bad sort key, a `sent` without a message id, a `pending` email over an hour old, a `pending` one just created that still passes, a state missing, a negative count, a preference for a `required` type, a stuck broadcast), plus one that a clean table passes. Confirm `packages/e2e/src/helpers/table-invariants.ts` runs them without change.

## Implementation strategy

- **Minimum useful slice**: Phases 1 to 3 and 8 give a working bell fed by any producer. Email, preferences and unsubscribe (Phases 4 to 7, 9) follow without changing the contract.
- Each phase leaves `pnpm build` and the affected tests green, so a PR can merge alone. Phase 6's route and function exist before Phase 7 fills the handler, so T023 may not merge ahead of T026; keep T020, T023 and T026 in adjacent PRs or merge Phases 6 and 7 together if the stub cannot be deployed safely (a stub returns `501`).
