# Tasks: Core Table Stream Event Router

**Input**: Design documents from `/specs/20261116-183449-stream-event-router/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: The Discava constitution (principle IV) requires them, so they are included: unit tests for the registry, the router, the adapter, the feature runner and each handler change; construct tests for the queues, alarms and mappings; duplicate-delivery and reordered-delivery tests for both handlers (SC-004); e2e coverage that already exists for progress and search and must pass unchanged, a new router scenario, a failure-and-redrive scenario and a new ordering concurrency test in `packages/e2e`. This feature adds no record and no cross-record rule, so no new invariant is added (see the plan's impact check); the invariant check after every e2e test stays.

**Who runs what**: an automated agent implements these tasks without `pnpm dev` or Docker. It runs unit tests, lint, typecheck, `build` and `synth` locally. The e2e suite is run by PR CI (`pr-checks.yml`'s `E2E tests` job). Tasks marked **(human)** need Docker, an AWS account or a decision, and must not be attempted by an agent.

**Organization**: Grouped into phases, each sized for its own agent PR and mergeable in order, except where a phase says it can run alongside another. Each phase lists the user stories it serves (US1 routing and one consumer, US2 progress and search unchanged, US3 search order-safe, US4 failures per feature, US5 local parity). Paths are relative to the repository root. Use the `ts#lambda-function` generator for new Lambda wrappers (constitution II); the construct, stack and queue code are hand-written because no generator covers them.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 to US5, as above

## Implementation strategy

**MVP**: Phases 1 to 3, then 4 and 5. Phase 1 alone has no user-visible effect but unblocks everything, and Phase 5 is what makes the stream safe for #331 and #332. Phase 4 can ship first if search's correctness is wanted before the infrastructure move. After Phase 5, #331 and #332 each add one registration and a handler.

**Risks to watch**: the KMS grants on the queues (T026), the AppConfig wiring in T027, and SQS's lack of batch bisecting (a poison message can carry its batch-mates to the failure queue, which is safe to redrive).
