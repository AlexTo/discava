# Tasks: Instructor Announcements to Enrolled Students

**Input**: Design documents from `/specs/20261115-210422-announcements/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Depends on the notifications spec** (`specs/20261115-204427-notifications/`, PR #331, issue #281): Phase 1 here needs its Phases 1 and 2 (T001 to T004, T007) merged; the e2e in Phase 6 needs its Phase 5 (T014, T016) and, for bell assertions, Phases 3 and 8 (T008 to T010, T028 to T030). See the plan's Dependency gate. Announcements publish only through its producer contract (`notifyCourseStudents`, the registered type `announcement.posted`) and add no delivery of their own.

**Tests**: The Discava constitution (principle IV) requires them, so they are included: unit tests for each helper and procedure, two invariant checks each with a test that breaks it, a stream-filter test, portal component tests, and a `packages/e2e` scenario plus a concurrency test for a double post. Write each phase's tests first and see them fail. Never weaken an existing test to make one pass.

**Who runs what**: an automated agent implements these tasks without `pnpm dev` or Docker. It runs unit and component tests, lint, typecheck, `build` and `synth` locally. The e2e scenario and the concurrency test are written by the agent but run on PR CI (`pr-checks.yml`'s `E2E tests` job). Tasks marked **(human)** need a running local stack, a deployed stage or people, and are done by a reviewer before merge.

**Organization**: Grouped into phases, each sized for its own agent PR and mergeable in order. US1 post (P1), US2 read in the course home (P1), US3 edit and delete (P2), US4 instructor portal (P2). Paths are relative to the repository root. No new project, Lambda or infrastructure is created, so no generator is needed (plan, Constitution Check II).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 to US4, as above
- **(human)**: needs a running local stack, a deployed stage or people; not done by the agent

## Dependencies and order

- Gate: T001 before any other task; the notifications Phases 1 and 2 must be merged. Phase 1 before everything here.
- Phase 2 needs Phase 1. Phase 3 needs Phase 2 for data to read (its tests mock the helpers, so T016 and T017 can start after Phase 1) and is independent of Phases 4 and 5.
- Phase 4 needs Phase 2 (same procedures file). Phase 5 needs Phases 2 and 4 for its API calls and can start with Phase 2's list and create.
- Phase 6 needs all of the above and, for its notification assertions, the notifications spec's Phases 3, 5 and 8 (see the plan's Dependency gate).
- Within Phase 1, T003 and T008 are [P] with the others; T005 to T007 are sequential (one file); T009 and T010 are sequential (one file).

## Implementation strategy

- **Minimum useful slice**: Phases 1 and 2 (the foundations and posting) are the first agent issue: announcements can be posted and the audience request created, and students are notified as soon as the notifications fan-out is deployed. Phase 3 makes them readable; Phases 4 and 5 complete the instructor's side.
- Each phase leaves `pnpm build` and the affected tests green, so a PR can merge alone. No phase changes infrastructure, so no `synth` surprises are expected; run it anyway.
- The only contract change is the one registry path in T002; any other need to change the notifications contract is a stop-and-ask, not a workaround here.
