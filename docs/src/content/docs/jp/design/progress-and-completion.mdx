## ルール

**レッスンとコースの進捗および完了は、1つの Lambda だけがサーバー側で書き込みます。** 受講者がページを再読み込みすることや、その他のクライアント側のトリガーには一切依存しません。

受講者から始まるのは、個々のアイテムが完了したかどうか(たとえば動画の最後まで到達したこと)だけです。それを観測できるのはブラウザだけだからです。その場合でも、それを完了として数えるかどうかは core-api が決め、アイテムより上の階層はすべてサーバーで導出されます。

## レコード

| レコード | キー | 書き込み元 | 内容 |
|---|---|---|---|
| `itemCompletion` | pk `userId`, sk `courseId / lessonId / contentItemId` | core-api | `completedAt` |
| `progress` (レッスンごと) | pk `userId`, sk `courseId / lessonId` | 進捗再計算 Lambda のみ | `status`, `completedAt` |
| `enrolment` | pk `courseId`, sk `userId` | 進捗再計算 Lambda のみ(これらのフィールドについて) | `progressPercent`, `status`, `completedAt` |

core-api が書き込むのは `itemCompletion` レコードとクイズの受験だけです。`progress` や受講登録の進捗フィールドは書き込みません。

## アイテムが完了となる条件

| アイテムの種類 | 完了となる条件 |
|---|---|
| テキスト | 受講者が **Mark as done** を押したとき |
| 動画 | 受講者が **Mark as done** を押したとき |
| ファイル | 受講者が **Mark as done** を押したとき |
| クイズ | 合格したとき、またはすべての受験回数を使い切ったとき |
| アップロード課題 | 受講者がファイルを提出したとき |

受験回数を使い切って完了したクイズは、進捗上は完了ですが、修了証の上では合格として数えません。コースがクイズの合格を求める場合、受講者はコースを完了していても、合格するまで修了証は発行されません。

テキスト、動画、ファイルのアイテムが自動的に完了することはありません。スクロール、視聴時間、ダウンロードの追跡はありません。多くの学習プラットフォームと同じく、アイテムを終えたかどうかは受講者が決めます。

### 完了の記録

- **テキスト、動画、ファイル:** レッスンプレーヤーの **Mark as done** が core-api の `contentItem.complete` を呼び出し、core-api が完了として数えるかどうかを決めます。1つのトランザクションで、コースが公開されていること、アイテム、そのレッスン、そのモジュールが表示状態でアーカイブされていないこと、受講者が受講登録済み(`dropped` ではない)であることを確認します。そのうえで、まだなければ `itemCompletion` を作成します。
  - この完了は受講者にとってそのアイテムの最初のレコードなので、同じトランザクションでアイテムの `studentActivityCount` を加算します。各受講者は1回だけ数えられます(<Link path="design/live-course-editing">コースのライブ編集</Link>を参照)。
  - 再度完了すると、既存の完了が返されます。アーカイブされたコースは読み取り専用なので、その中のものは何も完了できません。
- **クイズ:** 自動で完了します。合格した受験、または最後の受験回数を使った受験が、その受験と同じトランザクションで完了を記録します(<Link path="design/quizzes">クイズ</Link>を参照)。受講者を再度数えることはありません。最初の受験で数え済みだからです。
  - `contentItem.complete` もクイズを受け付けますが、合格済みか、残りの受験回数がない場合に限ります。これは、受験回数の上限が受講者の使用済みの回数より少なく下げられ、それ以上提出できない場合を扱うためのものです。
- **アップロード課題:** 自動で完了します。受講者の最初の提出が、`assignmentSubmission` と同じトランザクションで完了を記録し、`studentActivityCount` に1回だけ数えます。再提出するとファイルが置き換わり、提出の `version` が上がりますが、再度数えることはありません。`contentItem.complete` は課題について既存の完了を返しますが、新たに作成することはありません。提出がなければ "Submit your work to complete it" というエラーで失敗します。
- **動画内の問題:** 動画内の問題に答えることは完了ではありません。`itemCompletion` は作成されず、答えた数、間違えた数、スキップした数にかかわらず、レッスンやコースの進捗は変わりません。動画が完了するのは、やはり **Mark as done** だけです。回答は専用の `videoAnswerSheet` に記録されます(<Link path="design/quizzes">クイズ</Link>を参照)。回答は `studentActivityCount` における動画の最初のレコードとして数えられ、`lastActivityAt` を設定します。**Mark as done** で受講者が2回目に数えられることはありません。
- **最終アクティビティ:** アイテムの完了、クイズの受験や課題の提出、動画内の問題への回答は、同じトランザクションで受講登録の `lastActivityAt` を設定し、これは前にしか進みません。これは受講者のコースを最近アクティブな順に並べるために使われ、ログイン後のホームで続きから再開できるようにします。進捗の再計算はこれに触れません。講師による変更は受講者のアクティビティではないからです。

### 進捗の読み取り

- **完了:** `course.myItemCompletions` は、コース内の受講者の完了を返します。その後に非表示やアーカイブになったアイテムのものも含みます。そのうちどれがまだ有効かは、現在のカリキュラムから判断されます。
- **レッスンの進捗:** `course.myLessonProgress` は、コース内の受講者のレッスン進捗レコードを、進捗再計算が最後に書き込んだとおりに返します。レコードのないレッスンは未開始です。コース単位の集計は受講登録とともに返されます(`course.myEnrolment`)。
- **コースをまたぐ場合:** `course.myEnrolments` は、受講者の(退会していない)受講登録を最近アクティブな順に一覧します。それぞれに進捗、次のレッスン(実効的に表示されていて、進捗が `completed` ではない最初のレッスン)、新しいアイテムの数が含まれます。ログイン後のホームと My Learning がこれを使っています。

## レッスンとコースの完了

- レッスンは、その中の**実効的に表示されている**アイテムのすべてに `itemCompletion` があるとき `completed` になります。
- `progressPercent` は、コースの実効的に表示されているアイテムのうち、受講者が完了したものの割合です。常に現在のカリキュラムから**再計算**され、加算されることはないため、コンテンツの追加、削除、非表示で値が誤ったままになることはありません。
- 100% になると、受講登録に `status: 'completed'` と `completedAt` が設定されます。
- **完了は永続的です。** レッスンもコースも同様です。受講者が完了したものにコンテンツを追加しても、未完了に戻ることはありません。その後 `progressPercent` が 100 を下回ることはありますが、受講者には **Completed ✓ · 2 new items** と表示され、新しいアイテムには **New** バッジが付きます。

受講者のコースページは、すぐに表示するために読み取り時に進捗を計算することがあります。これは表示専用で、書き込みはしません。

## 進捗再計算 Lambda

`packages/events` 内の Lambda が、レッスンの `progress` と、受講登録の `progressPercent`、`status`、`completedAt` の唯一の書き込み元です。

### トリガー

コアテーブルのストリーム(新旧のイメージ)が、<Link path="design/stream-event-router">ストリームイベントルーター</Link>を通ります。`progress-recalculation` 機能のフィルター(`PROGRESS_STREAM_FILTERS`)は、ElectroDB が各レコードに保存するエンティティ名(`__edb_e__`)で照合するため、Lambda が実行されるのは次の場合だけです。

| ストリームイベント | 再計算の対象 |
|---|---|
| `itemCompletion` が挿入された | そのコースのその受講者1人 |
| モジュール、レッスン、コンテンツアイテム: `visibility` または `archivedAt` が変更された、またはレコードが削除された | コースの受講登録済みで退会していない全受講者 |
| `quizSummary` が挿入または変更された | `passedAt` が現れたとき、または合格済みクイズの最高点が上がったときの、その受講者1人。それ以外の変更は無視される |
| `assignmentSubmission` が変更された | 旧イメージと新イメージで `status`、`points`、`returnedAt` が異なるときだけ、その受講者1人。再提出ではこれらのどれも変わらない |
| `course` が変更された | 旧イメージと新イメージで `certificateCriteria.version` または `certificatesEnabled` が異なるときだけ、退会していない受講登録済みの全受講者。それ以外のコース編集は無視される |
| クイズのコンテンツアイテム: `settings.passMarkPercent` が変更された | 退会していない受講登録済みの全受講者。合格は最高点が現在の合格点に達している間だけ有効なので、合格点を下げると受講者が対象になることがあり、合格点が 0 をまたぐと評価対象の受講者が変わる |

フィルターはレコードの旧イメージと新イメージを比較できないため、モジュール、レッスン、コンテンツアイテム、クイズの集計、コースへのあらゆる変更が Lambda に届きます。Lambda はその後、`visibility` と `archivedAt` が変わっていないものを無視します(クイズの合格点は上記のとおり例外です)。たとえば新しいタイトル、並び順、`studentActivityCount` などです。Lambda 自身の書き込み(`progress`、`enrolment`、`certificate`)はどのフィルターにも一致しないため、自分自身をトリガーすることはありません。

### 処理内容

影響を受ける(受講者、コース)ごとに次を行います。

1. コースのカリキュラムを1回読み込み(`curriculum` コレクション、全ページ)、`@discava/core-table` の `filterEffectivelyVisible` で実効的に表示されているアイテムだけを残します。これは core-api のコースビューと同じルールです。
2. コースについて、受講者の `itemCompletion` レコードとレッスンの `progress` を読み取ります(pk `userId`、sk プレフィックス `courseId`)。受講登録していない、または退会した受講者はそのままにします。
3. 各レッスンの `progress` を、変更があった場合に限って書き込みます。
   - レッスンは、実効的に表示されているアイテムがすべて完了していれば `completed`、一部が完了していれば `in_progress`、それ以外は `not_started` です。
   - 実効的に表示されているアイテムがないレッスンには進捗がありません。
   - レコードがなければ未開始を意味するため、手つかずのレッスンは書き込まれません。
   - `completed` は設定されるだけで、解除されることはありません。書き込みは、レコードがまだ `completed` ではないことを条件にしています。
4. 変更があれば、受講登録の `progressPercent` を書き込みます(切り捨てるので、すべてが終わったときだけ 100 になります)。100% の場合は、受講登録がまだ `active` であることを条件に、`status: 'completed'` と `completedAt` を設定します。表示されているものがないコースが完了することはありません。
5. 受講登録が `completed` で、受講者がまだ修了証を持たず、コースが修了証を発行する場合、コースの修了証の基準を確認し(`evaluateCertificateCriteria`、<Link path="design/certificates">修了証</Link>を参照)、基準を満たしたときだけ `issueCertificate` を呼び出します。受講者のクイズの集計と採点済みの提出は、基準が必要とする場合にだけ読み取られます。
6. 受講者が修了証を持っている場合、LinkedIn のリマインダーを1回だけ予約します。ただし、すでに予約済みか送信済み、LinkedIn のクリックが記録済み、または期限を過ぎている場合は予約しません。

受講者は10人ずつ再計算され、各コースのカリキュラムはバッチごとに1回読み込まれます。

### 失敗

失敗したバッチは機能のキューに戻され、再試行されます。`maxReceiveCount` 回受信してもまだ失敗しているメッセージは、後続の変更をブロックせず、機能の失敗キューに移されます(<Link path="design/stream-event-router">ストリームイベントルーター</Link>を参照)。毎回ゼロから再計算するため、同じ受講者に対する次の変更で、失敗したバッチが取りこぼした分も修復されます。

受講登録はコースのパーティションキーを共有しているため、再計算する受講者の一覧取得は1回のクエリで済みます。カリキュラムの変更では、受講登録済みの受講者1人につき1回のクエリがかかります。

### 冪等性

毎回ゼロから再計算するため、重複したストリームレコードや講師による連続した編集があっても、同じ結果になるだけです。機能のキューは、最大100件のレコードのバッチを集めるために最長5秒待ちます。バッチ内のレコードはグループ化され、各コースの各受講者は、そのレコードがいくつ該当してもバッチごとに1回だけ再計算されます。同じ受講者に対する2つの実行が同時に走る場合(完了とカリキュラムの変更が別のストリームシャードに届く場合)も、どちらも自分が読み取った内容から再計算します。完了の書き込みは、すでに完了していないことを条件にしているため、どちらも相手の完了を取り消すことはできません。

### 結果として起きること

- 受講者がまだ終えていなかった最後のレッスンを削除すると、受講者が戻ってこなくても `completed` になります。
- コース一覧と講師向けレポートは保存された値を読むので、受講者が戻ってくるのを待つことはありません。
- 保存された値は、引き金となった書き込みよりも、ストリームの遅延とキューのバッチ処理の分だけ遅れます。通常は数秒です。

どの講師の操作が再計算を引き起こすかは、<Link path="design/live-course-editing">コースのライブ編集</Link>を参照してください。
