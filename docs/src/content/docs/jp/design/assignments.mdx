**Spec:** [`specs/20261120-230057-assignment-grading/`](https://github.com/AlexTo/discava/tree/main/specs/20261120-230057-assignment-grading/)

受講生はアップロード課題に1つのファイルを提出でき、返却されるまでは差し替えられます。コースの講師は、受講登録しているすべての受講生の提出物を一覧し、提出物を開き、ポイントとフィードバックを付けて最終として返却するか、フィードバックのみで再提出を依頼します。提出物を一覧、閲覧、返却できるのはそのコースの講師だけです。

| 誰が | API | プロシージャ |
|---|---|---|
| 受講生 | core-api | `assignment.uploadUrl`, `submit`, `mySubmission`, `submissionFileUrl` |
| 講師 | instructor-api | `assignmentSubmission.list`, `get`, `fileUrl`, `return`, `requestResubmission`, `amendGrade`, および `gradingQueue.list` |

## 提出と採点

提出物は、受講生1人につき課題1つあたり `assignmentSubmission` レコード1件です。`status` は次のように遷移します。

| 遷移 | 誰が | 条件 | 効果 |
|---|---|---|---|
| 提出（初回） | 受講生 | まだ提出がない | `submitted`、`version` 1、待機インデックスに入る |
| 再提出 | 受講生 | `version` が変わっておらず、status が `submitted` または `resubmission_requested` | `submitted`、`version` + 1、待機インデックスに戻る |
| 再提出の依頼 | 講師 | `version` と `reviewRevision` が変わっておらず、status が `submitted` | `resubmission_requested`、待機インデックスから外れる |
| 最終として返却 | 講師 | `version` と `reviewRevision` が変わっておらず、status が `submitted` または `resubmission_requested` | `returned`、ポイントを設定、受講生は再提出できなくなる |
| 成績の修正 | 講師 | `reviewRevision` が変わっておらず、status が `returned` | ポイントとフィードバックが変わり、status は `returned` のまま |

- **同時実行。** 講師が操作するたびに `reviewRevision` が1増え、各書き込みは講師が見ていた `version` と `reviewRevision` を条件にします。受講生がその後に差し替えたファイルに対して返却が成立することはなく、2人の講師が同時に操作した場合は必ず1人だけが成功します。
- **ポイント**は0から課題の `maxPoints` までの数値で、小数は2桁までです。`pointsOutOf` は、後で `maxPoints` が変わった場合に備えて、その提出物が採点された時点の最大値を保持します。
- **退会した受講生。** 受講登録が外れた受講生への返却や修正は拒否されます。講師はその提出物を引き続き閲覧できます。
- **完了状態は変わりません。** 採点によって受講生の完了状態やコンテンツ項目の `studentActivityCount` が変わることはありません。再提出の依頼で完了が取り消されることはなく、再提出で受講生が二重にカウントされることもありません。

## フィードバックのラウンド

講師の操作ごとに `submissionFeedback` レコードが1件書き込まれます。再提出の依頼、最終返却、修正のいずれかです。フィードバックは再提出の依頼では必須で、返却では任意です。

- ラウンドは追記専用で、提出物と時刻をキーにするため、受講生の履歴は1回のクエリで新しい順に取得できます。受講生は再提出をまたいで以前のフィードバックを見られるので、何を求められたかがわかります。
- 提出物が保持するのは現在の成績だけです。ラウンドを別レコードにしているのは、それぞれが Tiptap JSON を20 000文字まで保持でき、数に上限がないためです。提出物にリストとして持たせると、DynamoDB のアイテムサイズ上限に達する可能性があります。

受講生には、各操作がアプリ内とメール（デフォルトでオン）で通知されます。通知は `assignment.returned`、`assignment.resubmission_requested`、`assignment.grade_updated` で、それぞれラウンドの `feedbackId` で重複排除されます。通知とラウンドは、提出物の変更と同じトランザクションで書き込まれます。

## 待機インデックスと受講登録

講師の対応を待っている提出物（status が `submitted`）は `waitingCourseId` と `waitingSince` を持ちます。これらはスパースインデックス（`byWaiting`）のキーで、コースがパーティションキー、提出時刻がソートキーです。`status` を変更するすべての書き込みは、`waitingKeys` を通じてこの2つの属性を一緒に設定または削除します。

そのため、講師ホームページの採点キュー（`gradingQueue.list`）は、講師が担当するコースごとに1回のクエリ（それぞれ古い順）をメモリ上でマージしたものになります。待機中のエントリをすべて読むので、合計は正確です。

**受講登録は読み取り時に適用されます。** キューは一覧に載る受講生の受講登録をバッチで読み、登録が `dropped` または存在しない受講生を除外します。受講登録をインデックスに保存すると、返金や決済のたびに、受講生がそのコースに持つすべての提出物を、それぞれのトランザクション内で書き換えることになります。読み取り時に適用すれば決済のコードに手を入れずに済み、再登録した受講生は書き込みなしでキューに再び現れます。

受講登録が存在しないと受講生が非表示になるため、部分的な読み取りを完全な読み取りとして扱ってはいけません。スロットリングで DynamoDB が未処理のキーを残した場合、キューは間隔を広げながら最大3回まで再度取得し、それでも取得できなければ、短くなったキューを返さずにリクエストを失敗させます。

課題ごとの一覧は、コースのすべての提出物とすべての受講登録を読み（単一パーティションへの2回のクエリ）、マージして、メモリ上で50行ずつページ分割します。カーソルは最後の行のソート位置をエンコードしたものです。提出物のない受講生は「未提出」と表示され、退会した受講生は「受講登録なし」と表示されます。

## 日次の通知

講師には、新しい提出物が `assignment.submissions_received` で通知されます。課題ごと、講師ごとに1日（UTC）に最大1回で、アプリ内通知のみ、メールはデフォルトでオフです。小さな `submissionNotice` レコード（課題ごとに1日1件、2日後に期限切れ）が目印になります。`submit` はまずこれを読み、存在しなければ同じトランザクションで作成し、講師ごとに通知を書き込みます。トランザクションが DynamoDB の100アイテムの上限を超えないよう、通知数には上限があります。別の提出が先に成立した場合は、既存のリトライが目印と通知なしで再実行されます。これにより、「1日に最大1回」はタイミングへの期待ではなく、データベース上の事実になります。

## 提出ファイルのプレビュー

レビューページでは、PDFと画像（png、jpg、jpeg、gif、webp）が採点フォームの横に表示されます。それ以外のファイル形式では、詳細情報とダウンロードボタンが表示されます。

- **画像**は、ダウンロードと同じ5分間有効な署名付き CloudFront URL を使った `<img>` です。ブラウザは画像に対して `Content-Disposition` を無視します。
- **PDF**は署名付き URL から取得され、`react-pdf`（PDF.js）でキャンバスに描画されます。これはレビューページでのみ読み込まれます。保存されたファイルは `Content-Disposition: attachment` で配信され、ポータルの CSP は `<iframe>` と `<embed>` をブロックします。そのため、キャンバスへの描画なら、ディストリビューション、CSP、保存済みオブジェクトのいずれも変更する必要がありません。

**既知の制限: JPEG 2000 と JBIG2。** PDF.js はこれらの埋め込み画像形式を WebAssembly でデコードしますが、ポータルの CSP（`script-src 'self'`、`'wasm-unsafe-eval'` なし）がこれをブロックします。そうした画像は描画されない場合がありますが、ページの残りは表示され、ダウンロードも使えます。このために共有の CSP を緩めるのは割に合わないと判断しました。

講師が未送信のポイントとフィードバックは、提出物ごとに講師自身のブラウザに保持され、サーバーには保存されません。

## チェックが強制するルール

core-table の `helpers/assignment-grading.ts` にある共有ヘルパーだけが、成績フィールドと `submissionFeedback` の書き込み元です。受講生の提出処理（`helpers/assignment-submission.ts`）は、同じ `waitingKeys` を通じて待機キーを設定します。`helpers/invariants/assignment-grading.ts` のチェックは次を対象にします。

- 成績の形: `returned` は `pointsOutOf` の範囲内のポイント、返却者、時刻を持ち、それ以外の status は持たない
- 待機キーが `status` と一致していること
- すべてのラウンドがいずれかの提出物に属していること、およびラウンドの形
- 最新のラウンドが提出物の状態と `reviewRevision` に一致していること
- 日次通知マーカーの形
