コアテーブル(`packages/databases/core-table`)は、キーによるアクセスのために作られており、「このテキストに一致するタイトルや説明を持つコースを探す」ためのものではありません。そのための検索レイヤーが [Amazon OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html) です。GSI を増やすのではなく、コアテーブルの外に置いています。

## 範囲

1 つのコレクションに 2 つのインデックスがあります。

| インデックス | 保持するもの | 検索できる人 |
|---|---|---|
| `courses` | 現在**公開中**のすべてのコース。非公開のコースは、フラグを付けて残すのではなく、ドキュメントを削除します | サインインの有無を問わず誰でも(`course.publicSearch`、`course.publicSuggest`) |
| `transcripts` | 受講登録した受講者が視聴できる動画の、キャプショントラックの文章 | 受講登録した受講者。1 つのコースの範囲内(`transcript.search`) |

コンテンツの種類(講師、お知らせ)は今後追加されます。それぞれ専用のインデックスと専用のプロシージャを持ち、1 つのクエリで混ぜることはしません。マッピングタイプは OpenSearch 2.0 で廃止されたため、種類ごとに 1 つのインデックスです。種類ごとに表示のルールも異なり、分けておくと読みやすく、テストもしやすくなります。

## コスト NextGen を採用し zero-ETL は不採用

AWS ネイティブの代替案が 2 つありましたが、どちらもコストの理由で見送りました。

- **同期**: [DynamoDB 向けの OpenSearch Ingestion zero-ETL 統合](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/OpenSearchIngestionForDynamoDB.html)は、テーブルが変化しているかどうかにかかわらず、固定の最小値付きで OCU 時間単位で課金されるマネージドパイプラインを動かし、ローカル開発での代替もありません。DynamoDB Streams と Lambda(後述)は、書き込みの合間は無料で、ローカルのイベントランナーも再利用できます。
- **コレクションの容量**: 従来の世代には、常時課金される 2 OCU の固定下限があります。このコレクションは代わりに NextGen のコレクショングループ(`AWS::OpenSearchServerless::CollectionGroup`、`Generation: NEXTGEN`)に置かれ、下限はステージごとの選択です(ステージの `search` 設定の `min{Indexing,Search}CapacityInOcu`)。

| ステージ | 最小 OCU(インデックス / 検索) | 効果 |
|---|---|---|
| `discava-development` | 0 / 0 | テスターがいない間はゼロにスケールします。しばらく使われなかった後の最初の検索は、コールドスタートのために 10 秒から 30 秒ほど待ちます |
| `discava-production` | 1 / 1 | コールド状態で応答することはなく、それでも従来世代の下限を下回ります |

NextGen は一部のリージョンでのみ利用できます(執筆時点: 米国東部のバージニア北部とオハイオ、米国西部のオレゴン、アジアパシフィックのムンバイ、シンガポール、シドニー、東京、ヨーロッパのフランクフルト、アイルランド、スペイン、ストックホルム)。ステージのデプロイ先リージョンがその中にあることを確認してください。

## パッケージ

| パッケージ | 保持するもの |
|---|---|
| `packages/databases/search` | クライアント(`getOpenSearchClient`、`resolveIndexName`)、各インデックスの zod スキーマとマッピング(`src/indices`)、インデックスマニフェストのジェネレーター、index-sync(`src/index-sync`) |
| `packages/common/constructs` | `OpenSearchCollection`(汎用。NextGen のコレクショングループ、コレクション、そのセキュリティポリシー、`grantRead`/`grantWrite`、index-sync のカスタムリソース)と、Discava でのインスタンスである `SearchCollection` |
| `packages/events` | `src/search/search-indexing.ts` が `courses` インデックスをテーブルと同期させ、`search-reindex.ts` が再構築します。`transcript-indexing.ts` と `transcript-reindex.ts` は `transcripts` に対して同じことをします([文字起こし検索](#文字起こし検索)を参照) |
| `packages/apis/core-api` | `course.publicSearch` と `course.publicSuggest`(`procedures/search.ts`、`helpers/search-query.ts` と `suggest-query.ts`)。`transcript.search`(`procedures/transcript.ts`、`helpers/transcript-access.ts`、`transcript-query.ts`、`transcript-snippet.ts`) |
| `packages/common/web-utils` | `webvtt`: 文字起こしパネルと文字起こしインデクサーが共有する WebVTT パーサー |

**Index-sync** は、存在しないインデックスを作り、既存のインデックスにはマッピングを適用します(`putMapping`)。インデックスを削除することはありません。デプロイのたびに実行されるので、手で削除したインデックスは元に戻ります。

search パッケージは、意図的に `packages/databases/core-table` と同じ構成にしています。[awslabs/nx-plugin-for-aws#1267](https://github.com/awslabs/nx-plugin-for-aws/issues/1267) が提案する `ts#opensearch` ジェネレーター(まだ `@aws/nx-plugin` にはありません)に合わせて手で作ってあり、アップストリームへ貢献でき、後から小さな差分で入れ替えられます。

## インデックス作成パイプライン

```d2 title="A course change reaches the search index through the stream router"
direction: right

table: "Core table" {shape: cylinder}
router: "Stream router"
queue: "search-indexing queue"
index: "Search indexing"
search: "courses index" {shape: cylinder}

table -> router: "stream"
router -> queue: "SEARCH_STREAM_FILTERS"
queue -> index
index -> table: "read course and rating"
index -> search: "index / delete"
```

コアテーブルのストリームの読み取り役は 1 つで、<Link path="design/stream-event-router">ストリームルーター</Link>です。ルーターは各変更を、それを登録したすべての機能のキューに送ります。検索のインデックス作成はその 1 つ(`search-indexing`)で、専用のキューと失敗キューを持つため、ここでの失敗が他の機能を妨げることはありません。

そのフィルター `SEARCH_STREAM_FILTERS`(`core-table/src/helpers/search-stream.ts`)は、`course` または `courseRating` レコードのすべての挿入と変更、および `course` の削除を通します。カリキュラムの編集と個別のレビューはドキュメントを変えられないので、ルーティングされません。

`search-indexing.ts` は、変更をどのコースが変わったかを知るためだけに使い、そのコースを現在のテーブルの状態で読み直します。

- バッチ内の `courseId` ごとに、キーで一度、強い整合性で、評価の集計とともに読みます。
- コースが `'published'` なら、ドキュメントを書き込みます(`toCourseDocument` で作り、`CourseDocumentSchema` で検証します)。公開されていない、または存在しなければ、ドキュメントを削除します。
- ドキュメントの ID はコースの `courseId` なので、再送、再試行、順序が入れ替わったレコードも同じドキュメントに収束し、重複しません。

作ったばかりのインデックスは空から始まります。ストリームにはインデックスができた後の変更しか流れないため、それ以前に公開されたコースは、次に書き込まれるかインデックスが再構築されるまで検索できません。

### コースドキュメント

ドキュメントには、`courseId`、`title`、`description`、`imageKey`、`status`、`publishedAt`、`updatedAt` のほかに、3 つの任意のフィールドグループがあります。

| グループ | フィールド | マッピング |
|---|---|---|
| カタログ | `categoryId`、`tags`、`level`、`language`、`durationHours` | `keyword`(`tags` は配列)、`durationHours` は `integer` |
| 評価 | `ratingCount`、`ratingAverage`、`ratingScore`、`ratingBoost` | `integer` と `float`。評価のないコースは `ratingBoost` だけを持ち、1 に設定されます |
| 価格 | `priceAmount`(最小単位)、`priceCurrency` | `integer`、`keyword` |

`title` と `description` は `english` アナライザー付きの `text` なので、「design」で「designing」も見つかります。

ドキュメントが保存するのは `categoryId` で、カテゴリの名前やスラッグではありません。そのため名前を変更してもドキュメントには触れず、レスポンスの構築時に `category` レコードから名前とスラッグを解決します。

### デプロイ済みステージの再インデックス

`src/search/search-reindex.ts` は、イベントソースも API ルートもない非公開の Lambda です。公開中のコースをページ単位で処理し、ストリームのインデクサーと同じ `toCourseDocument` を使って `_bulk` で書き込み、その後、もう公開されていないコースのドキュメントを削除します。インデックスを作り直した後、インデックス作成のバグの後、フィールドを追加するデプロイの後に実行してください。

```sh
pnpm nx run @discava/tooling-deploy:reindex-search --stage=discava-development
```

インデックスしたコースの数と、削除した古いドキュメントの数を出力します。2 回実行しても、結果のドキュメントは同じです。

- 独自のロールで動きます。コレクションのデータアクセスポリシーが、スタックの Lambda ロールだけを指定しているためです。人の AWS ログインは、データプレーンで 403 になります。
- `grantWrite` の `aoss:WriteDocument` は、削除もカバーします。
- タイムアウトは 5 分です。1 回の呼び出しに収まらないほど大きなカタログでは、Lambda が自分自身に処理を引き継ぐ必要があります。

ローカルでは、`pnpm nx run @discava/e2e:seed-local-courses` が講師 API を通してコースを作成して公開し、ストリームがそれらをインデックスします。

### カタログフィールドの展開

`courses` のマッピングへのフィールド追加は加算的です。index-sync の `putMapping` が、デプロイ時にライブのインデックスへその場で適用し、新しいインデックスは作りません。カタログフィールドはこの方法で追加されました。既存のプロパティの変更や削除は破壊的な変更で、代わりに #270 のバージョン付きインデックスが必要です。

そのようなデプロイより前に公開されたコースは、次に書き込まれるまで新しいフィールドの値を持たないため、デプロイ後に**再インデックスを一度実行**してください(上のコマンド)。

## 検索プロシージャ

`course.publicSearch` は `publicSearchProcedure`(`src/init.ts`)の上に作られています。これは、手書きの検索プラグイン(`src/middleware/search.ts` の `createSearchPlugin`)と core-table プラグインを追加したものです。`connection` ジェネレーターには、tRPC と OpenSearch の組み合わせがまだないため、プラグインは手書きです。

`course.publicList` と同じく公開されており、サインインしていない呼び出し元も検索できます。表示範囲の制御は 2 回行われます。インデックス時(前述)と、クエリ時です。クエリは、インデックスされたコースがすでに公開済みであっても、常に `status: 'published'` で絞り込みます。そのため、どちらか一方にバグがあっても、呼び出し元と下書きまたはアーカイブ済みのコースの間にある防御はそれだけではありません。

`buildSearchRequest`(`helpers/search-query.ts`)が 1 つのリクエストを組み立てます。

- **テキスト**: `title` と `description` に対する `multi_match`。どの単語に一致しても構わず、一致する単語が多いほど順位が上がります。テキストがなければ、公開中のすべてのコースが一致します。
- **ランキング**: 既定のソートでは、テキストクエリのスコアにコースの `ratingBoost` が掛けられるため、評価の高いコースが、同程度に関連する評価の低いコースより上に来ます。テキストがない場合は、公開日時の新しい順です。`rating` と `newest` のソートは、どちらもこれを置き換えます。
- **フィルター**: カテゴリ、タグ、レベル、言語、所要時間は `post_filter` に入るので、ヒットは完全に絞り込まれます。最低評価はクエリ自体に入るので、すべてのファセット件数がそれを反映します。
- **ファセット**: ファセットごとに 1 つの `filter` 集計があり、自分自身以外のすべてのフィルターを適用します。そのため件数は、別の値を選んだ場合に得られる結果を示します。

レスポンスでは、各ヒットのカテゴリ名を `category` レコードから、検索と並行して読み取って付けます。8 秒を超えるリクエストは tRPC の `TIMEOUT` になるので、コールドなコレクションでも、Lambda 自身のタイムアウトより前に、再試行できる明確なエラーが返ります。

## サジェスト

**仕様:** [`specs/20261119-195009-search-suggestions/`](https://github.com/AlexTo/discava/tree/main/specs/20261119-195009-search-suggestions/)

受講者ポータルの検索ボックス(`site-search.tsx`)は、入力中に一致するコースを最大 10 件表示します。`course.publicSuggest`(入力は `{ q }`、出力は `{ items: [{ courseId, title, imageKey? }] }`)は、`publicSearch` と同じファイルの `publicSearchProcedure` の上に作られています。リクエストは `buildSuggestRequest`(`helpers/suggest-query.ts`)が組み立てます。

### `publicSearch` を使わない理由

`publicSearch` は常に 5 つのファセット集計を実行し、コアテーブルからすべてのカテゴリを読み、完全な結果カードを返します。サジェストにそれらは必要なく、呼ばれる頻度ははるかに高くなります。別のプロシージャにすれば、`publicSearch` を緩めることなく、独自の入力範囲(3 文字から 200 文字)と短いタイムアウトを持てます。`publicSearch` に `mode` フラグを付ける案は見送りました。出力の形が 2 つある 1 つのプロシージャは、型付けもテストも難しくなるためです。

### クエリ

`title` に対する `match_bool_prefix` です。フルサーチと同じ `function_score`(`ratingBoost`)と、同じ `status: 'published'` フィルターの内側で実行されます。

- 最後以外のすべての語は完全な語(ステミング済み)として、最後の語は前方一致として照合されます。「pyth」で「Python for Data Analysis」が見つかります。
- リクエストは `operator` を指定しないので、語は OR で結合されます。1 語の一致で十分で、より多くの語に一致するコースほどスコアが高くなります。「java zzzz」でも Java のコースがサジェストされます。
- ヒットは、スコア、次に `publishedAt` の降順、次に `courseId` の順に並びます。
- 集計はなく、`track_total_hits` はオフで、取得するのは `courseId`、`title`、`imageKey` だけです。

既存の `title` フィールドに対するクエリなので、マッピングは変わらず、どのステージも再インデックスは不要です。

既知の制限があります。最後の語は前方一致が適用される前にステミングされるため、入力途中の語のステムがインデックスされたステムの前方部分でない場合、次の文字が入力されるまで見つからないことがあります。これが頻繁すぎる場合の対応は、`standard` アナライザーを使う `search_as_you_type` 型の `title.suggest` サブフィールドを追加し、`multi_match` の `bool_prefix` で照会することです。加算的な変更(`putMapping`)ですが、ステージごとに 1 回の再インデックスが必要です。

### 入力、デバウンス、再利用

- トリム後 **3 文字未満**、または 200 文字を超える場合は、何も送られません。
- トリムしたテキストは **300 ms デバウンス**されます(`useDebouncedValue`)。続けて入力しても、最後のテキストに対する 1 つのリクエストだけが送られます。
- クエリはテキストをキーにしているため、「javas」への遅い応答は「javas」のキャッシュエントリに入り、「javascript」のリストを置き換えることはありません。`staleTime`(60 秒)以内に最近のテキストを入力し直すと、その応答を再利用し、何も送りません。
- フォームを送信するか行を選ぶと、保留中のデバウンスが取り消されるため、すでに送信されたテキストのリクエストは発行されません。

### 失敗、タイムアウト、スロットル

リクエストの**タイムアウトは 3 秒**(`SUGGEST_REQUEST_TIMEOUT_MS`)で、`publicSearch` の 8 秒より短くなっています。これは、コールドなコレクションが入力の間隔ごとに Lambda の同時実行数を占有しないようにするためです。`TimeoutError` は、`publicSearch` と同じく tRPC の `TIMEOUT` になります。ポータルは、429 を含むあらゆるエラーを「サジェストなし」として扱い、アラートを出さず、再試行もしません。次の入力で、どのみちリクエストが置き換わるためです。

`course.publicSuggest` は `PUBLIC_OPERATIONS` に含まれますが、共有の `publicThrottle` は使いません。その上限は、すべての呼び出し元で共有され、訪問者ごとには数えられず、core-api が受ける最も頻度の高いリクエストには厳しすぎます。`discava-development` では、2 人が同時に入力するとドロップダウンが何も言わずに動かなくなります。そのため独自のスロットルを持ち、2 つの `coreApi` ステージキー、`publicSuggestThrottleRateLimit` と `publicSuggestThrottleBurstLimit` で設定します。

| ステージ | サジェストのスロットル(レート / バースト) | その他の公開オペレーション |
|---|---|---|
| `discava-development` | 5 / 10 | 1 / 3 |
| `discava-production` | 100 / 200 | 20 / 40 |
| 既定(ステージがどちらのキーも設定しない) | 100 / 200 | 20 / 40 |

1 人が一定のペースで入力すると、約 1 リクエスト/秒です。

- development の 5 / 10 は、およそ 5 人のテスターが同時に使う分をカバーし、匿名のフラッドが到達できる量を小さく保ちます。そこでは WAF がオフですが、core-api の予約済み同時実行数 10 が、同時リクエストの上限になります。
- production の 100 / 200 は、約 100 人が同じ瞬間に入力する分をカバーします。リクエストはコアテーブルを読まない 10 ヒットのクエリなので、Lambda を占有する時間は短くて済みます。ステージの他の上限と同様に、実際のトラフィックを見て引き上げてください。

どちらのステージにも IP 単位のレートルールはないため、他の公開オペレーションと同様に、1 つの負荷の高い呼び出し元が上限全体を使い切ることはあり得ます。

## 文字起こし検索

**仕様:** [`specs/20261120-002950-transcript-search/`](https://github.com/AlexTo/discava/tree/main/specs/20261120-002950-transcript-search/)

受講登録した受講者は、コースの動画で話された内容を検索し、その時点から動画を開けます。1 つの動画の文字起こしを表示するパネルは、<Link path="design/video-player">動画プレーヤー</Link>のページで説明しています。

### 別のインデックスにする理由

`transcripts` インデックスは `courses` の中ではなく、その隣にあります。

- **単位**: 一方はコース、もう一方は文章です。
- **ライフサイクル**: コースドキュメントは、コースが公開されている間存在します。文章は、下書きやアーカイブ済みのコースであっても、その動画が視聴できる間存在します。
- **表示範囲**: `courses` は公開で、文字起こしは受講登録した受講者向けです。有料コースの内容を、匿名の呼び出し元が照会するインデックスに入れないことで、公開クエリの間違いによって返ってしまうことがなくなります。
- **サイズ**: 文字起こしはメガバイト単位です。コースドキュメントに入れると、コースを編集するたびにそれらを書き直すことになり、カタログ検索のたびにそれらに対してスコアを計算することになります。

Index-sync はデプロイ時にこのインデックスを作り、既存のマッピングは一切変えません。

### 文章と、ヒットが時刻になる仕組み

1 つのドキュメントは、1 つのキャプショントラックの 1 つの**文章**です。連続するキューを、1 つのスペースでつないだものです。次のキューを加えると最初のキューの開始から 30 秒、または 600 文字を超える場合、文章はそこで閉じます。最初以降の各文章は、前の文章の最後のキューから始まるため、2 つのキューにまたがる語句も、常に 1 つの文章の中で見つかります。

ドキュメントには、テキスト、その開始時刻と終了時刻、そしてキューごとの開始時刻とテキスト内の文字オフセットが保存されます(保存のみで、インデックスはされません)。トラックあたり動画 1 時間で約 130 ドキュメントです。

ヒットを時刻にするには、次のようにします。

1. クエリは、文章全体をハイライトするよう求めます。タグには 2 つの私用領域文字を使います(`transcript-query.ts` の `MATCH_START` と `MATCH_END`)。
2. プロシージャは、タグ付けされた最初の一致を見つけ、そのオフセットを取り、それが含まれるキューを調べます。そのキューの開始が、その時点の時刻です。
3. スニペットは同じテキストから切り出され、`{ text, match }` の部分として返されます。HTML は返しません。

重なりがあるため、共有されたキュー内の一致は 2 回見つかります。プロシージャは 40 ヒットを求め、動画、トラック、キュー開始の組で重複を除いて、最大 20 件を返します。

### `transcript-indexing` 機能

独自のストリーム機能(<Link path="design/stream-event-router">ストリームルーター</Link>を参照)で、独自のキューと失敗キューを持ちます。これはレッスンメディアのバケットを読みますが、コースのインデクサーが読むべきではありません。また、不正なキャプションファイルがコースのインデックス作成を止めてはなりません。`search-indexing` と同様に、変更はどのアイテムが変わったかを知るためだけに使い(`transcript-actions.ts`)、そのアイテムを現在のテーブルの状態で読み直します(`transcript-sync.ts`)。

| レコード | 効果 |
|---|---|
| `contentItem` INSERT | すでに `captionTracks` を持つ動画が同期される |
| `contentItem` MODIFY | `captionTracks`、`captionTracksRev`、`status`、`s3Key`、`previousS3Key`、`visibility`、`archivedAt` が変わった動画が同期される。それ以外の変更(受講者のカウンターなど)は何もせず、何も読まない |
| `contentItem` REMOVE | その `contentItemId` のすべてのドキュメントが削除される |
| `lesson` または `module` の MODIFY | 表示されるかどうかが変わった場合、その下のすべての動画アイテムが同期される |
| `lesson` または `module` の REMOVE | その `lessonId` または `moduleId` のすべてのドキュメントが削除される |

**アイテムの同期**(`syncItemTranscripts`):

1. アイテム、そのレッスン、そのモジュールを、強い整合性で読みます。
2. 必要なドキュメントを割り出します。3 つとも表示されており、アイテムが再生可能なバージョンを持つ動画なら、そのバージョンのすべてのトラックの文章で、レッスンメディアバケットの WebVTT ファイルから作ります。そうでなければ、必要なドキュメントはありません。
3. インデックスがそのアイテムについて持つ ID を一覧し、必要なものを `_bulk` で書き込み、残りを削除します。
4. 3 つのレコードをもう一度読みます。ドキュメントが依存するものが変わっていれば、もう一度同期します(再試行のために失敗する前に最大 3 ラウンド)。そのため、同じアイテムの 2 つの重なった同期も、最終的に現在の状態に行き着きます。

ドキュメントの ID は `<contentItemId>.<trackId>.<seq>`(`transcriptDocumentId`)です。したがって、重複、遅延、順序が入れ替わった配信でも同じドキュメントが書き込まれ、置き換えられたトラックは新しい `trackId` を持つので、古いものと取り違えられることはありません。

**既知の残存ケース。** OpenSearch Serverless は、書き込みが検索に反映されるまで数秒かかり、`refresh=wait_for` もありません。トラックが追加されて数秒以内に置き換えられると、2 回目の同期が ID を一覧するときに 1 回目のドキュメントが見えず、それらを残してしまうことがあります。検索は、そのトラックとバージョンが現在テーブルに載っているヒットだけを返す(後述)ので、それらが表示されることはありません。再構築で取り除かれます。`_delete_by_query` には何も依存していません。

書き込み側(Transcribe の完了、instructor-api のキャプションプロシージャ、バージョンの入れ替え)は変更がなく、検索が原因で失敗することはありません。

### 再構築

インデックスはどのステージでも空から始まり、その後の変更しか知らないので、デプロイ前にキャプションが付いた動画には 1 回の実行が必要です。再構築は、上の残存ケースの修復、インデックスを作り直したとき、将来のアナライザー変更のときにも使います。

```sh
pnpm nx run @discava/tooling-deploy:reindex-transcripts --stage=discava-development
pnpm nx run @discava/tooling-deploy:reindex-transcripts --stage=discava-development --course=<courseId>
```

`transcript-reindex.ts` は、`search-reindex.ts` と同じく、イベントソースのない非公開の Lambda です。各コース(1 つ、またはステータスごとの `course.query.byStatus` によるすべてのコース)について、カリキュラムを読み、すべての動画アイテムを同期し、カリキュラムにないアイテムのそのコースのドキュメントを削除します。

時間切れが近づくとカーソルを返し、スクリプトはカーソルがなくなるまで再度呼び出して、合計を出力します。`--stage` なしでは、ローカルスタックに対してプロセス内で実行されます。2 回実行しても、結果のドキュメントは同じです。

### 検索プロシージャ

`transcript.search` はサインイン済みユーザー専用(`courseSearchProcedure`)で、`{ courseId, q, language? }` を受け取ります。`q` は 2 文字から 200 文字です。呼び出しのたびに、次を行います。

1. コースのカリキュラムと呼び出し元の受講登録を読み、`contentItem.videoUrl` が使う関数 `requireEnrolment` を呼びます。
2. テーブルから**視聴可能セット**(`watchableVideos`)を作ります。実質的に表示されている、再生可能なバージョンを持つ動画アイテムで、それぞれのバージョンとトラックの ID が付きます。
3. 自分で組み立てたフィルターでインデックスを照会します。検証済みの入力から `courseId`、視聴可能セット内の `contentItemId`、そして下の言語ルールです。セットが空なら、照会せずに何も返しません。
4. バージョンまたはトラックが視聴可能セットにないヒットを除外します。
5. タイトルは、インデックスからではなく、読み取ったカリキュラムから取ります。

インデックスはテーブルより数秒遅れ、残存ドキュメントを持つことがあるため、インデックスされたフラグを信頼するフィルターでは、非表示にしたばかりの動画のテキストが、その数秒の間返ってしまいます。フィルターをテーブルから作ることでこの隙間を塞ぎ、ブラウザーから送られるものが動画をそこに加えることはできません。これは「2 回強制する」ルールの再来です。インデクサーは視聴可能なアイテムの文章だけを保持し、クエリは視聴可能なアイテムだけを受け入れます。

コストは検索ごとのカリキュラムクエリ 1 回で、`course.view` がコースプレーヤーの各ページですでに払っているものです。8 秒を超えるリクエストは、コース検索と同じく `TIMEOUT` になります。

### どのトラックを検索するか

文章は、受講者が再生するバージョンのすべてのトラック(最大 10)について作られ、それぞれ `language`、`isDefault`、`trackLanguages` を持ちます。

検索は動画ごとに、ブラウザーが送る言語(受講者が記憶しているキャプション言語)のトラックがあればそれを、なければ既定のトラックを調べます。そのため、同じ時点が 2 つの言語で重複して並ぶことはなく、結果は受講者が開く文字起こしと一致します。キャプション言語を変えても、再インデックスは不要です。

`text` は `standard` で解析され、`english` サブフィールドを持ちます。すべてのクエリは両方を照合し、すべての語を必須とします。英語のトラックはコース検索と同じステミングを得て、他の言語は完全な語で一致します。語句の一致は順位が高くなります。中国語、日本語、タイ語は 1 文字ずつに分割され、順位は低くなるものの語句も見つかります。言語ごとのサブフィールドは、加算的な変更になります。

### コスト

ステージ設定の変更はありません。2 つ目のインデックスが、コレクショングループに容量の下限を加えることはありません。

- **インデックス作成**は、動画にキャプションが付いたときやトラックが変わったときの短いバーストで行われます。動画 1 時間、トラック 1 つあたり、約 130 の小さなドキュメントの `_bulk` が 1 回です。
- **検索**は、キー入力ごとではなく送信時で、1 つのコースに絞り込まれ、集計はありません。
- **ストレージ**は、動画 1 時間、トラック 1 つあたり、ソースで約 150 KB なので、2 トラックの 20 時間のコースで約 5,000 ドキュメント、6 MB です。
- **周辺**: ルーティングされた `contentItem`、`lesson`、`module` の変更ごとに SQS メッセージ 1 件、同期ごとにトラックあたり S3 GET 1 回、検索ごとにカリキュラムクエリ 1 回です。

容量の下限が 0 のステージでは、しばらく使われなかった後の最初の検索がコールドスタートに当たり、タイムアウトすることがあります。インデックス作成側では、キューの 5 回の受信がコールドスタートより長く続くはずです。

### #270 との関係

インデックスの追加は、index-sync がすでに扱うケースなので、ここには #270(既存インデックスのマッピング変更)と衝突するものはありません。

- すべての呼び出し元は `resolveIndexName('transcripts')` を使うため、論理名がバージョン付きインデックスへのエイリアスになっても、呼び出し元は変わりません。
- 今後の加算的な変更は `putMapping` を通します。
- 破壊的な変更(`text` のアナライザー、フィールドの型)は #270 のケースで、上の再構築が必要とされる「再構築ジョブ」です。その古い書き込みを防ぐガードには、バージョンとともにアイテムの `captionTracksRev` を使うべきです。ドキュメントは `versionId` を持ち、`captionTracksRev` はそのときにフィールドとして追加できます。
- ローンチ前の破壊的な変更は、「インデックスを削除し、デプロイして、再構築を実行する」ことです。

### AI チューター(#289)が頼れるもの

ドキュメントは、約 30 秒の文章で、コース、モジュール、レッスン、動画、バージョン、トラック、言語、時間範囲を持ちます。したがって、取得はレッスン、動画、コースに絞り込めて、「レッスン X の 12:40」のように引用できます。

`watchableVideos` は受講者が視聴できる動画を返し、`buildTranscriptSearchRequest` はそれらに絞り込んだリクエストを組み立てます。チューターも同じ 2 つを呼ぶので、受講者が視聴できないものを取得することはできません。

取得は語彙ベース(BM25)です。チューターがベクトル検索を必要とするかどうかは #289 の未決事項です。文章ごとの埋め込みと `knn_vector` フィールドが必要で、NextGen の検索コレクションがそれを受け付けるかを先に確認しなければなりません。作成時の設定が必要なら、インデックスを作り直して再構築することになり、ローンチ前なら費用はかかりません。

## ローカル開発

`pnpm dev` は、ポート 9200 で `opensearchproject/opensearch` コンテナーを動かします(`packages/tooling/local-dev/src/opensearch`。DynamoDB local や S3Mock と同じ `runLocalContainer` パターンです)。シングルノードで、セキュリティプラグインは無効、メモリには上限があります。`@discava/search` の `dev` ターゲットがそれを起動し、ローカルのインデックスを同期します。

- ローカルのイベントランナー(`packages/events/src/local/event-runner.ts`)は、デプロイされたステージと同じストリームルーター、機能、インデックス作成ハンドラーを動かします。
- `pnpm nx run @discava/tooling-local-dev:reset-local-data` は、インデックスも消去します。

イメージは `packages/databases/search/config.json` で、`latest` ではなく 3.x のリリースに固定されています。[OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-overview.html) は、コレクションを新しいオープンソースのリリースへ自動的にアップグレードし、OpenSearch 3.x と互換のあるクライアントを必要とします。そのため、ローカル開発もリリースのたびに動かさず、そのラインに留まります。固定した時点で最新のリリースで、Serverless に合わせて選ばれたため、他のローカルイメージのように 2 週間遅らせてはいません。Serverless がより新しいマイナーバージョンに移ったら固定し直し、`sync-indices.ts` とプロシージャの呼び出しを、その[サポートされるオペレーションの一覧](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-genref.html)と照らして再確認してください。

## #1267 からの差異

アップストリームの `ts#opensearch` 提案(またはそれを採用する PR)が 1 つずつ確認できるよう、ここに残しています。

- CDK には、`AWS::OpenSearchServerless::*` の L2 コンストラクトがまだなく、L1 の `Cfn*` リソースだけがあります。`OpenSearchCollection` は、その上にデータアクセスポリシーと `grantRead`/`grantWrite` を手作りしています。
- 権限を受けるものに対するデータアクセスポリシーのエントリには、そのままのプリンシパル ARN が必要です(OpenSearch Serverless は、ここでは権限を受けるものの IAM ポリシーではなく ARN で認可します)。各 grant は、すべての grantee に依存するスタックの 1 つの共有ポリシーではなく、grantee のスタックに、grantee のコンストラクトパスから名付けた独自のポリシーを作ります。共有ポリシーはすべてのロールの ARN をインポートすることになり、CloudFormation は、別のスタックへ移ったロールのエクスポートをやめるスタックのデプロイを拒否するためです。
- index-sync のカスタムリソース自身のデータアクセス権は、`grantRead`/`grantWrite` が設定するものとは別の、即時で同一スタック内のポリシーです。それは、コレクション自身のスタックのデプロイ中、カスタムリソースが最初に実行される前に存在していなければならず、遅延されるクロススタックのポリシーでは保証できないためです。
- すべてのコレクションは、#1267 より後に登場したリソースである、独自の NextGen `AWS::OpenSearchServerless::CollectionGroup`(「[コスト NextGen を採用し zero-ETL は不採用](#コスト-nextgen-を採用し-zero-etl-は不採用)」を参照)の中に作られます。#1267 の現状に基づいて書かれたジェネレーターは、代わりに従来型の常時稼働のコレクションを作ってしまいます。
- インデックスマニフェストを生成するターゲットは `indices` ではなく `generate-indices-manifest` です。このワークスペースの他のターゲットはすべて動詞(`compile`、`bundle`、`pull-image`)で、`indices` はマニフェストファイルを書くのではなく、インデックスを作成または一覧するように読めるためです。
