## ルール

**すべての販売とすべての返金は1回だけ記録され、同じ収益が二重に支払われることはありません。** 収益は、<Link path="design/payments">注文</Link>から作られる追記専用の台帳であり、支払いは台帳のエントリを対象にします。別に計算した金額を使うことはありません。

## 収益のルール

core-table の `helpers/revenue.ts` は、通貨の最小単位での純粋な整数演算です。

- **手数料。** プラットフォームは、支払われた金額に対する手数料を受け取ります。手数料はステージごとにベーシスポイントで設定され（2000 は 20%）、四捨五入されます。販売には、記録された時点の手数料がそのまま残ります。設定を変更しても、影響するのは以降の販売だけです。
- **分配。** コースの講師は、販売額を均等に分け合います。分配は、定価、支払額、手数料のそれぞれに別々に適用され、端数の単位は ID の順に先頭の講師から1つずつ割り当てられるため、各取り分の合計は常に全体と一致します。
- **純額。** 講師の純額は、支払額の取り分から手数料の取り分を引いたものです。
- **返金。** 返金では、返金額に対する講師の取り分から、それに対して返還された手数料を引いた額が戻されます。各ステップは、新しい返金合計に対する取り分から、記録済みの返金合計に対する取り分を引いて計算されるため、返金がどのようにステップに分割されても、注文が全額返金されたときには、エントリの合計がちょうど1回分になります。返金は支払額が上限です。

## 台帳

| レコード | 保持するもの |
| --- | --- |
| `earningOrder` | 1件の販売についての台帳のスナップショットと、これまでに記録された返金合計 |
| `earningEntry` | 講師ごと、販売または返金ステップごとに1行。総額、割引、返金、手数料、純額、いつ解放されるか、これを取り込んだ支払い |
| `earningDay` | 講師の、あるコース、通貨、UTC の日についてのエントリの合計 |

この3つすべてを書き込むのは core-table の `helpers/earning.ts` だけです。例外が1つあり、エントリの `payoutId` を設定または解除するコードは `helpers/payout.ts` だけです。販売と各返金ステップは、エントリ、その日次の行への加算、注文のカウンターを含む**1つのトランザクション**なので、レポートと台帳が食い違うことはありません。

エントリが購入者の名前を持つことはありません。また、エントリには、その注文が支払われた Stripe アカウントとモードも記録されます。[決済アカウントのルール](#決済アカウントのルール)を参照してください。

## 記録

記録は<Link path="design/stream-event-router">ストリーム機能</Link>の `earnings-recording` が行います。`order` へのすべての変更を受け取り、販売にあたるものに対して処理を行います。注文が販売になるのは、次の両方を満たすときです。

- `paid` であるか、理由が `requested` の `refunded` であること
- 金額が0より大きいこと

配達不能として自動的に返金された注文は販売ではなく、クーポンが価格の全額を引いた金額0の注文も同様です。割引された注文では、エントリの総額は定価で、割引は支払額との差です。

ルーターは少なくとも1回、任意の順序で配信するので、ハンドラーはそれを前提に作られています。

- **すべての注文イメージが必要な情報をすべて持っています。** そのため、どれか1つがあれば、販売を記録して返金合計を最新にできます。ほかのレコードを待つレコードはありません。
- **重複しても何も変わりません。** 販売のエントリは存在しないことを条件に作成され、台帳がすでに到達している返金合計は何も記録しません。
- **順序は関係ありません。** 遅れて届いた古いイメージは、記録済みのより高い合計を見つけて、何もしません。
- **失敗するとバッチが再試行されます。** 適用できるものはすべて適用されてからバッチが例外を投げ、適用済みのものは2回目には何も起こしません。

販売のエントリは、注文が支払われてから `holdDays` 日後に解放されます。返金のエントリは即座に解放されるので、次の支払いを減らします。

## Earnings ページの読み取り

instructor-api は呼び出し元自身の数値を返し、入力として講師 ID を受け取りません。

- `earnings.report` は、最大366日の期間にわたる日次の行を合計します。1回の範囲クエリで、通貨とコースごとにグループ化されます。
- `earnings.lines` は、1つのコースのエントリをページ分割して返します。レコードのほかの内容が呼び出し元に届かないよう、フィールドごとに組み立てられます。
- `payout.overview` は、まだ支払いに取り込まれていないエントリを、通貨ごとに **on hold**、**waiting for account setup**、**ready**、**held** に分類し、講師の支払いを一覧します。

## 支払いアカウント

講師への支払いは、Stripe Connect Express アカウントに行われます。

- `payout.startOnboarding` は、冪等にアカウントを作成し、Stripe のオンボーディングリンクを返します。
- `payout.account` は、Stripe からアカウントの状態を読み取り、変更があれば `payoutAccount` に保存します。Stripe に接続できない場合は、保存済みの status に `stale` の印を付けて返します。
- `payout.dashboardLink` は、オンボーディングが完了した後に、講師の Stripe Express ダッシュボードへのサインインリンクを返します。

| Status | 意味 |
| --- | --- |
| `not_started` | アカウントがまだない。何も保存されない |
| `in_progress` | Stripe のフォームが完了していない |
| `active` | Stripe が送金と支払いを行える |
| `restricted` | Stripe が追加の情報を必要としている |

プラットフォームの接続が有効でない限り、ここでは Stripe は呼び出されません。接続がなければ、`payout.account` は `unavailable` を返します。

## 支払いの実行

`Payouts` スタックにある1つの Lambda 関数が、EventBridge のスケジュールで1日1回実行されます。この関数が読めるのは Stripe キーだけで、ほかのシークレットは読めません。

1. **決済アカウントに紐付ける。** 実行は接続の現在のアカウントとモードに対して行われ、そのアカウントのものと確認できたキーだけを使います。
2. **復旧する。** 以前の実行が未決着のまま残した支払いを、最初に完了させます。まだ `collecting` または `releasing` のものはエントリを返し、`pending` のものは後述のとおりに決着させます。
3. **有効なアカウントを持つ各講師について、** Stripe からアカウントを再度読み取ります。有効でなくなったものは、新しい status を保存してスキップします。
4. **通貨ごとに、** 解放済みで、まだ支払いに取り込まれていないエントリを合計します。合計がステージの最小額を下回る場合、または0より大きくない場合は、待機します。
5. **収集、封印、送信。** 支払いは `collecting` で作成され、エントリは99件ずつのバッチで添付され（トランザクションは100アイテムまで）、`pending` で封印されます。その後、支払い ID を冪等キーと転送グループにして Stripe で送金を作成し、支払いに `sent` の印を付けます。

| Status | 意味 |
| --- | --- |
| `collecting` | エントリを添付している途中 |
| `pending` | 封印済み。送金が存在するかどうかは不明 |
| `sent` | Stripe が送金を受け付けた |
| `releasing` | エントリを返している途中 |
| `failed` | Stripe が送金を拒否した。エントリは再び未払いになる |

### 二重に支払われない理由

- エントリは、支払いにまだ紐付いていないことを条件に添付されるため、重なって実行された2つの実行が、両方でそれを取り込むことはありません。
- 支払いが `failed` になり、エントリが再び開かれるのは、**Stripe が送金を明確に拒否した場合だけ**です。つまり、無効なリクエストや権限エラーです。タイムアウト、5xx、レート制限、または認識できないものでは、支払いは `pending` のままです。
- 復旧では、再試行する前に、`pending` の支払いの送金を転送グループで探します。存在すれば、支払いに送信済みの印を付けます。存在しなければ、同じ冪等キーを再度使います。
- 実行は、未決着の支払いに触れる前にそれを確保し、ほかの実行が直近15分以内に処理したものには手を触れません。

1人の講師の失敗がほかの講師を止めることはありませんが、オペレーターが気づけるよう、実行は失敗として終了します。Stripe が保存済みのキーを拒否した場合は、以降の呼び出しがどれも成功しないため、実行はすぐに止まります。

## 決済アカウントのルール

収益は、その注文が支払われた Stripe アカウントとモードに属し、お金はそのアカウントの内側でだけ動きます。管理者がアカウントまたはモードを切り替えた後は、次のようになります。

- 古いアカウントの未払いの収益は**保留**されます。実行はそれらに対して何も送らず、Earnings ページは講師にプラットフォームへ連絡するよう案内します。
- 各講師の支払いアカウントは決済アカウントごとなので、支払いの設定をやり直します。
- 元に戻すと、古い収益は以前と同じように支払い可能になります。

## 設定

ステージごとに、`stages.config.ts` の `payouts` の下にあります。<Link path="deploy/configuration">ステージ設定</Link>を参照してください。

## 不変条件

core-table の `helpers/invariants/earnings.ts` は、エンドツーエンドのシナリオのたびに、エントリが注文と一致していること、返金が支払額を超えないこと、日次の行がエントリの合計と等しいこと、支払いの金額がそのエントリと等しいこと、各支払いアカウントが正しい形であることを確認します。

## ローカル開発

Stripe のスタンドインは、Connect の範囲をカバーします。Express アカウント、オンボーディングリンク、ダッシュボードリンク、送金です。

- `POST http://localhost:2024/payout-run` は、支払いの実行を1回行います。任意の `{ "graceSeconds": n }` ボディで、15分の復旧の猶予を置き換えられます。
- `LOCAL_PAYOUT_RUN_INTERVAL_SECONDS` は、タイマーで実行します。
- `GET /stripe/test/transfers` は、行われた送金を一覧し、`POST /stripe/test/transfers/fail-next` は、次の送金を選んだ方法（たとえば `rejected` や `timeout`）で失敗させます。

## 制限事項

- 税の処理、請求書、税務書類はありません。
- 通貨の換算はありません。通貨ごとに独自の残高と支払いがあります。
- 係争やチャージバックは記録されません。
- 保留された収益は、プラットフォームが手作業で支払います。新しいアカウントに移す仕組みはありません。
