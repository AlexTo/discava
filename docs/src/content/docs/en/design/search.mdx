The core table (`packages/databases/core-table`) is built for key-based access, not for "find a course whose title or description matches this text". [Amazon OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html) is the search layer for that, kept outside the core table rather than added as more GSIs.

## Scope

Two indices in the one collection:

| Index | Holds | Who can search it |
|---|---|---|
| `courses` | Every currently **published** course. An unpublished course has its document deleted rather than kept with a flag | Anyone, signed in or not (`course.publicSearch`, `course.publicSuggest`) |
| `transcripts` | Passages of the caption tracks of videos an enrolled learner can watch | Enrolled learners, within one course (`transcript.search`) |

More content types (instructors, announcements) come later, each as its own index and its own procedure rather than one query mixing them. Mapping types were removed in OpenSearch 2.0, so it is one index per type. Each type also has its own visibility rule, which is simplest to read and test kept apart.

## Cost: NextGen, not zero-ETL

Two AWS-native alternatives were rejected, both on cost:

- **Sync**: [OpenSearch Ingestion's zero-ETL integration for DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/OpenSearchIngestionForDynamoDB.html) runs a managed pipeline billed per OCU-hour with a fixed minimum, whether or not the table is changing, and has no local-dev equivalent. DynamoDB Streams and a Lambda (below) cost nothing between writes and reuse the local event runner.
- **Collection capacity**: the classic generation has a fixed 2-OCU floor, billed continuously. The collection instead sits in a NextGen collection group (`AWS::OpenSearchServerless::CollectionGroup`, `Generation: NEXTGEN`), whose floor is a per-stage choice (`min{Indexing,Search}CapacityInOcu` in the stage's `search` config).

| Stage | Minimum OCUs (indexing / search) | Effect |
|---|---|---|
| `discava-development` | 0 / 0 | Scales to zero between testers. The first search after a quiet spell waits about 10 to 30 s for a cold start |
| `discava-production` | 1 / 1 | Never served from cold, and still below classic's floor |

NextGen is only available in a subset of regions (as of writing: US East N. Virginia/Ohio, US West Oregon, Asia Pacific Mumbai/Singapore/Sydney/Tokyo, Europe Frankfurt/Ireland/Spain/Stockholm). Confirm the stage's deploy region is one of them.

## Packages

| Package | Holds |
|---|---|
| `packages/databases/search` | The client (`getOpenSearchClient`, `resolveIndexName`), each index's zod schema and mapping (`src/indices`), the indices manifest generator, and index-sync (`src/index-sync`) |
| `packages/common/constructs` | `OpenSearchCollection` (generic: a NextGen collection group, the collection, its security policies, `grantRead`/`grantWrite`, the index-sync custom resource) and `SearchCollection` (Discava's instance of it) |
| `packages/events` | `src/search/search-indexing.ts` keeps the `courses` index in step with the table, and `search-reindex.ts` rebuilds it. `transcript-indexing.ts` and `transcript-reindex.ts` do the same for `transcripts` (see [Transcript search](#transcript-search)) |
| `packages/apis/core-api` | `course.publicSearch` and `course.publicSuggest` (`procedures/search.ts`, with `helpers/search-query.ts` and `suggest-query.ts`). `transcript.search` (`procedures/transcript.ts`, with `helpers/transcript-access.ts`, `transcript-query.ts` and `transcript-snippet.ts`) |
| `packages/common/web-utils` | `webvtt`: the WebVTT parser shared by the transcript panel and the transcript indexer |

**Index-sync** creates a missing index and applies the mapping to an existing one (`putMapping`). It never deletes an index. It runs on every deploy, so an index deleted by hand comes back.

The search package mirrors `packages/databases/core-table`'s shape on purpose. It is hand-built to match [awslabs/nx-plugin-for-aws#1267](https://github.com/awslabs/nx-plugin-for-aws/issues/1267)'s proposed `ts#opensearch` generator (not yet in `@aws/nx-plugin`), so it can be contributed upstream and later swapped back in with a small diff.

## Indexing pipeline

```d2 title="A course change reaches the search index through the stream router"
direction: right

table: "Core table" {shape: cylinder}
router: "Stream router"
queue: "search-indexing queue"
index: "Search indexing"
search: "courses index" {shape: cylinder}

table -> router: "stream"
router -> queue: "SEARCH_STREAM_FILTERS"
queue -> index
index -> table: "read course and rating"
index -> search: "index / delete"
```

The core table's stream has one reader, the <Link path="design/stream-event-router">stream router</Link>, which sends each change to the queue of every feature registered for it. Search indexing is one such feature (`search-indexing`), with its own queue and failure queue, so a failure in it never blocks another feature.

Its filter, `SEARCH_STREAM_FILTERS` (`core-table/src/helpers/search-stream.ts`), passes every insert and change of a `course` or `courseRating` record, and the removal of a `course`. Curriculum edits and individual reviews can't change a document, so they aren't routed.

`search-indexing.ts` uses a change only to learn which course changed, then reads that course as the table holds it now:

- Each distinct `courseId` in the batch is read once by key, consistently, with its rating tally.
- If the course is `'published'`, its document is written (built by `toCourseDocument`, validated against `CourseDocumentSchema`). If it isn't published or is gone, its document is deleted.
- A document's id is the course's `courseId`, so a replayed, retried or reordered record converges on the same document, never a duplicate.

A freshly created index starts empty. The stream only carries changes made after the index exists, so a course published before then isn't searchable until it is next written or the index is rebuilt.

### The course document

Besides `courseId`, `title`, `description`, `imageKey`, `status`, `publishedAt` and `updatedAt`, a document carries three optional groups of fields:

| Group | Fields | Mapped as |
|---|---|---|
| Catalogue | `categoryId`, `tags`, `level`, `language`, `durationHours` | `keyword` (`tags` as an array), `durationHours` as `integer` |
| Rating | `ratingCount`, `ratingAverage`, `ratingScore`, `ratingBoost` | `integer` and `float`s. An unrated course has only `ratingBoost`, set to 1 |
| Price | `priceAmount` (minor units), `priceCurrency` | `integer`, `keyword` |

`title` and `description` are `text` with the `english` analyzer, so "design" finds "designing".

The document stores `categoryId`, not the category's name or slug. A rename then touches no document, and a response resolves names and slugs from the `category` records when it is built.

### Re-indexing a deployed stage

`src/search/search-reindex.ts` is a private Lambda with no event source and no API route. It pages through the published courses, writes them with `_bulk` using the same `toCourseDocument` the stream indexer uses, then deletes the documents of courses that aren't published any more. Run it after the index is recreated, after an indexing bug, or after a deploy that adds a field:

```sh
pnpm nx run @discava/tooling-deploy:reindex-search --stage=discava-development
```

It prints how many courses were indexed and how many stale documents were removed. Running it twice leaves the same documents.

- It runs under its own role because the collection's data access policy names only the stack's Lambda roles. A person's AWS login gets a 403 on the data plane.
- `grantWrite`'s `aoss:WriteDocument` covers the deletes too.
- Its timeout is 5 minutes. A catalogue too big for one invocation would need the Lambda to hand off to itself.

Locally, `pnpm nx run @discava/e2e:seed-local-courses` creates and publishes courses through the instructor API, and the stream indexes them.

### Rolling out the catalogue fields

Adding a field to the `courses` mapping is additive: index-sync's `putMapping` applies it to the live index in place on deploy, with no new index. The catalogue fields were added this way. Changing or removing an existing property is a breaking change and needs the versioned index of #270 instead.

A course published before such a deploy has no value for the new field until it is next written, so after deploying **run the re-index once** (the command above).

## The search procedure

`course.publicSearch` is built on `publicSearchProcedure` (`src/init.ts`), which adds a hand-written search plugin (`createSearchPlugin`, in `src/middleware/search.ts`) and the core-table plugin. The plugin is hand-written because the `connection` generator has no tRPC to OpenSearch combination yet.

It is public, like `course.publicList`: a signed-out caller can search too. Visibility is enforced twice: at index time (above), and again in the query, which always filters to `status: 'published'` even though every indexed course already is one. A bug in one is then not the only thing between a caller and a draft or archived course.

`buildSearchRequest` (`helpers/search-query.ts`) builds one request:

- **Text**: a `multi_match` over `title` and `description`. Any word may match, and more matching words rank higher. With no text, every published course matches.
- **Ranking**: under the default sort, a text query's score is multiplied by the course's `ratingBoost`, so a well-rated course ranks above an equally relevant poorly rated one. Without text the order is newest published first. The `rating` and `newest` sorts replace both.
- **Filters**: category, tags, level, language and duration go in `post_filter`, so the hits are fully filtered. A minimum rating goes in the query itself, so every facet count respects it.
- **Facets**: one `filter` aggregation per facet, applying every filter except its own, so its counts show what picking another value would give.

The response names each hit's category from the `category` records, read in parallel with the search. A request that takes over 8 seconds becomes tRPC `TIMEOUT`, so a cold collection gives a clear, retriable error before the Lambda's own timeout.

## Suggestions

**Spec:** [`specs/20261119-195009-search-suggestions/`](https://github.com/AlexTo/discava/tree/main/specs/20261119-195009-search-suggestions/)

The student portal's search box (`site-search.tsx`) shows up to 10 matching courses as you type. `course.publicSuggest` (`{ q }` in, `{ items: [{ courseId, title, imageKey? }] }` out) is built on `publicSearchProcedure`, in the same file as `publicSearch`. Its request is built by `buildSuggestRequest` (`helpers/suggest-query.ts`).

### Why not `publicSearch`

`publicSearch` always runs five facet aggregations, reads every category from the core table and returns full result cards. Suggestions need none of that, and fire far more often. A separate procedure also gets its own input bounds (3 to 200 characters) and a shorter timeout without loosening `publicSearch`'s. A `mode` flag on `publicSearch` was rejected: one procedure with two output shapes is harder to type and test.

### The query

A `match_bool_prefix` on `title`, inside the same `function_score` with `ratingBoost` and the same `status: 'published'` filter as full search.

- Every term but the last is matched as a whole (stemmed) term, and the last as a prefix. "pyth" finds "Python for Data Analysis".
- The request sets no `operator`, so the terms are OR'd. One matching term is enough, and a course matching more of them scores higher: "java zzzz" still suggests the Java courses.
- Hits sort by score, then `publishedAt` descending, then `courseId`.
- There are no aggregations, `track_total_hits` is off, and only `courseId`, `title` and `imageKey` are fetched.

It queries the existing `title` field, so the mapping doesn't change and no stage needs a re-index.

The known limit: the last term is stemmed before the prefix is applied, so a part-typed word whose stem isn't a prefix of the indexed stem can miss until the next character is typed. If that proves too common, the follow-up is a `title.suggest` sub-field of type `search_as_you_type` with the `standard` analyzer, queried with `multi_match` `bool_prefix`. It is additive (`putMapping`) but needs one re-index per stage.

### Typing, debounce and reuse

- Nothing is sent under **3 characters** (after trimming) or over 200.
- The trimmed text is **debounced by 300 ms** (`useDebouncedValue`), so a burst of typing sends one request, for the last text.
- The query is keyed by the text, so a slow answer for "javas" lands in the "javas" cache entry and never replaces the list for "javascript". Retyping a recent text within `staleTime` (60 s) reuses its answer and sends nothing.
- Submitting the form or choosing a row cancels the pending debounce, so no request fires for text that was already submitted.

### Failure, timeout and throttle

The request has a **3 s timeout** (`SUGGEST_REQUEST_TIMEOUT_MS`), shorter than `publicSearch`'s 8 s, so a cold collection doesn't hold Lambda concurrency on every pause. A `TimeoutError` becomes tRPC `TIMEOUT`, as in `publicSearch`. The portal treats any error, a 429 included, as "no suggestions": it shows no alert and does not retry, because the next pause replaces the request anyway.

`course.publicSuggest` is in `PUBLIC_OPERATIONS`, but it does not use the shared `publicThrottle`. That limit is shared by every caller, not counted per visitor, and is too tight for the most frequent request core-api gets: on `discava-development` two people typing at once would make the dropdown quietly stop working. It has a throttle of its own, set by two `coreApi` stage keys, `publicSuggestThrottleRateLimit` and `publicSuggestThrottleBurstLimit`:

| Stage | Suggest throttle (rate / burst) | Other public operations |
|---|---|---|
| `discava-development` | 5 / 10 | 1 / 3 |
| `discava-production` | 100 / 200 | 20 / 40 |
| Default (stage sets neither key) | 100 / 200 | 20 / 40 |

One person typing steadily costs about 1 request/s.

- Development's 5 / 10 covers about five testers at once and keeps what an anonymous flood can reach small. WAF is off there, and core-api's reserved concurrency of 10 still caps concurrent requests.
- Production's 100 / 200 covers about 100 people typing at the same moment. A request is a 10-hit query with no core-table read, so it holds a Lambda briefly. Raise it with real traffic, like the stage's other limits.

There is no per-IP rate rule on either stage, so one heavy caller can still use the whole limit, as for the other public operations.

## Transcript search

**Spec:** [`specs/20261120-002950-transcript-search/`](https://github.com/AlexTo/discava/tree/main/specs/20261120-002950-transcript-search/)

An enrolled learner can search what is said in a course's videos and open the video at that moment. The panel that shows one video's transcript is described on the <Link path="design/video-player">video player</Link> page.

### Why a separate index

The `transcripts` index sits beside `courses`, not inside it:

- **Unit**: a course in one, a passage in the other.
- **Lifecycle**: a course document exists while the course is published. A passage exists while its video can be watched, even in a draft or archived course.
- **Visibility**: `courses` is public, transcripts are for enrolled learners. Keeping paid course content out of the index anonymous callers query means a mistake in a public query can't return it.
- **Size**: transcripts are megabytes. On the course document, every course edit would rewrite them and every catalogue search would score against them.

Index-sync creates the index on deploy with no change to any existing mapping.

### A passage, and how a hit becomes a time

A document is one **passage** of one caption track: consecutive cues joined with single spaces. A passage closes when the next cue would take it past 30 seconds from its first cue's start, or past 600 characters. Each passage after the first begins with the previous one's last cue, so a phrase straddling two cues is always found inside one passage.

A document stores the text, its start and end time, and for each cue its start time and character offset in the text (stored, not indexed). That is about 130 documents an hour of video per track.

To turn a hit into a time:

1. The query asks for the whole passage highlighted, with two private-use characters as tags (`MATCH_START` and `MATCH_END` in `transcript-query.ts`).
2. The procedure finds the first tagged match, takes its offset, and looks up the cue it falls in. That cue's start is the moment's time.
3. The snippet is cut from the same text and returned as `{ text, match }` parts, never HTML.

The overlap means a match in a shared cue is found twice. The procedure asks for 40 hits and drops repeats by video, track and cue start, to return up to 20.

### The `transcript-indexing` feature

A stream feature of its own (see the <Link path="design/stream-event-router">stream router</Link>), with its own queue and failure queue. It reads the lesson media bucket, which the course indexer shouldn't, and a bad caption file must not hold up course indexing. Like `search-indexing`, it uses a change only to learn which item changed (`transcript-actions.ts`), then reads the item as the table holds it now (`transcript-sync.ts`).

| Record | Effect |
|---|---|
| `contentItem` INSERT | A video that already has `captionTracks` is synced |
| `contentItem` MODIFY | A video whose `captionTracks`, `captionTracksRev`, `status`, `s3Key`, `previousS3Key`, `visibility` or `archivedAt` changed is synced. Any other change (such as a student counter) does nothing and reads nothing |
| `contentItem` REMOVE | Every document of that `contentItemId` is deleted |
| `lesson` or `module` MODIFY | If whether it is shown changed, every video item under it is synced |
| `lesson` or `module` REMOVE | Every document of that `lessonId` or `moduleId` is deleted |

**Syncing an item** (`syncItemTranscripts`):

1. Reads the item, its lesson and its module consistently.
2. Works out the wanted documents. If all three are shown and the item is a video with a playable version, they are the passages of every track of that version, built from the WebVTT files in the lesson media bucket. Otherwise none are wanted.
3. Lists the ids the index holds for the item, writes the wanted ones with `_bulk` and deletes the rest.
4. Reads the three records again. If what the documents depend on changed, it syncs once more (up to 3 rounds before failing for a retry), so two overlapping syncs of one item still end on the current state.

A document's id is `<contentItemId>.<trackId>.<seq>` (`transcriptDocumentId`). A duplicate, late or reordered delivery therefore writes the same documents, and a replaced track, which gets a new `trackId`, can't be mistaken for the old one.

**Known leftover case.** OpenSearch Serverless shows a write to searches a few seconds later and has no `refresh=wait_for`. If a track is added and replaced within seconds, the second sync may not see the first one's documents when it lists ids, and leaves them behind. They are never shown, because search only returns hits whose track and version the table lists now (below). The rebuild removes them. Nothing relies on `_delete_by_query`.

The writers (Transcribe's completion, instructor-api's caption procedures, the version swap) are unchanged and can't fail because of search.

### Rebuilding

The index starts empty on every stage and only learns of later changes, so videos captioned before the deploy need one run. The rebuild is also the repair for the leftovers above, for a recreated index, and for a future analyzer change.

```sh
pnpm nx run @discava/tooling-deploy:reindex-transcripts --stage=discava-development
pnpm nx run @discava/tooling-deploy:reindex-transcripts --stage=discava-development --course=<courseId>
```

`transcript-reindex.ts` is a private Lambda with no event source, like `search-reindex.ts`. For each course (one, or every course by `course.query.byStatus` for each status) it reads the curriculum, syncs every video item, then deletes that course's documents whose item isn't in the curriculum.

When its time is nearly up it returns a cursor, and the script calls it again until there is none, then prints the totals. With no `--stage` it runs in-process against the local stack. Running it twice leaves the same documents.

### The search procedure

`transcript.search` is signed-in only (`courseSearchProcedure`) and takes `{ courseId, q, language? }`, with `q` of 2 to 200 characters. On every call it:

1. reads the course's curriculum and the caller's enrolment and calls `requireEnrolment`, the function `contentItem.videoUrl` uses;
2. builds the **watchable set** from the table (`watchableVideos`): effectively visible video items with a playable version, each with its version and track ids;
3. queries the index with filters it builds itself: `courseId` from the checked input, `contentItemId` in the watchable set, and the language rule below. With an empty set it returns nothing without querying;
4. drops any hit whose version or track isn't in the watchable set;
5. takes titles from the curriculum it read, not from the index.

The index is a few seconds behind the table and can hold leftovers, so a filter that trusted an indexed flag would return a just-hidden video's text for those seconds. Building the filter from the table closes that gap, and nothing the browser sends can add a video to it. This is the "enforced twice" rule again: the indexer keeps only watchable items' passages, and the query admits only watchable items.

The cost is one curriculum query per search, which `course.view` already pays on every page of the course player. A request that takes over 8 seconds becomes `TIMEOUT`, as in course search.

### Which track is searched

Passages are built for every track of the version students play (up to 10), each carrying its `language`, `isDefault` and `trackLanguages`.

A search looks, per video, in the track for the language the browser sends (the learner's remembered caption language) when the video has one, otherwise in the default track. A moment is then never listed twice in two languages, and the result matches the transcript the learner opens. Changing the caption language needs no re-index.

`text` is analysed with `standard` and has an `english` sub-field. Every query matches both and requires every word, so English tracks get the stemming course search has and other languages match on whole words. A phrase match ranks higher. Chinese, Japanese and Thai are split per character, which still finds phrases with weaker ranking. Per-language sub-fields would be an additive change.

### Cost

No stage configuration changes: the second index adds no capacity floor to the collection group.

- **Indexing** happens in short bursts when a video is captioned or a track changes: one `_bulk` of about 130 small documents per hour of video per track.
- **Searching** is on submit, not per keystroke, filtered to one course, with no aggregations.
- **Storage** is about 150 KB of source per hour of video per track, so a 20-hour course with two tracks is about 5,000 documents and 6 MB.
- **Around it**: one SQS message per routed `contentItem`, `lesson` or `module` change, one S3 GET per track per sync, and one curriculum query per search.

On a stage with a capacity floor of 0, the first search after a quiet spell can hit the cold start and time out. On the indexing side, the queue's five receives should outlast a cold start.

### How it fits #270

Adding the index is the case index-sync already handles, so nothing here conflicts with #270 (changing an existing index's mapping).

- Every caller uses `resolveIndexName('transcripts')`, so when logical names become aliases over versioned indices the callers don't change.
- Later additive changes go through `putMapping`.
- A breaking change (the analyzer of `text`, a field's type) is #270's case, and the rebuild above is the "rebuild job" it needs. Its stale-write guard should use the item's `captionTracksRev` with the version: documents carry `versionId`, and `captionTracksRev` can be added as a field then.
- Before launch, a breaking change is "delete the index, deploy, run the rebuild".

### What the AI tutor (#289) can rely on

A document is a passage of about 30 seconds with its course, module, lesson, video, version, track, language and time span. Retrieval can therefore be scoped to a lesson, a video or a course and can cite "lesson X at 12:40".

`watchableVideos` gives the videos the learner can watch and `buildTranscriptSearchRequest` builds the request filtered to them. The tutor calls the same two, so it can't retrieve what the learner can't watch.

Retrieval is lexical (BM25). Whether the tutor wants vector retrieval is open for #289: it needs an embedding per passage and a `knn_vector` field, and whether a NextGen search collection accepts one must be verified first. If it needs a setting at creation, the index is recreated and rebuilt, which costs nothing before launch.

## Local dev

`pnpm dev` runs an `opensearchproject/opensearch` container on port 9200 (`packages/tooling/local-dev/src/opensearch`, the same `runLocalContainer` pattern as DynamoDB local and S3Mock), single-node, with the security plugin disabled and memory capped. `@discava/search`'s `dev` target starts it and syncs the local indices.

- The local event runner (`packages/events/src/local/event-runner.ts`) runs the same stream router, features and indexing handlers as a deployed stage.
- `pnpm nx run @discava/tooling-local-dev:reset-local-data` also wipes the indices.

The image is pinned in `packages/databases/search/config.json` to a 3.x release, not `latest`. [OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-overview.html) upgrades collections automatically to new open source releases and requires clients compatible with OpenSearch 3.x, so local dev stays on that line without moving every time a release lands. It was the newest release when pinned, chosen to match Serverless, so unlike the other local images it wasn't held back two weeks. Re-pin it when Serverless moves to a newer minor version, and re-check the calls in `sync-indices.ts` and the procedures against its [list of supported operations](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-genref.html).

## Deviations from #1267

Kept here so the upstream `ts#opensearch` proposal (or a PR adopting it) can check each one:

- CDK has no L2 construct for `AWS::OpenSearchServerless::*` yet, only L1 `Cfn*` resources; `OpenSearchCollection` hand-rolls the data access policy and `grantRead`/`grantWrite` on top of them.
- A grantee's data access policy entry needs its literal principal ARN (OpenSearch Serverless authorises by ARN there, not via the grantee's own IAM policy). Each grant creates its own policy in the grantee's stack, named from the grantee's construct path, rather than one shared policy in a stack that depends on every grantee: a shared policy would import every role's ARN, and CloudFormation then refuses to deploy a stack that stops exporting a role that moved to another stack.
- The index-sync custom resource's own data access grant is a separate, eager, same-stack policy from the one `grantRead`/`grantWrite` populate: it has to exist before the custom resource first runs, during the collection's own stack's deploy, which a deferred cross-stack policy can't guarantee.
- Every collection is created inside its own NextGen `AWS::OpenSearchServerless::CollectionGroup` (see [Cost](#cost-nextgen-not-zero-etl)), a resource that postdates #1267; a generator written against #1267 as it stands would create a classic, always-on collection instead.
- The target that generates the indices manifest is `generate-indices-manifest`, not `indices`: every other target in this workspace is a verb (`compile`, `bundle`, `pull-image`), and `indices` reads as if it creates or lists indices rather than writing the manifest file.
