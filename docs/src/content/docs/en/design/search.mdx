Discava has no full-text or cross-entity search inside the core table (`packages/databases/core-table`): it's fine for key-based access, but not for "find a course whose title or description matches this text". [Amazon OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html) is the search layer for that, kept outside the core table rather than added as more GSIs.

## Scope (v1)

Courses only: one index, **courses**, holding every currently **published** course. An unpublished course has its document deleted rather than kept with a flag.

More content types (lessons, instructors, announcements) come later, each as its own index (mapping types were removed in OpenSearch 2.0, so one index per type rather than one mixed index) and its own procedure, such as `lesson.search`, rather than one query mixing them. Each type has its own visibility rule (a lesson's depends on its module, its course, and the caller's enrolment), which stays simplest to read and test kept apart.

## Cost: NextGen, not zero-ETL

Two AWS-native alternatives were considered and rejected for how the collection is sized and how it's kept in sync, both on cost:

- **Sync**: [OpenSearch Ingestion's zero-ETL integration for DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/OpenSearchIngestionForDynamoDB.html) runs a managed pipeline billed per OCU-hour with a fixed minimum, continuously, whether or not the table is changing -- and has no local-dev equivalent. DynamoDB Streams → Lambda (above) costs nothing between writes and reuses the local event runner that already existed for progress recalculation.
- **Collection capacity**: the collection's capacity is set on a NextGen collection group (`AWS::OpenSearchServerless::CollectionGroup`, `Generation: NEXTGEN`), not the classic generation. Classic has a fixed 2-OCU floor, billed continuously, idle or not. NextGen's floor is a per-stage choice (`CapacityLimits.min{Indexing,Search}CapacityInOcu`): `discava-development` sets it to 0 -- true scale-to-zero between testers, at the cost of a ~10-30s cold start on the first search after a quiet spell -- while `discava-production` keeps a small non-zero minimum (smaller than classic's fixed floor) so real traffic is never served from cold.

NextGen is only available in a subset of regions (as of writing: US East N. Virginia/Ohio, US West Oregon, Asia Pacific Mumbai/Singapore/Sydney/Tokyo, Europe Frankfurt/Ireland/Spain/Stockholm) -- confirm the stage's deploy region is one of them.

## Packages

| Package | Holds |
|---|---|
| `packages/databases/search` | The collection's client (`getOpenSearchClient`, `resolveIndexName`), each index's zod schema + mapping (`src/indices`), the indices manifest generator, and index-sync (creates missing indices / updates mappings, never deletes one; runs on every deploy, so an index deleted by hand comes back) |
| `packages/common/constructs` | `OpenSearchCollection` (generic: a NextGen collection group, the collection, its security policies, `grantRead`/`grantWrite`, the index-sync custom resource) and `SearchCollection` (Discava's instance of it) |
| `packages/events` | `src/search/search-indexing.ts`: the DynamoDB-stream Lambda that keeps the index in sync |
| `packages/apis/core-api` | `course.publicSearch` and `course.publicSuggest`: the tRPC procedures |

This mirrors `packages/databases/core-table`'s shape closely on purpose: it's hand-built to match [awslabs/nx-plugin-for-aws#1267](https://github.com/awslabs/nx-plugin-for-aws/issues/1267)'s proposed `ts#opensearch` generator (not yet in `@aws/nx-plugin`), so it can be contributed upstream and later swapped back in with minimal diff.

## Indexing pipeline

```d2 title="A course edit reaches the search index through the same DynamoDB stream progress recalculation reads"
direction: right

table: "Core table" {shape: cylinder}
stream: "DynamoDB Stream"
recalc: "Progress recalculation"
index: "Search indexing"
search: "OpenSearch Serverless" {shape: cylinder}

table -> stream
stream -> recalc: "PROGRESS_STREAM_FILTERS"
stream -> index: "SEARCH_STREAM_FILTERS"
index -> search: "index / delete"
```

The core table's stream has one reader, the <Link path="design/stream-event-router">stream router</Link>, which sends each change to the queue of every feature registered for it. Search indexing is one such feature (`search-indexing`), with its own filter (`SEARCH_STREAM_FILTERS`, in `core-table/src/helpers`), queue and failure queue, so a failure in it never blocks progress recalculation.

`search-indexing.ts` uses a change only to learn which course changed, then reads that course as the table holds it now, the same philosophy as progress recalculation:

- A **course** or **course rating** record names its `courseId`. Each distinct course in the batch is read once by key, consistently, with its rating tally.
- If the course is `'published'`, its document is written (built by `toCourseDocument`, validated against `CourseDocumentSchema`); if it isn't published or is gone, its document is deleted.
- A document's id is always the course's own key (`courseId`), so a replayed, retried or reordered record converges on the same document rather than a duplicate -- idempotent, the same requirement the core table's own writers hold to.

A freshly created index starts empty: the stream only carries changes made after its mapping exists, so a course published before then isn't searchable until it's next written.

### Re-indexing a deployed stage

`src/search/search-reindex.ts` is a private Lambda (no event source, no API route) that pages through the published courses, writes them with `_bulk` using the same `toCourseDocument` the stream indexer uses, then deletes the documents of courses that aren't published any more. It runs under its own role because the collection's data access policy names only the stack's Lambda roles, so a person's AWS login gets a 403 on the data plane; `grantWrite`'s `aoss:WriteDocument` covers the deletes too. Run it after the index is recreated or an indexing bug:

```sh
pnpm nx run @discava/common-scripts:reindex-search --stage=discava-development
```

It prints how many courses were indexed and how many stale documents were removed, and running it twice leaves the same documents. A catalogue too big for one invocation's 5-minute timeout would need the Lambda to hand off to itself. Locally, `pnpm nx run @discava/e2e:seed-local-courses` seeds the index instead.

### Rolling out the catalogue fields

Courses carry five optional catalogue fields (`categoryId`, `tags`, `level`, `language`, `durationHours`), and the `courses` index maps them as `keyword`, `keyword` (an array), `keyword`, `keyword` and `integer`. The change is additive: it only adds properties, so index-sync's `putMapping` applies it to the live index in place on deploy, with no new index. Changing or removing an existing property would be a breaking change and needs the versioned index of #270 instead.

The document stores `categoryId`, not the category's name or slug. A rename then touches no document, and a response resolves names and slugs from the `category` records when it is built.

Facets are `filter` aggregations in one search request (see `buildSearchRequest` in `core-api`): every selected filter goes in `post_filter` so the hits are fully filtered, and each facet's aggregation applies every filter except its own, so its counts show what picking another value would give.

A course published before the deploy has no document with these fields until it is next written, so after deploying the change **invoke the re-index Lambda once**:

```sh
pnpm nx run @discava/common-scripts:reindex-search --stage=discava-development
```

It rebuilds every published course's document, with the fields, from the course records. Running it again leaves the same documents.

## The search procedure

`core-api`'s `course.publicSearch` is built on `publicSearchProcedure` (in `src/init.ts`), which adds a hand-written search plugin (`createSearchPlugin`, in `packages/apis/core-api/src/middleware/search.ts`), the same pattern as `courseProcedure`'s core-table plugin -- the `connection` generator has no tRPC → OpenSearch combination yet.

It's public, like `course.publicList`: a signed-out caller can search too. Visibility is enforced twice, once at index time (above) and again in the query itself, which always filters to `status: 'published'` even though every indexed course already is one. A bug in one isn't then the only thing standing between a caller and a draft or archived course.

## Suggestions

**Spec:** [`specs/20261119-195009-search-suggestions/`](https://github.com/AlexTo/discava/tree/main/specs/20261119-195009-search-suggestions/)

The student portal's "What do you want to learn?" box shows up to 10 matching courses as you type. `course.publicSuggest` (`{ q }` in, `{ items: [{ courseId, title, imageKey? }] }` out) is built on `publicSearchProcedure`, in the same file as `publicSearch`, with its request built by `buildSuggestRequest` (`helpers/suggest-query.ts`).

### Why not `publicSearch`

`publicSearch` always runs five facet aggregations, reads every category from the core table and returns full result cards. Suggestions need none of that, and fire far more often. A separate procedure also gets its own input bounds (3 to 200 characters) and a shorter timeout without loosening `publicSearch`'s. A `mode` flag on `publicSearch` was rejected: one procedure with two output shapes is harder to type and test.

### The query

A `match_bool_prefix` on `title`, inside the same `function_score` with `ratingBoost` and the same `status: 'published'` filter as full search. Each analysed term but the last is matched as a whole (stemmed) term and the last as a prefix, so whole words stem as they do in full search and "pyth" finds "Python for Data Analysis". The request sets no `operator`, so the terms are OR'd: one matching term is enough, and a course matching more of them scores higher. "java zzzz" still suggests the Java courses. Requiring every term (`operator: 'and'`) would be a change to `suggest-query.ts`, not a docs change. Hits sort by score, then `publishedAt` descending, then `courseId`. There are no aggregations, `track_total_hits` is off, and only `courseId`, `title` and `imageKey` are fetched.

It queries the existing `title` field, so the mapping doesn't change and no stage needs a re-index. The known limit: the last term is stemmed before the prefix is applied, so a part-typed word whose stem isn't a prefix of the indexed stem can miss until the next character is typed. If that proves too common, the follow-up is a `title.suggest` sub-field of type `search_as_you_type` with the `standard` analyzer, queried with `multi_match` `bool_prefix`. It is additive (`putMapping`) but needs one re-index per stage.

### Typing, debounce and reuse

- Nothing is sent under **3 characters** (after trimming) or over 200.
- The trimmed text is **debounced by 300 ms** (`useDebouncedValue`), so a burst of typing sends one request, for the last text.
- The query is keyed by the text, so a slow answer for "javas" lands in the "javas" cache entry and never replaces the list for "javascript". Retyping a recent text within `staleTime` (60 s) reuses its answer and sends nothing.
- Submitting the form or choosing a row cancels the pending debounce, so no request fires for text that was already submitted.

### Failure, timeout and throttle

The request has a **3 s timeout** (`SUGGEST_REQUEST_TIMEOUT_MS`), shorter than `publicSearch`'s, so a cold collection doesn't hold Lambda concurrency on every pause. A `TimeoutError` becomes tRPC `TIMEOUT`, as in `publicSearch`. The portal treats any error, a 429 included, as "no suggestions": it shows no alert and does not retry, because the next pause replaces the request anyway.

`course.publicSuggest` is in `PUBLIC_OPERATIONS`, which would give it the shared `publicThrottle`. That limit is shared by every caller, not counted per visitor, and is far too tight for suggestions, the most frequent request core-api gets: on `discava-development` it is 1 request/s with a burst of 3, so two people typing at once would make the dropdown quietly stop working. It therefore has a throttle of its own, set by two `coreApi` stage keys, `publicSuggestThrottleRateLimit` and `publicSuggestThrottleBurstLimit` (default 100 / 200), which only `course.publicSuggest` uses:

| Stage | Suggest throttle (rate / burst) | Other public operations |
|---|---|---|
| `discava-development` | 5 / 10 | 1 / 3 |
| `discava-production` | 100 / 200 | 20 / 40 |
| Default (stage sets neither key) | 100 / 200 | 20 / 40 |

One person typing steadily costs about 1 request/s. Development's 5 / 10 covers about five testers at once and keeps what an anonymous flood can reach small (WAF is off there, and core-api's reserved concurrency of 10 still caps concurrent requests). Production's 100 / 200 covers about 100 people typing at the same moment; a request is a 10-hit query with no core-table read, so it holds a Lambda for tens of milliseconds. Raise it with real traffic, like the stage's other limits. There is no per-IP rate rule on either stage, so one heavy caller can still use the whole limit, as for the other public operations.

## Local dev

An `opensearchproject/opensearch` container (`packages/common/scripts/src/opensearch`, the same `runLocalContainer` pattern as DynamoDB local and S3Mock), security plugin disabled and memory capped, started by `@discava/search`'s `dev` target. Its image is pinned in `packages/databases/search/config.json` to a 3.x release rather than `latest`: [OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-overview.html) upgrades collections automatically to new open source releases and requires clients compatible with OpenSearch 3.x, so local dev stays on that line without moving every time a release lands. It's the newest release at the time, chosen over an older one to match Serverless, so unlike the other local images it wasn't held back two weeks. Re-pin it when Serverless moves to a newer minor version, and re-check the calls in `sync-indices.ts` and the procedures against its [list of supported operations](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-genref.html). `pnpm nx run @discava/common-scripts:reset-local-data` also wipes its indices. The local event runner (`packages/events/src/local/event-runner.ts`) routes `SEARCH_STREAM_FILTERS` matches to the same indexing handler deployed stages use.

## Deviations from #1267

Kept here so the upstream `ts#opensearch` proposal (or a PR adopting it) can check each one:

- CDK has no L2 construct for `AWS::OpenSearchServerless::*` yet, only L1 `Cfn*` resources; `OpenSearchCollection` hand-rolls the data access policy and `grantRead`/`grantWrite` on top of them.
- A grantee's data access policy entry needs its literal principal ARN (OpenSearch Serverless authorises by ARN there, not via the grantee's own IAM policy). Each grant creates its own policy in the grantee's stack, named from the grantee's construct path, rather than one shared policy in a stack that depends on every grantee: a shared policy would import every role's ARN, and CloudFormation then refuses to deploy a stack that stops exporting a role that moved to another stack.
- The index-sync custom resource's own data access grant is a separate, eager, same-stack policy from the one `grantRead`/`grantWrite` populate: it has to exist before the custom resource first runs, during the collection's own stack's deploy, which a deferred cross-stack policy can't guarantee.
- Every collection is created inside its own NextGen `AWS::OpenSearchServerless::CollectionGroup` (see "Cost" above), a resource that postdates #1267; a generator written against #1267 as it stands would create a classic, always-on collection instead.
- The target that generates the indices manifest is `generate-indices-manifest`, not `indices`: every other target in this workspace is a verb (`compile`, `bundle`, `pull-image`), and `indices` reads as if it creates or lists indices rather than writing the manifest file.
