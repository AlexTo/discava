## The rule

**A certificate is only ever written server-side, by the progress recalculation, and a student has at most one per course.** It is issued when the student has completed the course (see <Link path="design/progress-and-completion">Progress and completion</Link>) **and** met the criteria in force for the course at that moment. Nothing a student or an instructor does in a browser can create one.

Completion itself is unchanged by the criteria: an enrolment still becomes `completed` when every visible item is complete. "Completed, with no certificate yet" is a normal, lasting state, and the course home explains what is still required.

## The criteria

- **Where they live**: a `certificateCriteria` map on the course, beside the per-course switch: `{ version, requireQuizPass }`. A new course has `{ version: 1, requireQuizPass: false }`. `setCertificateCriteria` is its only writer after creation and adds one to `version` only when something changed.
- **The rule**: `evaluateCertificateCriteria` in `core-table` is a pure function used by both the issuer and the reader (`certificate.requirements`, which the course home shows), so the page and the issuer can't disagree. With `requireQuizPass` on, every assessed quiz must be passed: its `passedAt` is set (and `passedAt` is permanent) **and** the student's best score reaches the quiz's *current* pass mark. So raising a pass mark can hold back a certificate that hasn't been issued yet, and lowering one can release it. An assessed quiz is an effectively visible quiz with a pass mark above 0; a quiz with a 0% pass mark is practice and is not assessed.
- **Changing criteria on a live course**: the criteria read when a student is evaluated apply. A certificate already issued is never re-examined. Loosening issues certificates to everyone it makes qualify; tightening only affects students who haven't qualified yet. The instructor's control says this before saving.

## Graded uploads

A second criterion, `minUploadScorePercent` (a whole number from 1 to 100, absent when not required), sits in the same map and is set through the same `setCertificateCriteria`, which removes it when given `null`.

- **The rule**: with it set, every effectively visible assignment is assessed. One is met when the student's submission is `returned` and `floor(points / pointsOutOf * 100)` is at least the minimum, where `pointsOutOf` is what the work was graded out of (the assignment's `maxPoints` when there is no grade to read it from). A submission that is missing is "not submitted", one not yet returned is "waiting to be graded", and one returned with fewer points is "below the score". A course with no visible assignment has nothing to meet.
- **Regrading**: a submission's `status`, `points` or `returnedAt` changing recalculates that student, so a grade amended upwards issues the certificate, and a resubmission (which changes none of them) does nothing. A returned submission that an instructor reopens is waiting again and doesn't count until it is returned.
- **What is recorded**: the certificate's `assessment` keeps `minUploadScorePercent`, `assessedUploadCount` and one `upload` entry per assignment in the internal list; the band is over quizzes and uploads together. The statement gains "Graded assignments returned with at least 60%: 2."
- Submissions are read only when the criterion is set.

## What the certificate records
The certificate copies the criteria it was issued under, with their `version`, into a read-only `assessment`, so what it describes never drifts when the course changes:

- the two settings, the number of visible items, the number of assessed items, the lowest and highest pass mark, the course length in hours and a **score band** (the ten-point band of the mean of the best scores, from 0–9% up to 90–100%). Each is shown on the public page and in the PDF as the same lines of text (`assessmentStatement`).
- the **list of assessed items** with each score. It exists so an invariant can check the rule, and it is never returned by any API or shown.
- When nothing was required, there is no band and the statement says "No graded assessment was required for this certificate." An exact score is never shown.

## What makes a waiting certificate arrive

The recalculation (see <Link path="design/progress-and-completion">Progress and completion</Link>) runs for more than a completed item. A student who qualifies is issued a certificate within seconds of:

- passing a quiz after its item was already complete (attempts used up, limit raised, a later attempt passing), or a better best score on a quiz already passed: that student;
- the criteria changing, or certificates being turned on: every enrolled student who hasn't dropped;
- a quiz's pass mark changing (including to or from 0, which changes whether it is assessed): every enrolled student who hasn't dropped;
- the item completions and visibility changes that already triggered it.

This replaces the "no backfill" limitation: turning certificates on now issues to everyone who already qualifies.

## How it is issued

- The progress recalculation Lambda calls `issueCertificate` after it writes a student's progress and enrolment, when the student is not dropped and the enrolment is `completed`.
- It reads the student's `certificate` for the course first. Only when there is none does it read the course and the user, so students still in progress, and students who already have a certificate, cost no extra reads.
- `issueCertificate` is the only writer of `certificate`. It creates the record with a condition that the key doesn't exist already, so two recalculations running at the same moment still leave one certificate with one ID, and both return it. An error is never swallowed: the batch is retried.
- The certificate copies what it prints (the learner's name, the course title and the completion date) at the time it is issued. Renaming the course later doesn't change it.
- The ID is 16 characters of Crockford base32, shown as `XXXX-XXXX-XXXX-XXXX`. Lookups ignore dashes, spaces and case, and read `O` as `0` and `I` or `L` as `1`.

## The per-course switch

An instructor turns **Issue a certificate on completion** on or off in the course's settings, in any course status. It is on for every new course.

- It applies from then on. Turning it off never removes or invalidates a certificate already issued, and turning it on gives a certificate to every student who has already qualified, within seconds.
- Existing certificates keep verifying while the switch is off.

## What the public page shows

`/certificates/<ID>` in the student portal needs no sign-in. It shows the learner's name, the course title, the completion date, the certificate ID and the assessment statement, and nothing else: no email, no user ID, no scores per item and no link to the learner's account. An ID that is malformed or unknown gets the same "Certificate not found".

A **revoked** certificate shows "This certificate has been revoked and is no longer valid", with the ID and the date, and nothing about the learner, the course, the reason or who acted. It is distinct from "not found" so an ID that used to verify doesn't look like a platform fault. The change shows on the next load of the page, and the link preview and the PDF check follow it. `certificate.pdf` refuses a revoked certificate ("This certificate has been revoked"); a PDF already downloaded can't be recalled and the page is the truth.

## Revoking and restoring

- **Who**: an instructor of the course lists its certificates (Certificates section of the course) and revokes one with the reason `academic-integrity`, `issued-in-error` or `other` (with a note). An administrator looks up any certificate by ID and may also use `refunded`.
- **Restore**: an administrator always; an instructor only a revocation made by an instructor. An instructor sees "Revoked by an administrator" and no Restore on the other kind.
- **The record**: the certificate carries its current state (`revokedAt`, `revocationReason`, `revokedByRole`), and every change also appends a `certificateEvent` (`revoked` or `restored`, actor, role, reason, note, time) in the same transaction. `revokeCertificate` and `restoreCertificate` in `core-table` are the only writers of both. The history is kept for an audit; a revoke, restore and second revoke leave three events.
- **Races**: the write is conditioned on the state it expects, so two simultaneous revokes leave one revocation and one event, and both requests are answered.
- **Never replaced**: a revoked certificate keeps its ID and is never re-issued; the recalculation stops at an existing certificate whatever its status. Restoring makes the same ID valid again.
- **Telling the learner**: `certificate.revoked` and `certificate.restored` notifications go out after the change, with the reason category and a dedupe key of the certificate ID and the event time.
- **Nothing revokes automatically.** In particular a refund does not: certificates survive refunds, and an administrator revokes with the reason `refunded` when that is warranted. This is the decision taken by default (research R-8 in the spec lists what revoking on every refund would change), pending the maintainer's confirmation.
- **A revoked certificate hides its actions**: the LinkedIn action is hidden, `recordLinkedInClick` refuses it, and the share reminder is never sent for it.

## Invariants

The invariant checks (see the spec's research R-10) hold that: a certificate's `assessment` is well formed and its counts, pass marks and band follow from the listed items; every listed quiz was passed by the student no later than the issue time, at or above its pass mark, and every listed upload scored at least the recorded minimum and still has a submission, even one reopened since (`certificate-met-criteria`); a certificate is revoked exactly when its latest event is `revoked` (`certificate-status-matches-history`); every course has well-formed criteria; and a certificate still needs a completed (or dropped-after-completion) enrolment, revoked or not. Not violations: a completed enrolment with no certificate, a certificate that differs from the course's current criteria, and a listed quiz since hidden or given a higher pass mark.

## Sharing and verifying

A student finds their certificates in **My Learning**, on each completed course, with four actions:

- **View** opens the public page.
- **Download PDF** saves a one-page A4 certificate that carries the same ID and the page's address.
- **Copy link** copies the public page's address.
- **Add to LinkedIn profile** opens LinkedIn's form for a new certification (see below).

Anyone with the link, or the ID, can check a certificate on that page.

## Adding it to LinkedIn

The student portal builds the link in the learner's browser (`lib/linkedin-add-to-profile.ts`, `buildLinkedInAddToProfileUrl`) and opens it. No server builds or sees it, and nothing is sent to LinkedIn until the learner clicks.

- **What is sent**: LinkedIn's `profile/add` address with `startTask=CERTIFICATION_NAME`, `name` (the course title printed on the certificate), the issuer (`organizationName` from the platform name set on the admin portal's Branding page, or `organizationId` instead when the stage sets `linkedInOrganizationId`, never both), `issueYear` and `issueMonth` (from the completion date in UTC), `certUrl` (the public page's address) and `certId` (as displayed). There is no expiry. Every value is percent-encoded.
- **What never is**: the learner's name, email, user ID or any session value. LinkedIn knows who the member is; we don't tell it. The link carries `rel="noopener noreferrer"` so the browser doesn't name the referring page, and no LinkedIn script or API is loaded or called.
- **What the click records**: the first click calls the public `certificate.recordLinkedInClick({ certificateId, source })`, which sets `linkedInClickedAt` and `linkedInClickSource` on the certificate once and never changes them. A failure to record never stops the form from opening. The record means "the learner opened the form", not "the certificate is on LinkedIn": LinkedIn sends nothing back.
- **Where a click can come from**: `linkedInClickSource` is one of `my-learning`, `certificate-page`, `issued-email` and `reminder-email`. The two emails link to `/certificates/<ID>/linkedin?source=…`. That portal route works signed out, records the use and replaces the page with LinkedIn's address.
- **Reading uptake**: the share of certificates with `linkedInClickedAt`, split by `linkedInClickSource`. The figure is derived from the stored records.
- **If LinkedIn ignores the values**: the link still opens the right form, and the owner's view of the public page lists every value to copy by hand. LinkedIn's own help says customised links may not autofill; a maintainer checked on 2026-11-20 that the form opens with the values (research R-1 to R-3 in the spec).

## Telling the learner

- **The notification** `certificate.issued` is written in the same transaction as the certificate by `issueCertificate`, with the certificate ID as its dedupe key, so there is never a certificate without its notification, and a retry doesn't make a second one.
- **The email** has two links: the certificate's page, and **Add to LinkedIn profile** (the notification's optional `action`, which the bell ignores).
- **The setting**: one switch, **Certificates**, in Notification settings governs both the issue email and the reminder. `certificate.reminder` has no setting of its own (`emailPreferenceType` points at `certificate.issued`), and unsubscribing from the first email also stops the reminder.
- **The reminder**: three days after issue, a one-time EventBridge Scheduler schedule (`cert-reminder-<ID>`) invokes the `certificate-reminder` Lambda. It stops if the email type is off. Otherwise it claims the reminder with a conditional write of `reminderSentAt` that only succeeds when no click has been recorded and no reminder was sent, then publishes `certificate.reminder` with the stored time. A click and a send are safe against each other: whichever write lands first decides. A later recalculation repairs a certificate that was issued but never scheduled (research R-4 to R-7).

## The link preview

Link-preview crawlers run no scripts, so the page renderer (see <Link path="design/public-pages">Public pages</Link>) answers `/certificates/<ID>` with a head built from `certificate.verify`: the title "the learner completed the course", the completion date, the platform name and the ID. It never shows more than the page does. The page is always `noindex`, on every stage, because it names a person. Deeper paths such as `/certificates/<ID>/linkedin` get the plain template (research R-8).

## Limitations

- Criteria have no history: only the version and settings a certificate was issued under are kept, on the certificate.
- A quiz is assessed by its own pass mark; there is no course-wide pass mark and no per-quiz choice of what counts.
- A revoked PDF that was already downloaded still exists; only the page says it is no longer valid.
- LinkedIn sends nothing back, so Discava can't tell whether a certificate was saved to a profile, only that the form was opened.
- Anyone holding the certificate ID can record a first use. Its only effect is one reminder fewer.
- The PDF uses standard fonts, so characters outside Latin-1 (for example Chinese, Japanese or emoji) print as `?`. The public page shows them correctly.
