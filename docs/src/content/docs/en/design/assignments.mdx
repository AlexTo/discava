A student submits one file to an upload assignment and can replace it until it is returned. An instructor of the course lists every enrolled student's work, opens a submission, and either returns it as final with points and feedback, or asks for a resubmission with feedback only. Only the course's instructors can list, read or return submissions.

## Submissions and grading

A submission is one `assignmentSubmission` record per student per assignment. Its `status` moves like this:

| Transition | Who | Condition | Effect |
|---|---|---|---|
| Submit (first) | Student | No submission yet | `submitted`, `version` 1, enters the waiting index |
| Resubmit | Student | `version` unchanged and status `submitted` or `resubmission_requested` | `submitted`, `version` + 1, back in the waiting index |
| Request resubmission | Instructor | `version` and `reviewRevision` unchanged, status `submitted` | `resubmission_requested`, leaves the waiting index |
| Return as final | Instructor | `version` and `reviewRevision` unchanged, status `submitted` or `resubmission_requested` | `returned`, sets points, locks the student out of resubmitting |
| Amend grade | Instructor | `reviewRevision` unchanged, status `returned` | Points and feedback change, status stays `returned` |

Every instructor action adds one to `reviewRevision`. Each write is conditioned on the `version` and `reviewRevision` the instructor was looking at, so a return can't land on a file the student has since replaced, and when two instructors act at once exactly one wins. Points are a number from 0 to the assignment's `maxPoints` (at most two decimals); `pointsOutOf` keeps the maximum the work was graded against if `maxPoints` changes later. Returning or amending is refused for a student who is no longer enrolled, though the instructor can still read their work.

A resubmission request doesn't undo the student's completion of the assignment, and a resubmission after a request doesn't count the student a second time in the content item's `studentActivityCount`.

## Feedback rounds

Each instructor action writes one `submissionFeedback` record: a resubmission request, a final return, or an amendment. Rounds are append-only and keyed by submission and time, so a student's history is one query, newest first. They are separate records because feedback can be 20 000 characters of Tiptap JSON per round and the number of rounds is unbounded; a list on the submission could reach DynamoDB's item size limit. The submission keeps only the current grade. The student sees earlier feedback across resubmissions, so they know what was asked. Feedback is required on a resubmission request and optional on a return.

The student is notified in the app and by email (on by default) of each action: `assignment.returned`, `assignment.resubmission_requested` and `assignment.grade_updated`, each deduplicated on the round's `feedbackId`. The notification and the round are written in the same transaction as the submission change.

## The waiting index and enrolment

Submissions waiting for a first look (status `submitted`) carry `waitingCourseId` and `waitingSince`, which key a sparse index (`byWaiting`) with the course as partition and the submission time as sort key. The grading queue on the instructor home page is therefore one query per course the instructor teaches, each already oldest first, merged in memory. Every write that changes `status` sets or removes both attributes together through `waitingKeys`.

**Enrolment is applied at read time.** The queue batch-reads the listed students' enrolments and drops those who are `dropped`. Storing enrolment in the index would make refunds and checkout rewrite every submission a student has in the course, inside their own transactions. Reading it instead leaves the payment code alone, and a student who re-enrols reappears in the queue with no write.

The per-assignment list reads every submission and every enrolment of the course (two single-partition queries), merges them, and pages in memory, 50 rows at a time, with a cursor that encodes the last row's sort position. Students with no submission appear as "not submitted", and those who left as "no longer enrolled".

## The daily notice

Instructors are told about new submissions by `assignment.submissions_received`, at most once per assignment per day (UTC) per instructor, in the app, with email off by default. A small `submissionNotice` record (one per assignment per day, expiring two days later) is the marker. `submit` reads it first; if it is absent, the same transaction creates it and writes a notification per instructor, capped so the transaction stays under DynamoDB's 100-item limit. If another submission wins the race, the existing retry runs again without the marker and notifications. This makes "at most once a day" a database fact rather than a timing hope.

## Previewing a submitted file

The review page shows PDFs and images (png, jpg, jpeg, gif, webp) beside the grading form; every other file type shows its details and a Download button.

- **Images** are an `<img>` using the same five-minute signed CloudFront URL as a download. Browsers ignore `Content-Disposition` for images.
- **PDFs** are fetched from the signed URL and drawn to canvas by `react-pdf` (PDF.js), loaded only on the review page. The stored files are served with `Content-Disposition: attachment` and the portal's CSP blocks `<iframe>` and `<embed>`, so drawing to canvas needs no change to the distribution, CSP or stored objects.

**Known gap: JPEG 2000 and JBIG2.** PDF.js decodes these embedded image formats with WebAssembly, which the portal's CSP (`script-src 'self'`, no `'wasm-unsafe-eval'`) blocks. Such images may not draw, but the rest of the page renders and Download still works. Loosening a shared CSP for this was judged not worth it.

An instructor's unsent points and feedback are kept in their own browser, per submission, and are not saved on the server.

## Rules the checks enforce

The shared helpers in `assignment-grading.ts` are the only writers of the grade fields, the waiting keys and `submissionFeedback`. Invariant checks cover: grade shape (`returned` has points within `pointsOutOf`, a returner and times; nothing else does), waiting keys agreeing with `status`, rounds belonging to a submission, round shape, and the newest round matching the submission's state and `reviewRevision`.
