## The rule

**A priced course is entered only by a paid order, and only Stripe's signed confirmation makes an order paid.** Nothing a browser sends, including the return from Stripe's page, enrols anyone. core-api's `course.enrol` refuses a priced course ("This course must be purchased"), and the webhook is the only caller of `settleOrderPaid`.

There is one case with no payment: a [coupon](#coupons) that takes the whole price. The server computes that the total is zero and writes the order already `paid`, so Stripe is never called.

## Prices

A course has `priceAmount` and `priceCurrency`. The amount is an integer in the currency's smallest unit (1999 is 19.99), so no price is ever a floating point number. `0` is free, and every new course starts free.

- The supported currencies are USD, EUR, GBP, AUD and CAD. All have two decimals. A currency with none or three isn't supported.
- A price above zero is between 1.00 and 10,000.00.
- An instructor sets the price with instructor-api's `course.setPrice`, in any course status. Setting a price above zero needs an active Stripe connection. Going back to free never does.
- A price change applies to new purchases. It never touches an order or an enrolment: students already enrolled keep their access.

The rules and the formatting live in `@discava/common-web-utils/price`, shared by the portals and the APIs.

## The order

An `order` is one attempt by one student to buy one course. When it is created it copies the course title, the list price (`listAmount`), the amount to charge (`amount`) and the currency, along with the Stripe account and mode it was started under. An order started with a coupon also copies `discountAmount`, `couponCode`, `couponType` and `couponValue`, and `amount` is the list price less the discount.

| Status | Meaning |
| --- | --- |
| `pending` | A checkout is open |
| `paid` | Stripe confirmed the payment and the student is enrolled |
| `expired` | The checkout was abandoned, or creating it failed |
| `refunded` | The whole amount went back to the student |

`helpers/order.ts` in core-table is the only writer of `order` and of an enrolment's `orderId`. Every move is a conditional write on the status it comes from, so a repeated or racing call changes nothing. None of it calls Stripe: the caller does that before or after.

## Starting a checkout

core-api's `payment.checkout` takes a course ID and an optional `couponCode`. The amount and currency are computed on the server from the course (and the coupon), never taken from the input. Without a code:

1. It refuses a course that isn't published, a free course, and a student who is already enrolled.
2. If the student has a `pending` order for the course with no coupon and more than five minutes left, it returns that order's page, so choosing **Buy now** twice makes one order.
3. Otherwise `startOrder` creates a `pending` order in one transaction that also checks the Stripe connection is `active` and raises the connection's `latestCheckoutExpiresAt` to cover the new checkout.
4. It creates a Stripe Checkout session with the order ID as the idempotency key, card payments only, and the order, student and course IDs in the metadata. The session's address is stored on the order and returned.

A checkout lives for one hour. If Stripe can't be reached, the order is expired and the student sees "Couldn't start the payment".

A checkout with a code follows the same steps with a claim on the code added: see [Coupons](#coupons).

`payment.available` tells the student portal whether a purchase can start: only that the connection is active, nothing about the account or the key.

## The webhook

Stripe posts to `POST /stripe/webhook`, an API Gateway API of its own in the `Payments` stack, with its own WAF, throttling and domain. The handler is in `packages/events/src/payments/`.

- **The signature is the only gate.** The message is verified against its exact bytes with the stored signing secret, and refused with 400 if it is older than five minutes or doesn't verify. With nothing connected there is no secret, so every message fails.
- **400** means nothing changed. **500** means handling failed and Stripe should retry. **200** covers handled, duplicate, unmatched and ignored events.

| Event | What happens |
| --- | --- |
| `checkout.session.completed` | The order is settled, or refunded if it can't be delivered. A session that isn't paid yet is ignored |
| `checkout.session.expired` | A `pending` order becomes `expired`, and its coupon claim is released |
| `charge.refunded` | The refund is recorded against the order |
| `refund.failed`, `charge.refund.updated` (`status: failed`) | `refundFailedAt` is set on the order, which stays `paid` |

These are the only events registered with Stripe.

### Delivering exactly once

`settleOrderPaid` moves the order from `pending` to `paid` and gives the student their enrolment in **one transaction**, which also checks the course is still published. The enrolment is created, or restored if the student had a `dropped` one. If the order holds a coupon, the same transaction confirms its redemption. Stripe delivers at least once and in any order, so the same confirmation arriving five times at once still leaves one paid order and one enrolment: every call after the first finds the order is no longer `pending`.

### A payment that can't be delivered

The money was taken, so it is never kept. The webhook asks Stripe for a full refund, with an idempotency key built from the order ID, and `refundUndeliverable` marks the order `refunded` with a reason. No enrolment is given, and the order's coupon claim is released.

| Reason | When |
| --- | --- |
| `duplicate` | The student is already enrolled |
| `unavailable` | The course is no longer published |
| `mismatch` | The session's amount, currency, or order, student or course ID differs from the order's. This is also logged as an error ("Paid session differs from its order; refunding"), and the student has been refunded by the time the line appears |

A paid session, expired session or refund whose order isn't in the table is logged as an error ("Paid session for an unknown order", "Expired session for an unknown order", "Refund for an unknown order") and answered 200. An operator should watch for these lines: they mean Stripe holds a payment Discava has no record of.

## Coupons

An instructor makes discount codes for a paid course with instructor-api's `coupon.create`, `coupon.list`, `coupon.update` and `coupon.delete`. A student types one on the course page: core-api's `coupon.preview` shows what they would pay and writes nothing, and `payment.checkout` takes the code as `couponCode`. The <Link path="guides/payments">Payments guide</Link> covers the screens.

| Record | Key | Holds |
| --- | --- | --- |
| `coupon` | Course, then code | `type` (`percent` or `fixed`), `value`, optional `expiresAt` and `maxRedemptions`, `enabled`, and `redeemedCount` |
| `couponRedemption` | Course and code, then student | The order it belongs to, `status` (`reserved` or `redeemed`), and `reservedUntil` while reserved |

The key of `couponRedemption` is the rule that a student uses a code once.

### Codes and prices

- A code is 4 to 24 characters of A-Z, 0-9 and `-`, stored upper case. A generated code is 8 characters written `XXXX-XXXX`.
- A percentage is a whole number from 1 to 100. A fixed amount is in the course's currency, above zero and not above the course's price when the code is made.
- A code's type, value and currency never change. `coupon.update` changes only `enabled`, the expiry and the limit, and can't lower the limit below `redeemedCount`. `coupon.delete` works only while `redeemedCount` is 0; a used code is disabled instead.
- `priceWithCoupon` in core-table's `helpers/coupon-price.ts` is the one price function. A percentage is rounded down, and a fixed amount never takes more than the list price.
- A total above zero but under Stripe's minimum charge (0.50, or 0.30 for GBP) can't be paid, so the code is refused.

`coupon.preview` and `payment.checkout` run the same check (`checkCoupon`), so they refuse the same codes with the same messages. An unknown code, another course's code and a fixed code in another currency all get "This code is not valid for this course", so a student can't tell them apart.

### Claim, confirm, release

`helpers/coupon-redemption.ts` in core-table is the only writer of `redeemedCount` and of `couponRedemption`. It builds three sets of writes, each run inside the transaction of the order change that causes it:

| Step | When | What it writes |
| --- | --- | --- |
| **Claim** | `payment.checkout` creates the order | Adds one to `redeemedCount`, on the condition that the coupon is enabled, not expired and under its limit. Creates the student's redemption as `reserved`, which fails if they already have one for the code |
| **Confirm** | `settleOrderPaid` marks the order paid | `reserved` becomes `redeemed` |
| **Release** | The order expires, is replaced by a new checkout, or is refunded as undeliverable | Deletes the `reserved` redemption and takes one off `redeemedCount` |

`redeemedCount` therefore counts reserved and redeemed redemptions together. Because the claim is a condition in the order's own transaction, the limit holds when many students start a checkout at the same moment. A cancelled transaction writes nothing; checkout reads again to give the exact refusal, and gives up with "Too many people are checking out; try again" after three conflicts.

A reservation lasts until five minutes after its checkout expires (`reservedUntil`). When a code looks used up, checkout first releases its reservations that are past that time and whose Stripe session has ended, then checks once more. A session Stripe reports as complete keeps its reservation: its paid event may still be on the way.

### One live checkout

A student has one live checkout per course. Starting a checkout with a different code, or with none after one with a code, replaces the earlier `pending` order:

1. The earlier order's Stripe session is expired first, so it can never be paid.
2. The new order's transaction moves the earlier order to `expired` and releases its claim.

If Stripe says the earlier session was already paid, the answer is "You are already enrolled in this course". Starting again with the same code and more than five minutes left returns the open checkout's page.

### A code that takes the whole price

When the total is zero, `startFreeOrder` writes the order already `paid` with amount 0, the enrolment and the redemption as `redeemed`, in one transaction. Stripe is never called and `payment.checkout` returns `enrolled: true` in place of a page address. It still needs an active Stripe connection. Such an order isn't a sale, so it records no <Link path="design/instructor-payouts">earnings</Link>.

### Coupons and refunds

A full refund after delivery leaves the redemption `redeemed`, so the student can't use the same code again.

## Refunds

A refund starts in Stripe: from the Stripe dashboard, or from core-api's `payment.requestRefund` on the student's behalf. `charge.refunded` carries the total refunded so far, and `refundOrder` applies it:

- **Below the order's amount**, only `refundedAmount` rises. The student keeps access.
- **At the order's amount**, one transaction moves the order to `refunded` and sets the enrolment to `dropped`, but only if the enrolment still names this order. A refund notice delayed past a second purchase can't end the new enrolment.

After a full refund, the webhook publishes an `order.refunded` notification ("Your refund for … is complete"), emailed as well as shown in the portal. It is sent only when the order is `refunded` with reason `requested` (every full refund recorded from `charge.refunded`, whether from the dashboard or a student's request) and the enrolment still names the order. Its dedupe key is the order ID, so a redelivered notice doesn't repeat it, and a publish that failed is retried by Stripe's redelivery. There is no notification for a partial refund, or for the automatic refund of a payment that couldn't be delivered.

### Refund requests

core-api's `payment.requestRefund` lets a student refund their own purchase, and `payment.myOrder` tells the course page whether they can. `refundEligibility` in core-table allows it only while:

- the order is `paid` and the student's enrolment names it and isn't `dropped`;
- the order was paid through the Stripe account connected now, and payments are connected;
- no refund has been requested for it yet;
- the student hasn't completed the course;
- the student has completed less than `REFUND_PROGRESS_LIMIT_PERCENT` (50) of it, computed when the request is made from their completions and the current curriculum (`readRefundLimits`), not read from the stored `progressPercent`;
- none of the student's earlier orders for the course was refunded at their own request (`refundRequestedAt` set; an operator's refund or an automatic refund doesn't count);
- it is within `REFUND_WINDOW_DAYS` (14) of payment.

`requestRefund` asks Stripe to refund what's left of the amount, with an idempotency key built from the order ID, then sets `refundRequestedAt` on the order. It never moves the order or the enrolment itself: the `charge.refunded` that follows does. Stripe is called before the mark, so a crash between the two leaves a refund the notice still records, never a mark with no refund.

If Stripe reports the refund as failed (`refund.failed`, or `charge.refund.updated` with `status: failed`), `markRefundFailed` sets `refundFailedAt` on the order. The order stays `paid` with `refundRequestedAt` kept, so no second request is offered; `payment.myOrder` returns `refundFailedAt` and the course page tells the student the refund failed and to contact support. The course page polls a pending refund for a limited time (2 minutes), then says it is still being processed and offers a button to check again.

A dropped enrolment keeps its progress and completions. The student can come back:

- **By buying again.** Settling the new order restores the enrolment, as `completed` if they had finished the course, with their progress.
- **By enrolling, if the course is now free.** `course.enrol` calls `restoreFreeEnrolment`, which restores the enrolment and removes its `orderId`. No order is written.

### Leaving a course

`course.unenrol` ends an enrolment that was not paid for: `unenrolFromCourse` sets it to `dropped` only while it has no `orderId`, and refuses with `EnrolmentPaidForError` otherwise. A bought enrolment ends only by a refund, so a paid course cannot be left without one. Progress and completions are kept, and `course.enrol` restores the enrolment while the course is free. The course's status and price are not checked, so a student can leave an archived or since-priced course.

### Terms

- The two limits are constants in core-table's `helpers/order.ts`: `REFUND_WINDOW_DAYS` (14) and `REFUND_PROGRESS_LIMIT_PERCENT` (50).
- `payment.myOrder` and `course.publicView` return them as `refundWindowDays` and `refundProgressLimitPercent`, so the terms line on the course page states what the API applies.
- `course.myEnrolment` returns `refundedBefore`, so the page warns a student who was refunded at their own request before they buy again.
- An operator's refund in Stripe is not subject to any of these terms.
- Requests are refunded automatically, with no review.
- Certificates survive refunds.

## The Stripe connection

Stripe isn't configured at deploy time. An administrator pastes a secret key on the admin portal's **Payments** page.

- **`paymentConnection`** is one record holding the non-secret facts: status, test or live mode, the account's ID and name, the key's last four characters and the registered webhook address.
- **The key and the webhook signing secret** live in Secrets Manager. admin-api's dedicated `PaymentsConnect` function is the only code that can write them. The checkout function reads the key, the webhook reads both, and neither can write.
- **`paymentChange`** is an append-only audit row for every attempt: who, when, which account and the key's last four characters. It never holds a key or Stripe's error text.

Saving a key checks its shape, asks Stripe whose it is, registers the stage's webhook address for the three events, and stores the key and the signing secret Stripe returns.

| Save | What it does |
| --- | --- |
| **Rotation** (same account, same address) | Replaces only the key. The registration and signing secret stay, so open checkouts still complete |
| **Switch** (another account or mode, or a new address) | Takes a lease, registers with the new key, stores both secrets, then removes the old registration |
| **Disconnect** | Takes a lease, marks the record `disconnected` and clears the secrets |

A switch or disconnect takes a two-minute **lease**: the record's status becomes `changing`, which checkout and pricing treat as not connected. The lease is refused while a checkout may still be open ("Checkouts are open until …"), so no payment is in flight while the secrets are replaced. A rotation takes no lease, but is conditioned on the record's `revision`, so it loses cleanly to a concurrent switch. A change that fails puts the record and the secrets back.

## Invariants

Two files in core-table's `helpers/invariants/` check the rules that span records, after every end-to-end scenario:

- `payments.ts`: an order's fields match its status, the list price less the discount is the amount charged, a paid order has its enrolment, an enrolment's `orderId` names an order of the same student and course, and an enrolment with no order in a priced course dates from when the course was free.
- `coupons.ts`: `redeemedCount` equals the number of the coupon's redemptions and is within the limit, each redemption has its order (pending while reserved, paid once redeemed), and a free order made by a code has its enrolment.

## Local development

The event runner includes a Stripe stand-in (`packages/events/src/local/stripe-stand-in.ts`): Stripe's API, a hosted checkout page with **Pay**, **Decline card** and **Cancel**, and signed webhook deliveries to `/stripe/webhook` on port 2024. Connect it as Carol with the key `sk_test_local`. The key is kept in the git-ignored `tmp/local-dev/secrets/` in place of Secrets Manager.

Controls under `/stripe/test/` drive what a real Stripe account would: `refund`, `refunds` (list a payment's refunds), `replay` (deliver a confirmation again), `expire`, `forge` (a wrongly signed message) and `endpoints`.

`LOCAL_CHECKOUT_TTL_SECONDS` shortens a checkout's one-hour life, in local dev only.

## Limitations

- Card payments only, with no tax handling and no currency conversion.
