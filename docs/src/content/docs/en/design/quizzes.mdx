A quiz is a content item (`type: 'quiz'`) placed in a lesson's sequence alongside video, text and file items. It has one or more questions, each **single choice** or **multiple choice**.

A quiz can also be the one item of an assignment lesson (a lesson of `kind: 'assignment'`). It is created with `lesson.createQuizAssignment`, and is then edited and attempted like any other quiz. Short questions asked inside a video reuse the quiz question shape; see [Questions in videos](#questions-in-videos).

## Data model

### Quiz content item

Quiz-specific `contentItem` attributes. As with the other types, which attributes a type requires is enforced by instructor-api's zod schemas (`schema/quiz.ts`), not by ElectroDB.

| Attribute | Shape |
|---|---|
| `questions` | `[{ questionId, kind: 'single' \| 'multiple', prompt, options: [{ optionId, text }] }]`. `prompt` is Tiptap JSON. Safe to send to students |
| `answerKey` | `{ [questionId]: { correctOptionIds: string[], explanation? } }`. `explanation` is Tiptap JSON. **Never read by core-api except when grading** |
| `settings` | `{ passMarkPercent, attemptsAllowed /* null = unlimited */, shuffleOptions, revealAnswers: 'after_each_attempt' \| 'after_final_attempt' \| 'never' }` |
| `quizVersion` | Number, incremented on every save. A save names the version the editor loaded, and is refused if the quiz has moved on (see [Saving a quiz](#saving-a-quiz)) |
| `questionsHash` | Hash of `questions` only (not the key or `settings`), recomputed on every save (`hashQuizQuestions`) |

`questions` and `answerKey` are separate attributes so that passing a content item through to students can't leak the answers. Course reads (`course.view`, `course.publicView`) list a quiz by its title and position only. They never include `questions` or `answerKey`.

`questionId` and `optionId` are supplied by the client and must stay the same across saves, because the answer key, student answers and the reconcile step below all refer to them.

### `quizAttempt`

- pk `userId`, sk `courseId / contentItemId / attemptId`. `attemptId` is a UUIDv7, so a student's attempts at a quiz sort in submission order.
- Holds `answers` (`{ [questionId]: optionId[] }`), `correctQuestionIds`, `scorePercent`, `passed`, `quizVersion`, `questionsHash`, `submittedAt`, plus `moduleId` and `lessonId`. `correctQuestionIds` records which questions were graded right at the time, because the key can change later.
- Never updated once written.

### Per-user quiz summary (`quizSummary`)

- pk `userId`, sk `courseId / contentItemId`. Holds `attemptsUsed`, `bestScore`, `bestAttemptId`, `passedAt`, plus `moduleId` and `lessonId`.
- Written in the same transaction as each attempt. The first attempt creates it. Each later one is conditioned on the `attemptsUsed` it read, so the attempt limit holds even when two submissions race: the loser re-reads and is refused.
- `bestScore` only increases. `passedAt` is set by the first passing attempt and never cleared.
- Creating a student's summary increments the quiz's `studentActivityCount` (see <Link path="design/live-course-editing">Live course editing</Link>).
- The attempt that passes, or that uses the last attempt, also records the quiz's `itemCompletion` in the same transaction, unless there already is one (see <Link path="design/progress-and-completion">Progress and completion</Link>).
- The `quiz-summary-matches-attempts` invariant (`core-table/src/helpers/invariants/student-activity.ts`) checks that every summary agrees with its attempts and every attempt has a summary.

## Grading

- Server-side only, in core-api. The client never receives `answerKey` before submitting.
- Each question is all-or-nothing: the selected options must exactly equal `correctOptionIds`.
- Score is the percentage of questions correct, rounded down to a whole number, so a student is never shown more than they scored. `passed` is `score >= passMarkPercent`.
- The **best** score across all attempts, and across quiz versions, is the one that counts.
- A recorded pass is permanent, even if the pass mark is later raised or the quiz is edited.
- Past attempts are never regraded automatically.

## Student API

core-api has three procedures (`procedures/quiz.ts`), each taking the quiz's `courseId`, `moduleId`, `lessonId` and `contentItemId`. All three require:

- an enrolment that isn't `dropped` (`FORBIDDEN` without one in a published course, `NOT_FOUND` otherwise);
- a quiz that is effectively visible: the quiz, its lesson and its module visible and not archived. Otherwise `NOT_FOUND` "This quiz is no longer available".

**`quiz.view`** returns the questions, settings, `quizVersion` and `questionsHash`, never the answer key. It still works in an archived course, like the rest of the course.

**`quiz.submitAttempt`** takes `answers` and the `questionsHash` the student answered. It grades on the server and writes the attempt and the summary in one transaction. The same transaction checks that:

- the course is still published;
- the module, lesson and quiz are still visible and not archived;
- the quiz is still the `quizVersion` it was graded against;
- the enrolment still isn't dropped.

If anything changed in between, nothing is written and the submission is read and graded again, up to three times, before `CONFLICT`.

| Refusal | When |
|---|---|
| `PRECONDITION_FAILED` | The course is archived, or no attempts remain |
| `CONFLICT` | The questions changed since the student loaded them (see [below](#quiz-edited-mid-attempt)), or three tries lost a race |
| `BAD_REQUEST` | An answer names an unknown question or option, repeats an option, or gives more than one option to a single choice question |

**`quiz.myAttempts`** returns the student's summary (or `null`) and their attempts, latest first, a page at a time (`cursor` and `limit`, 10 by default and at most 100). The history is paged because with unlimited attempts it has no bound.

Each attempt's result shows which questions were right. The correct options and explanations (`reveal`) come back from `submitAttempt` and `myAttempts` only when `revealAnswers` allows:

| `revealAnswers` | When `reveal` is returned |
|---|---|
| `after_each_attempt` | Once the student has made an attempt |
| `after_final_attempt` | Once no attempts remain. Never while attempts are unlimited |
| `never` | Never |

## Quiz edited mid-attempt

With each submission the client sends the `questionsHash` of the questions it showed.

| What the instructor changed | Result of submitting |
|---|---|
| Only the answer key or explanations (hash matches) | Accepted and graded against the **current** key. The student notices nothing |
| Any prompt, question kind, or option's wording, count or order (hash differs) | `CONFLICT`, and **no attempt is used**. The client refetches and reconciles (below) |
| Pass mark | Accepted and graded against the current pass mark. A pass already recorded stays |
| `attemptsAllowed` lowered to or below `attemptsUsed` | Rejected with "No attempts remaining", showing the best score |
| Quiz, or its lesson or module, archived or hidden | Rejected with "This quiz is no longer available"; local draft discarded |

"Answer-key-only" means the student's screen would look identical before and after. Examples:

- Correcting which option is right: the key said EC2 for "Which service runs containers without managing servers?", and it's corrected to Fargate.
- Adding another correct option to a multiple-choice question. The screen doesn't change, because it always says "Select all that apply" and never how many are correct.
- Adding or rewording an explanation.

Reordering options counts as a change even though it's harmless, to keep the rule simple: if the screen could look different, the student reviews.

### Reconciling after `CONFLICT`

The client compares the old and new `questions` by `questionId`:

- **Unchanged:** the answer is kept.
- **Removed:** the answer is dropped.
- **New:** starts unanswered, marked **New**.
- **Changed prompt, options or kind:** answers pointing at options that still exist are kept (for a question switched to single choice, only if exactly one remains), and the question is marked **Updated**.

`reconcile` in `@discava/common-web-utils/quiz` does this. The student lands on the review screen with "This quiz was updated. Check the marked questions before submitting." The quiz query also refetches when the review screen opens and on window focus, so the banner usually appears before they press Submit. The `CONFLICT` is the guarantee.

## Student experience

The lesson is one scrolling page with items in `order`. A step bar at the top shows each item's state (✓ done, ⚠ a quiz finished without passing, otherwise the item type's icon) and scrolls to it. **A failed quiz never blocks moving on.**

The quiz is a card in the lesson flow (`QuizCard` in `common/shadcn`, shared with the instructor's preview). It moves through four screens:

| Screen | Shows | Buttons |
|---|---|---|
| Overview | "5 questions · Pass 80% · 1 of 3 attempts used", the best score and a Passed badge | **Start quiz**, **Resume quiz** (a saved draft) or **Retake quiz**. "No attempts remaining" when none are left |
| Question | One question, with "Select all that apply" and checkboxes for multiple choice, radios for single | **Back**, **Next**, and **Review answers** on the last question |
| Review | Every answer, with unanswered questions flagged | **Back**, **Submit answers** |
| Result | "This attempt: 60% · Not passed", each question right or wrong, and the correct options and explanations when `revealAnswers` allows | **Done**, **Retake quiz** |

- **Question navigator.** A quiz with more than one question shows a row of numbered buttons above the options. Each jumps to its question, is filled once answered, and names its state to a screen reader ("Question 2, answered").
- Feedback comes only after submitting, never per question, so the key can't be probed one option at a time.
- In-progress answers are saved to localStorage per quiz (`readQuizDraft`, `writeQuizDraft`). The attempt is created on the server only on submit.
- A lower retake shows "Your best score of 80% still counts."
- Accessibility: a `fieldset` per question labelled by its number and prompt, right and wrong shown with an icon and text (not colour alone), full keyboard support.
- Prompts and explanations use a read-only Tiptap renderer, shared from `common/shadcn`.

## Saving a quiz

Creating a quiz, and every later save, writes the whole quiz as one document. `quizVersion` is how two editors, or a stale tab, are kept from overwriting each other.

```d2 title="What happens when an instructor saves a quiz: access and archive checks, the version check, then one conditional write"
direction: down

start: "contentItem.updateQuiz\n(sends the quizVersion\nthe editor loaded)" {shape: oval}
access: "Instructor of this\ncourse, and the item\nis a quiz?" {shape: diamond}
archived: "Quiz, its lesson, module\nor course archived?" {shape: diamond}
stale: "Stored quizVersion\n= the one sent?" {shape: diamond}
write: "One transaction: course, module and lesson\nstill exist and aren't archived, quiz isn't\narchived and is still at that quizVersion.\nWrites the new content, quizVersion + 1\nand the recomputed questionsHash"
landed: "Did a condition fail?" {shape: diamond}

forbidden: "FORBIDDEN or BAD_REQUEST"
frozen: "PRECONDITION_FAILED:\nrestore it first"
conflict: "CONFLICT: the quiz changed since it\nwas loaded; reload and retry.\nNothing written"
done: "Saved as quizVersion + 1" {shape: oval}

start -> access
access -> forbidden: no
access -> archived: yes
archived -> frozen: yes
archived -> stale: no
stale -> conflict: no
stale -> write: yes
write -> landed
landed -> conflict: "yes, and nothing is archived"
landed -> frozen: "yes, and something was archived"
landed -> done: no
```

- Of two saves made from the same version, exactly one lands; the other gets `CONFLICT`. The check is repeated inside the write's transaction, so it holds when the saves are simultaneous, not only when one follows the other.
- A save that succeeds returns the new `quizVersion`, which the editor uses for its next save.
- `questionsHash` is recomputed from `questions` only, so a save that changes just the answer key, explanations or settings keeps the same hash.
- Creating a quiz starts it at `quizVersion` 1. Like other new content, it starts `visible` in a draft course and `hidden` otherwise, and it can't be created or edited under an archived module or lesson, or in an archived course (see <Link path="design/live-course-editing">Live course editing</Link>).

## Instructor experience

- A **Quiz** button sits with the **Video**, **Text** and **File** buttons in the lesson's content row. It opens the builder for a new quiz, which is created on its first save; later saves update it.
- The builder opens in a large dialog, for a new quiz and for a quiz's **Edit** button, like the Text and Video dialogs. Closing it with unsaved changes asks first:
  - Settings: title, description, pass mark, attempts allowed, shuffle options, when to reveal answers.
  - A card per question: Tiptap prompt (the editor is mounted only for the expanded card), Single/Multiple toggle, option rows with a correct marker (radio for single, checkbox for multiple), add/remove/reorder options, optional explanation.
  - Drag to reorder questions.
  - A contents panel beside the questions lists them by number with the start of each prompt, marking any that need fixing; clicking one opens it and scrolls to it.
  - **Preview as student**, using the real student component (`QuizCard`) on the quiz as it stands in the builder, saved or not. It's graded in the browser with the same rules as core-api, nothing is sent or saved, and the correct answers and explanations are always shown. Its attempts count only while it's open.
  - The whole quiz saves as one document: `contentItem.updateQuiz` replaces questions, key and settings together, against the `quizVersion` the builder loaded. On `CONFLICT` the builder offers to reload the latest version.
  - Read-only, with the reason, while the quiz or anything above it is archived.
- Validation, in the form and in zod (the API enforces all of it, whatever the form does):
  - 1 to 50 questions, each with 2 to 10 options. Option text is 1 to 500 characters.
  - Single choice: exactly 1 correct. Multiple choice: at least 1 correct. Every correct id is one of the question's options.
  - Every question has an answer key entry, and the key has no entries for other questions. Question ids are unique, and option ids are unique within a question.
  - Prompts and explanations are Tiptap documents that conform to the editor's schema (the same `StarterKit` nodes and marks), stored as JSON strings.
  - Pass mark is a whole number from 0 to 100. Attempts allowed is a whole number from 1, or unlimited.
  - Questions and answer key together are at most 300 KB, well under DynamoDB's 400 KB item limit.
  - Switching Multiple → Single with more than one correct asks which to keep.
- Editing a quiz that has attempts warns "N students have attempted this quiz".

Quiz statistics for instructors (score spread, per-question results) are built from the attempts by the `analytics-update` stream feature; see <Link path="design/course-analytics">Course analytics</Link>.

## Questions in videos

An instructor can put up to 20 questions on a video item, each at a moment in the video or at the end. They are low-stakes: no pass mark, no attempt limit, no stored score, and they never block progress. How the player asks them is in <Link path="design/video-player">Video player and captions</Link>.

- **Where they are stored:** on the video's own `contentItem`, in the `questions`, `answerKey` and `quizVersion` attributes a quiz uses. Each question is a quiz question plus `atSeconds` (whole seconds, or `null` for an end question) and a server-set `contentHash`. A video has no `settings` or `questionsHash`.
- **The versioned save:** `contentItem.updateVideoQuestions` replaces the whole set against the `quizVersion` the editor loaded, as `updateQuiz` does. Version 0 means never saved. Of two saves from the same version exactly one lands and the other gets `CONFLICT`. It is separate from `contentItem.updateVideo`, so questions can change without touching the media. Authoring is limited to the course's instructors, and refused under an archived video, lesson, module or course.
- **The per-question hash:** the `contentHash` covers one question's id, kind, prompt and options, not its moment or key. It plays the part `questionsHash` plays for a quiz, per question, so editing one question never disturbs a learner answering another, and moving a question changes nothing.
- **The answer sheet:** a learner's answers to one video are one `videoAnswerSheet` record (pk `userId`, sk `courseId / contentItemId`) holding, for each question answered, the options chosen, whether that was correct against the key at the time, and when. `answerCount` conditions every write, so two tabs can't both land. The sheet only ever gains entries.
- **First answer only:** the first answer to a question is recorded and never changed, replaced or regraded. Submitting again returns the recorded answer. The key and explanation reach the learner only once their answer is on record. **Try again** is practice, graded in the browser against the key already shown, and records nothing. A skip records nothing.
- **Low stakes:** an answer creates no `itemCompletion` and changes no progress, quiz result or certificate. It does count the learner as having used the video (see <Link path="design/live-course-editing">Live course editing</Link>) and as active that day.

### Video question edited mid-answer

With each answer the client sends the `contentHash` of the question it showed.

| What the instructor changed | Result of submitting |
|---|---|
| Only the correct options or the explanation (hash matches) | Accepted and graded against the **current** key. The learner notices nothing |
| The prompt, kind, or an option's wording, count or order (hash differs) | `CONFLICT` and nothing is recorded. The learner is told the question was updated and is shown the updated question |
| The question's moment | Accepted. Recorded answers are unaffected, and a learner who hasn't answered it is asked at the new moment |
| The question removed | Rejected as not found and nothing is recorded. The video resumes. Answers already recorded are kept, but the question is no longer asked or listed in results |
| Video, lesson, module or course archived or hidden | Rejected with "no longer available" |

Recorded answers are never regraded: a learner who answered wrongly stays "incorrect" after the key is corrected. A learner who reopens an answered question sees the current key and explanation beside their recorded result.

The editor warns an instructor who opens the questions of a video that learners have already used: their answers are kept and not regraded. The preview in the editor grades in the browser with the instructor's own key and records nothing.
