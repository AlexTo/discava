## The rule

**Lesson and course progress and completion are only ever written server-side, by one Lambda.** They never depend on a student reloading a page or on any other client-side trigger.

The only thing that starts with the student is whether an individual item is complete (reaching the end of a video, for example), because only the browser can observe that. Even then, core-api decides whether it counts, and everything above the item is derived on the server.

## Records

| Record | Keys | Written by | Holds |
|---|---|---|---|
| `itemCompletion` | pk `userId`, sk `courseId / lessonId / contentItemId` | core-api | `completedAt` |
| `progress` (per lesson) | pk `userId`, sk `courseId / lessonId` | Progress recalculation Lambda only | `status`, `completedAt` |
| `enrolment` | pk `courseId`, sk `userId` | Progress recalculation Lambda only (for these fields) | `progressPercent`, `status`, `completedAt` |

core-api writes `itemCompletion` records and quiz attempts. It never writes `progress` or the enrolment's progress fields.

## When an item is complete

| Item type | Complete when |
|---|---|
| Text | Scrolled past, or marked done |
| Video | Watched to near the end |
| Quiz | Passed, or all attempts used |

### Recording a completion

- **Text and video:** the browser decides when the item is done and calls core-api's `contentItem.complete`; core-api decides whether it counts. One transaction checks that the course is published, that the item, its lesson and its module are visible and not archived, and that the student is enrolled (not `dropped`). It then creates the `itemCompletion` only if there isn't one.
  - The completion is the student's first record of the item, so the same transaction increments the item's `studentActivityCount`. Each student is counted once (see <Link path="design/live-course-editing">Live course editing</Link>).
  - Completing again returns the existing completion. An archived course is read-only, so nothing in it can be completed.
- **Quiz:** completes itself. The attempt that passes, or that uses the last attempt, records the completion in the same transaction as the attempt (see <Link path="design/quizzes">Quizzes</Link>). It doesn't count the student again: their first attempt did.
  - `contentItem.complete` also accepts a quiz, but only once it's passed or no attempts remain. That covers an attempt limit lowered below what a student has already used, where no further submission is possible.
- **Reading completions:** `course.myCompletions` returns a student's completions in a course, including ones for items since hidden or archived. Which of them still count is decided from the current curriculum.
- **Reading progress:** `course.myProgress` returns a student's lesson progress records in a course, as progress recalculation last wrote them; a lesson without one hasn't been started. The course-level rollup comes with the enrolment (`course.myEnrolment`).

## Lesson and course completion

- A lesson is `completed` when every **effectively visible** item in it has an `itemCompletion`.
- `progressPercent` is the share of the course's effectively visible items the student has completed. It is always **recomputed** from the current curriculum, never incremented, so adding, removing or hiding content can't leave it wrong.
- At 100% the enrolment gets `status: 'completed'` and `completedAt`.
- **Completion is permanent**, for both lessons and courses. Adding content to something a student has completed never makes it incomplete. `progressPercent` can drop below 100 afterwards, but the student sees **Completed ✓ · 2 new items**, and the new items get a **New** badge.

The student's course page may compute progress on read for immediate display. That is display only and never writes.

## Progress recalculation Lambda

A Lambda in `packages/events` is the single writer of lesson `progress` and of the enrolment's `progressPercent`, `status` and `completedAt`.

### Trigger

DynamoDB Streams on the core table (new and old images), with event-source filters on the entity name ElectroDB stores in each record (`__edb_e__`), so the Lambda only runs for:

| Stream event | Recalculates |
|---|---|
| `itemCompletion` inserted | That one student, in that course |
| Module, lesson or content item: `visibility` or `archivedAt` changed, or record removed | Every enrolled student in the course who hasn't dropped out |

A filter can't compare a record's old and new images, so every change to a module, lesson or content item reaches the Lambda. The Lambda then ignores the ones that leave `visibility` and `archivedAt` as they were: a new title, an order or a `studentActivityCount`. The Lambda's own writes, to `progress` and `enrolment`, match no filter, so it never triggers itself.

### What it does

For each affected (student, course):

1. Load the course curriculum once (the `curriculum` collection, every page) and keep the effectively visible items with `filterEffectivelyVisible` from `@discava/core-table`, the same rule core-api's course views use.
2. Read the student's `itemCompletion` records and lesson `progress` for the course (pk `userId`, sk prefix `courseId`). A student who isn't enrolled, or has dropped out, is left alone.
3. Write each lesson's `progress`, but only where it changed:
   - A lesson is `completed` when all its effectively visible items are, `in_progress` when some are, and `not_started` otherwise.
   - A lesson with no effectively visible items has no progress.
   - No record means not started, so an untouched lesson isn't written.
   - `completed` is only ever set, never cleared: the write is conditioned on the record not already being `completed`.
4. Write the enrolment's `progressPercent` (rounded down, so it's 100 only when everything is done) if it changed. At 100%, set `status: 'completed'` and `completedAt`, conditioned on the enrolment still being `active`. A course with nothing visible is never completed.

Students are recalculated a few at a time, and each course's curriculum is loaded once per batch.

### Failures

A batch that fails is retried. A batch still failing after its retries is split in half until the failing records are isolated, and those records' stream positions go to a dead-letter queue instead of blocking the stream. Since every run recomputes from scratch, the next change for the same students also repairs anything a failed batch missed.

Enrolments share the course's partition key, so listing the students to recalculate is one query. A curriculum change costs one query per enrolled student.

### Idempotency

Every run recomputes from scratch, so a duplicate stream record or a burst of instructor edits just produces the same result again. The event source waits up to five seconds to gather a batch, and records in a batch are grouped so each student in each course is recalculated once per batch, however many records name them. Two runs for the same student at the same moment (a completion and a curriculum change land on different stream shards) both recompute from what they read. Neither can undo the other's completion, because completing writes are conditioned on not being completed already.

### Consequences

- Removing the last lesson a student hadn't finished marks them `completed` even if they never come back.
- Course lists and instructor reports are never stale.
- Stored values lag the triggering write by the stream delay, typically under a second to a few seconds.

See <Link path="design/live-course-editing">Live course editing</Link> for which instructor actions trigger a recalculation.
