## The rule

**Lesson and course progress and completion are only ever written server-side, by one Lambda.** They never depend on a student reloading a page or on any other client-side trigger.

The only thing that starts with the student is whether an individual item is complete (reaching the end of a video, for example), because only the browser can observe that. Even then, core-api decides whether it counts, and everything above the item is derived on the server.

## Records

| Record | Keys | Written by | Holds |
|---|---|---|---|
| `itemCompletion` | pk `userId`, sk `courseId / lessonId / contentItemId` | core-api | `completedAt` |
| `progress` (per lesson) | pk `userId`, sk `courseId / lessonId` | Progress recalculation Lambda only | `status`, `completedAt` |
| `enrolment` | pk `courseId`, sk `userId` | Progress recalculation Lambda only (for these fields) | `progressPercent`, `status`, `completedAt` |

core-api writes `itemCompletion` records and quiz attempts. It never writes `progress` or the enrolment's progress fields.

## When an item is complete

| Item type | Complete when |
|---|---|
| Text | The student presses **Mark as done** |
| Video | The student presses **Mark as done** |
| File | The student presses **Mark as done** |
| Quiz | Passed, or all attempts used |
| Upload assignment | The student submits a file |

A quiz that completes by running out of attempts is complete for progress, but it doesn't count as passed for a certificate: where the course requires quizzes to be passed, the student has a completed course and no certificate until they pass.

Text, video and file items never complete on their own: there is no scroll, watch-time or download tracking. The student decides when they're done with an item, as on most learning platforms.

### Recording a completion

- **Text, video and file:** **Mark as done** in the lesson player calls core-api's `contentItem.complete`; core-api decides whether it counts. One transaction checks that the course is published, that the item, its lesson and its module are visible and not archived, and that the student is enrolled (not `dropped`). It then creates the `itemCompletion` only if there isn't one.
  - The completion is the student's first record of the item, so the same transaction increments the item's `studentActivityCount`. Each student is counted once (see <Link path="design/live-course-editing">Live course editing</Link>).
  - Completing again returns the existing completion. An archived course is read-only, so nothing in it can be completed.
- **Quiz:** completes itself. The attempt that passes, or that uses the last attempt, records the completion in the same transaction as the attempt (see <Link path="design/quizzes">Quizzes</Link>). It doesn't count the student again: their first attempt did.
  - `contentItem.complete` also accepts a quiz, but only once it's passed or no attempts remain. That covers an attempt limit lowered below what a student has already used, where no further submission is possible.
- **Upload assignment:** completes itself. The student's first submission records the completion in the same transaction as the `assignmentSubmission`, and counts them once in `studentActivityCount`. Resubmitting replaces the file and bumps the submission's `version`; it doesn't count them again. `contentItem.complete` returns an existing completion for an assignment but never creates one: without a submission it fails with "Submit your work to complete it".
- **Video questions:** answering a question on a video isn't a completion. It creates no `itemCompletion` and changes no lesson or course progress, however many questions are answered, missed or skipped; the video is still completed only by **Mark as done**. The answer is recorded in its own `videoAnswerSheet` (see <Link path="design/quizzes">Quizzes</Link>). It does count as the student's first record of the video for `studentActivityCount` and sets `lastActivityAt`, and **Mark as done** doesn't count the student a second time.
- **Reading completions:** `course.myItemCompletions` returns a student's completions in a course, including ones for items since hidden or archived. Which of them still count is decided from the current curriculum.
- **Reading progress:** `course.myLessonProgress` returns a student's lesson progress records in a course, as progress recalculation last wrote them; a lesson without one hasn't been started. The course-level rollup comes with the enrolment (`course.myEnrolment`).
- **Last activity:** completing an item, or submitting a quiz attempt, sets the enrolment's `lastActivityAt` in the same transaction. It orders the student's courses, most recently active first, so the signed-in home can offer to continue where they left off. Progress recalculation doesn't touch it: an instructor's change isn't the student's activity.
- **Across courses:** `course.myEnrolments` lists a student's enrolments that aren't dropped, most recently active first, each with its progress, the next lesson (the first effectively visible lesson whose progress isn't `completed`) and how many items are new. It powers the signed-in home and My Learning.

## Lesson and course completion

- A lesson is `completed` when every **effectively visible** item in it has an `itemCompletion`.
- `progressPercent` is the share of the course's effectively visible items the student has completed. It is always **recomputed** from the current curriculum, never incremented, so adding, removing or hiding content can't leave it wrong.
- At 100% the enrolment gets `status: 'completed'` and `completedAt`.
- **Completion is permanent**, for both lessons and courses. Adding content to something a student has completed never makes it incomplete. `progressPercent` can drop below 100 afterwards, but the student sees **Completed ✓ · 2 new items**, and the new items get a **New** badge.

The student's course page may compute progress on read for immediate display. That is display only and never writes.

## Progress recalculation Lambda

A Lambda in `packages/events` is the single writer of lesson `progress` and of the enrolment's `progressPercent`, `status` and `completedAt`.

### Trigger

The core table's stream (new and old images), through the <Link path="design/stream-event-router">stream event router</Link>: the `progress-recalculation` feature's filters (`PROGRESS_STREAM_FILTERS`) match on the entity name ElectroDB stores in each record (`__edb_e__`), so the Lambda only runs for:

| Stream event | Recalculates |
|---|---|
| `itemCompletion` inserted | That one student, in that course |
| Module, lesson or content item: `visibility` or `archivedAt` changed, or record removed | Every enrolled student in the course who hasn't dropped out |
| `quizSummary` inserted or modified | That one student, when `passedAt` appears or the best score of an already passed quiz rises; every other change is ignored |
| `assignmentSubmission` modified | That one student, only when `status`, `points` or `returnedAt` differs between the old and new image; a resubmission changes none of them |
| `course` modified | Every enrolled student who hasn't dropped out, only when `certificateCriteria.version` or `certificatesEnabled` differs between the old and new image; any other course edit is ignored |
| Quiz content item: `settings.passMarkPercent` changed | Every enrolled student who hasn't dropped out. A pass counts only while the best score reaches the current mark, so lowering a mark can make a student eligible, and a mark crossing 0 changes who is assessed |

A filter can't compare a record's old and new images, so every change to a module, lesson, content item, quiz summary or course reaches the Lambda. The Lambda then ignores the ones that leave `visibility` and `archivedAt` as they were (a quiz's pass mark is the exception, see above): a new title, an order or a `studentActivityCount`. The Lambda's own writes, to `progress` and `enrolment`, match no filter, so it never triggers itself.

### What it does

For each affected (student, course):

1. Load the course curriculum once (the `curriculum` collection, every page) and keep the effectively visible items with `filterEffectivelyVisible` from `@discava/core-table`, the same rule core-api's course views use.
2. Read the student's `itemCompletion` records and lesson `progress` for the course (pk `userId`, sk prefix `courseId`). A student who isn't enrolled, or has dropped out, is left alone.
3. Write each lesson's `progress`, but only where it changed:
   - A lesson is `completed` when all its effectively visible items are, `in_progress` when some are, and `not_started` otherwise.
   - A lesson with no effectively visible items has no progress.
   - No record means not started, so an untouched lesson isn't written.
   - `completed` is only ever set, never cleared: the write is conditioned on the record not already being `completed`.
4. Write the enrolment's `progressPercent` (rounded down, so it's 100 only when everything is done) if it changed. At 100%, set `status: 'completed'` and `completedAt`, conditioned on the enrolment still being `active`. A course with nothing visible is never completed.
5. If the enrolment is `completed`, the student isn't dropped and has no certificate yet, check the course's certificate criteria against the student's quiz summaries (`evaluateCertificateCriteria`, see <Link path="design/certificates">Certificates</Link>) and call `issueCertificate` only when they are met.

Students are recalculated a few at a time, and each course's curriculum is loaded once per batch.

### Failures

A batch that fails returns to the feature's queue and is retried. A message still failing after `maxReceiveCount` receives moves to the feature's failure queue instead of blocking later changes (see <Link path="design/stream-event-router">Stream event router</Link>). Since every run recomputes from scratch, the next change for the same students also repairs anything a failed batch missed.

Enrolments share the course's partition key, so listing the students to recalculate is one query. A curriculum change costs one query per enrolled student.

### Idempotency

Every run recomputes from scratch, so a duplicate stream record or a burst of instructor edits just produces the same result again. The feature's queue waits up to five seconds to gather a batch, and records in a batch are grouped so each student in each course is recalculated once per batch, however many records name them. Two runs for the same student at the same moment (a completion and a curriculum change land on different stream shards) both recompute from what they read. Neither can undo the other's completion, because completing writes are conditioned on not being completed already.

### Consequences

- Removing the last lesson a student hadn't finished marks them `completed` even if they never come back.
- Course lists and instructor reports are never stale.
- Stored values lag the triggering write by the stream delay, typically under a second to a few seconds.

See <Link path="design/live-course-editing">Live course editing</Link> for which instructor actions trigger a recalculation.
