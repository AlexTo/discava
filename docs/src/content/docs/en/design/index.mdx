## Shared concepts

**Curriculum hierarchy.** A course contains modules, a module contains lessons, and a lesson contains an ordered list of content items (video, text, file, quiz, assignment). All four live in one DynamoDB partition (`COURSE#<courseId>`) through ElectroDB's `curriculum` collection, so a whole course is one query. That query reads every page, since a course's curriculum can exceed DynamoDB's 1 MB per page.

**Effective visibility.** A module, lesson or content item is shown to students only if it **and every ancestor** is `visible` and not archived. Student reads, student writes and progress calculations all use effective visibility, never a record's own `visibility` alone. The rule is implemented once, as `filterEffectivelyVisible` in `@discava/core-table`.

**Enrolment.** A student reads a course's content, and writes anything in it, only while enrolled: they have an `enrolment` record (pk `courseId`, sk `userId`) whose `status` isn't `dropped`. Students enrol themselves with core-api's `course.enrol`, and only in a **published**, **free** course: the course's status and price are checked in the same transaction as the enrolment write, so a course archived or priced mid-request can't take a new enrolment. A priced course is entered only by a paid order (see <Link path="design/payments">Payments</Link>). Enrolling again returns the existing enrolment. A draft or archived course answers `NOT_FOUND`, as the anonymous `course.publicView` does, so a draft's existence isn't leaked. An enrolled student can still read a course after it's archived, but it is read-only for them too. `course.myEnrolment` returns the caller's enrolment, or none.

**Student data is keyed by user.** `progress`, `itemCompletion`, `quizAttempt` and `quizSummary` use `userId` as their partition key, so "a student's progress in a course" is one query. The flip side is that "which students touched this item?" can't be answered without a scan, which is why content items carry a `studentActivityCount`.
