A deployed installation is called a **stage**. A stage is a group of CloudFormation stacks, all named `<stage>-<Stack>`, such as `discava-production-Data`. Several stages can live in one AWS account without touching each other.

## The stacks

The application is split into ten stacks. One stack would exceed CloudFormation's limit of 500 resources, and separating stateful resources from code keeps routine deploys away from the data.

`PortalConfig` depends on every other stack. Only its arrows to the three APIs are drawn.

They deploy in this order:

```
Websites → Data → Payments → MediaPipeline → CoreApi → StreamRouter → Payouts → InstructorApi → AdminApi → PortalConfig
```

| Stack | Contains | Why it is separate |
| --- | --- | --- |
| **Websites** | The three portals: an S3 bucket and CloudFront distribution each. The student portal also has the page renderer function | Depends on nothing. Others need the portals' addresses for CORS and sign-in redirects |
| **Data** | Cognito user pool and its triggers, the core table, the lesson media and public media buckets with their CloudFront distributions, the upload bucket, the search collection and the function that creates its indices, the unsubscribe-link and Stripe secrets | Everything stateful. Changes rarely, and every other backend stack depends on it |
| **Payments** | The Stripe webhook API: its API Gateway and function | Called by Stripe, not by signed-in users, so its firewall, request limits and domain are set apart from the other APIs |
| **MediaPipeline** | MediaConvert pipeline, the functions reacting to finished transcodes and transcriptions, cleanup schedules, failure queues | Video processing, used by both core-api and instructor-api |
| **CoreApi** | core-api's API Gateway and functions, the search re-index function, the email unsubscribe route | The API every user calls |
| **StreamRouter** | The table stream's router function, one queue and failure queue per feature, the feature handlers, the certificate reminder function and the transcript re-index function | Background reactions to data changes, kept out of CoreApi's resource budget |
| **Payouts** | The daily payout run and its schedule | Kept apart so no stack nears the resource limit. It reads the table and the Stripe key only |
| **InstructorApi** | instructor-api's API Gateway and functions, with their media and transcoding permissions | The instructors' API |
| **AdminApi** | admin-api's API Gateway and functions, including the one that saves the Stripe key | The admins' API |
| **PortalConfig** | Each portal's `runtime-config.json` | Reads values from every other stack, so it deploys last |

When a portal or media distribution has WAF on, its web ACL is an extra small stack in `us-east-1`, where CloudFront requires it.

## What is in each layer

### Edge: CloudFront and API Gateway

| Entry point | Service | Origin |
| --- | --- | --- |
| Each portal | CloudFront | A private S3 bucket of static files |
| Public pages on the student portal (`/learn/*`, `/instructors/*`, `/certificates/*`, `/sitemap.xml`, `/robots.txt`) | The student portal's CloudFront distribution | The page renderer function, through a function URL only CloudFront may call |
| Lesson media | CloudFront, signed requests only | A private S3 bucket |
| Public media | CloudFront | A private S3 bucket |
| Each API | API Gateway (REST, regional) | Lambda |
| Stripe webhook | API Gateway (REST, regional) | Lambda |

No S3 bucket is public. CloudFront reaches each through Origin Access Control.

### Compute: Lambda

All code runs in Lambda on Node.js 24.

- **API functions.** Each API serves most procedures from one shared function. A procedure that needs more than the baseline access (the table, plus reading search in core-api) runs in a dedicated function, which keeps powerful permissions off the function handling every other request:

  | API | Dedicated functions |
  | --- | --- |
  | core-api | Signing media requests, assignment uploads, starting a checkout or refund (reads the Stripe key) |
  | instructor-api | Signing media requests, writing lesson media and submitting transcodes, course images and profile photos, payout accounts (reads the Stripe key) |
  | admin-api | Saving the Stripe secrets (the only writer), brand images |

- **Event functions.** One per job: the two Cognito triggers, the stream router and its feature handlers, the media pipeline's completion, recovery and cleanup handlers, the certificate reminder, the Stripe webhook, the daily payout run, and the email unsubscribe link.
- **The page renderer.** core-api's second handler, deployed with the student portal. It only reads the table.
- **Operations functions.** Three have no trigger and run when a deploy or an operator invokes them: the one that creates or updates the search indices on each deploy, and the two that rebuild the courses and transcripts indices.

### Data

| Resource | Service | Notes |
| --- | --- | --- |
| Core table | DynamoDB, on-demand with a throughput ceiling | A change stream feeds the stream router |
| Search | OpenSearch Serverless | Two indices: courses and transcripts. Can scale to zero on a development stage |
| Media | S3 | Three buckets: lesson media, uploads, public media |
| Users | Cognito user pool | Groups: `student`, `instructor`, `admin` |
| Configuration | Lambda environment variables | Resource names and addresses, set at deploy time and read by functions from their environment. The page renderer reads one Systems Manager parameter |
| Secrets | Secrets Manager | The key that signs lesson media requests, the key that signs unsubscribe links, and the Stripe secret key and webhook signing secret an administrator saves |

### Media processing

| Service | Used for |
| --- | --- |
| MediaConvert | Transcoding an uploaded video into HLS renditions |
| Transcribe | Automatic captions for each video |
| Translate | Translating captions into a course's other caption languages |

### Messaging and scheduling

| Service | Used for |
| --- | --- |
| DynamoDB Streams | Every change to the core table |
| SQS | One queue and one failure queue per stream feature, plus failure queues for the media pipeline and the certificate reminder |
| EventBridge | Rules that fire when a MediaConvert or Transcribe job finishes, a schedule that finds stuck videos, and the daily schedule of the payout run |
| EventBridge Scheduler | One-time schedules: delayed cleanups of retired media, and certificate reminders |
| SES | Notification emails |

## Runtime configuration

Deployed code never has resource names hardcoded.

- **Backend functions** read table names, bucket names and endpoints from their own **environment variables** (`DISCAVA_*`), set when the stack is deployed. Nothing is fetched at runtime, and a function is given only the settings its code reads. The page renderer is the exception: it reads the table's name and the public media address from one Systems Manager parameter, because it deploys in `Websites`, before the `Data` stack that owns them.
- **Portals** fetch `runtime-config.json` from their own origin when they load. It carries the API addresses, the Cognito ids and the other portals' addresses.

The portals' file is written by the `PortalConfig` stack from values the other stacks export, which is why it deploys last.

## Stages sharing an account

Three mechanisms keep stages apart:

- **Names.** Every stack and generated resource name starts with the stage name, and IAM permissions are scoped to that prefix.
- **Assets.** Each stage uploads its build output under its own prefix in the shared CDK bucket, so one stage can't overwrite what another is about to deploy.
- **Permissions boundary.** Every IAM role a stage creates carries that stage's boundary policy, capping what the stage's own code can be granted.

## How it is defined in code

| What | Where |
| --- | --- |
| Which stages exist and their settings | `packages/common/infra-config/src/stages.config.ts` |
| The CDK app: one `ApplicationStage` per configured stage | `packages/infra/src/main.ts` |
| How stacks are composed and wired | `packages/infra/src/stages/application-stage.ts` and `packages/infra/src/stacks/` |
| The building blocks (an API, a bucket, a website) | `packages/common/constructs` |

A **construct** owns one component's resources and exposes helpers such as `grantRead`. A **stack** wires constructs together and turns stage settings into construct options. See <Link path="deploy/configuration">Stage configuration</Link> for the settings.
