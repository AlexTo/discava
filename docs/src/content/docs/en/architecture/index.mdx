Discava is a set of serverless components on AWS. Nothing runs when nobody is using it: there are no servers, containers or clusters to keep alive.

## The system at a glance

```d2 title="Components and how they connect"

  student: "Student portal"
  instructor: "Instructor portal"

  core: "core-api"
  instr: "instructor-api"
  adm: "admin-api"

data: "Data" {
  table: "Core table\n(DynamoDB)"
  search: "Search\n(OpenSearch Serverless)"
  lesson: "Lesson media\n(S3 + CloudFront)"

async: "Background work" {
  router: "Stream router"
  handlers: "Feature handlers"
  media: "Media pipeline\n(MediaConvert, Transcribe)"
  router -> handlers: "one queue each"
}

email: "SES"
```

## The components

### Three portals

| Portal | For | Talks to |
| --- | --- | --- |
| **Student portal** | Browsing the catalogue, buying and taking courses, quizzes, discussions | core-api |
| **Instructor portal** | Building and pricing courses, analytics, earnings, answering students | core-api, instructor-api |
| **Admin portal** | Categories, review moderation and the Stripe connection | core-api, admin-api |

Each is a React single-page application: static files in a private S3 bucket, served by CloudFront. A portal learns where its APIs and sign-in page are from a `runtime-config.json` file deployed beside it, so the same build works on every stage.

### One identity provider

A Cognito user pool holds every user. Three groups, `student`, `instructor` and `admin`, decide what a user may do. Sign-in happens on Cognito's hosted page, and the portal receives tokens it sends with each API call.

### Three APIs

Each API is an API Gateway REST API in front of Lambda functions, speaking [tRPC](https://trpc.io/).

| API | Who may call it | Examples |
| --- | --- | --- |
| **core-api** | Any signed-in user, plus a few public procedures | Catalogue, enrolment, checkout, lesson content, quizzes, discussions, search |
| **instructor-api** | Members of `instructor` | Creating, editing and pricing courses, uploading media, analytics, earnings and payouts |
| **admin-api** | Members of `admin` | Category taxonomy, review moderation, the Stripe connection |

Splitting by audience means each API has its own function, permissions, request limits and firewall. An instructor-only bug can't be reached with a student's token, and a flood of student traffic can't starve the instructor API.

### One table

All application data is in a single DynamoDB table, the **core table**: courses, modules, lessons, enrolments, progress, quiz attempts, discussions, reviews, notifications, orders and instructor earnings. Related records share a partition, so a whole course's curriculum is one query.

### Search

Published courses are copied into an OpenSearch Serverless collection, which answers the catalogue's search and filters. The table is the source of truth: the index is rebuilt from it and never written to directly by an API.

### Media

| Store | Holds | Access |
| --- | --- | --- |
| **Lesson media** | Lesson videos, captions and files | Private. Served by CloudFront only to requests carrying a signature the API issued to an enrolled student |
| **Upload bucket** | Files on their way in | Write-only by presigned URL, read by the processing job, short-lived |
| **Public media** | Course images on catalogue cards | Readable by anyone through CloudFront |

### Payments

Paid courses are bought on Stripe's hosted checkout page, with a Stripe account an administrator connects in the admin portal. Stripe confirms each payment to a small API of its own, the **Stripe webhook API**, which verifies the message's signature and enrols the student. It is separate from the three tRPC APIs because Stripe, not a signed-in user, calls it. <Link path="design/payments">Payments</Link> has the design.

### Background work

Three things happen outside a request:

- **Reacting to data changes.** The table's change stream has one reader, the **stream router**, which hands each change to the queue of every feature that wants it: progress recalculation, search indexing, analytics, notification delivery and recording instructor earnings.
- **Processing video.** An uploaded video is transcoded into adaptive streaming renditions by MediaConvert, then captioned by Transcribe.
- **Paying instructors.** A daily run sends each instructor the earnings that are due, as a Stripe transfer. See <Link path="design/instructor-payouts">Instructor payouts</Link>.

## Design principles

- **Serverless only.** Every component bills by use and scales to zero.
- **One way to do it.** One cloud, one deployment tool, one table. Fewer options to configure, document and test.
- **Secure by default.** Every protection is on unless a stage turns it off.
- **Runs locally.** Every AWS service has a local stand-in, so development needs no AWS account.
