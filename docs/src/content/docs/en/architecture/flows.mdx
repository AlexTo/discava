Seven flows explain most of the system.

## Signing in

```d2 title="Sign-in"
shape: sequence_diagram
browser: "Browser"
portal: "Portal (CloudFront)"
cognito: "Cognito"
trigger: "Pre token generation"
table: "Core table"

browser -> portal: "load app and runtime-config.json"
browser -> cognito: "redirect to sign-in page"
cognito -> trigger: "before issuing tokens"
trigger -> table: "write the user record"
cognito -> browser: "tokens, with the user's groups"
```

1. The portal loads and reads `runtime-config.json` to find Cognito.
2. The user signs in on Cognito's hosted page.
3. Before issuing tokens, Cognito calls a function that writes the user's record to the core table, so the application has a row for anyone holding a token. The write is best effort: if it fails or is slow, the user still signs in, and the next sign-in or token refresh tries again.
4. The browser receives tokens that include the user's groups.

When someone signs up themselves, a second trigger adds them to the `student` and `instructor` groups.

## Calling an API

```d2 title="An API call"
shape: sequence_diagram
browser: "Browser"
waf: "WAF"
gw: "API Gateway"
fn: "API function"
table: "Core table"

browser -> waf: "tRPC call with token"
waf -> gw: "allowed"
gw -> gw: "verify token with Cognito, throttle"
gw -> fn: "invoke"
fn -> fn: "check group, validate input"
fn -> table: "read or write"
fn -> browser: "result"
```

A request is checked three times before it touches data:

1. **WAF**, when the stage has it on, filters common attacks.
2. **API Gateway** verifies the token against the user pool and applies the request limits. A few public procedures, such as viewing a published course's landing page, skip the token check.
3. **The function** checks the caller's group (instructor-api requires `instructor`, admin-api requires `admin`), validates the input, and applies the rule for that procedure, such as "the caller is enrolled in this course".

## Serving a public page

Course landing pages, instructor profiles and certificate pages must be readable by crawlers and link previews, which don't run the portal's JavaScript.

```d2 title="A public page"
shape: sequence_diagram
visitor: "Crawler or browser"
cf: "Student portal (CloudFront)"
fn: "Page renderer"
table: "Core table"

visitor -> cf: "GET /learn/<courseId>"
cf -> fn: "on a cache miss"
fn -> table: "read the course"
fn -> cf: "HTML"
cf -> visitor: "HTML, cached for up to five minutes"
```

1. The student portal's CloudFront distribution sends `/learn/*`, `/instructors/*`, `/certificates/*`, `/sitemap.xml` and `/robots.txt` to the page renderer. Every other path is the static site.
2. The renderer reads the table and fills the portal's own `index.html` with the page's content and metadata. It has read-only access, and only CloudFront can call it.
3. CloudFront caches the answer by path alone, so it never depends on who asks.

## A video's journey

```d2 title="From upload to playback"
direction: right
instructor: "Instructor"
api: "instructor-api"
upload: "Upload bucket"
mc: "MediaConvert"
lesson: "Lesson media bucket"
done: "transcode-complete"
tr: "Transcribe"
cap: "transcribe-complete"
table: "Core table"
cf: "CloudFront"
student: "Student"

instructor -> api: "1. ask to upload"
instructor -> upload: "2. PUT file (presigned URL)"
api -> mc: "3. submit job"
mc -> lesson: "4. HLS renditions"
mc -> done: "5. job finished (EventBridge)"
done -> table: "mark ready"
done -> tr: "6. start captions"
tr -> cap: "7. finished (EventBridge)"
cap -> lesson: "caption track"
student -> cf: "8. play (signed)"
cf -> lesson
```

**Uploading.** The browser uploads straight to S3 with a presigned URL from instructor-api, so large files never pass through a Lambda function.

**Transcoding.** MediaConvert turns the upload into HLS renditions at several qualities, so the player adapts to the viewer's connection. When the job finishes, an EventBridge rule invokes a function that marks the video ready and starts a Transcribe job for captions.

**Captions.** When Transcribe finishes, a second function saves the caption track. If the course has other caption languages, the caption translation feature (see [Reacting to a change](#reacting-to-a-change)) translates the track with Amazon Translate. The transcript indexing feature adds the caption text to search.

**Recovering.** A function runs every 30 minutes to find videos stuck in processing. Each completion handler has a failure queue, and retired files are removed by scheduled cleanups.

**Playing.** Lesson media is private. When an enrolled student opens a lesson, core-api checks the enrolment and issues a short-lived CloudFront signature. CloudFront serves the video only to requests carrying it. Two things are open to anyone, signed in or not: a course's preview video, and lessons the instructor marked as free previews. The signing key is held by one dedicated function in each API that signs, not by the API's shared function.

## Reacting to a change

Some results depend on many records: a student's course progress, a course's search entry, an instructor's analytics and earnings. They aren't computed inside the request that changes the data. They are recomputed afterwards from the table's change stream.

```d2 title="One stream reader, one queue per feature"
direction: right
api: "Any API write"
table: "Core table"
stream: "Change stream"
router: "Stream router"
q1: "progress queue"
q2: "search queue"
q3: "analytics queue"
q4: "notification queue"
h1: "Progress recalculation"
h2: "Search indexing"
h3: "Analytics update"
h4: "Notification delivery"
os: "OpenSearch"
ses: "SES"

api -> table
table -> stream
stream -> router
router -> q1
router -> q2
router -> q3
router -> q4
q1 -> h1
q2 -> h2
q3 -> h3
q4 -> h4
h1 -> table
h3 -> table
h2 -> os
h4 -> ses
```

The diagram shows four of the eight features:

| Feature | Reacts to a change by |
| --- | --- |
| Progress recalculation | Updating a student's course progress, and issuing the certificate when the course is complete |
| Search indexing | Updating the course's entry in the courses index |
| Transcript indexing | Updating a video's caption text in the transcripts index |
| Analytics update | Updating the course's analytics figures |
| Notification delivery | Fanning a broadcast out to its students and sending emails through SES |
| Earnings recording | Recording each instructor's share of a paid order |
| Caption translation | Translating a video's captions into the course's other languages |
| Brand publishing | Writing the platform's brand file to public media, where the portals fetch it |

- The **stream router** is the stream's only reader. It copies each change to the queue of every feature whose filter matches.
- Each **feature** has its own queue, so a slow or failing feature never delays another.
- A message that keeps failing moves to that feature's **failure queue**, which raises an alarm. An operator fixes the cause and redrives the queue.
- Handlers can receive a change twice or out of order, so each is written to give the same result either way.

The consequence for users: figures such as progress and analytics update a few seconds after the action that caused them.

<Link path="design/stream-event-router">Stream event router</Link> has the full design, and <Link path="design/search">Search</Link> and <Link path="design/progress-and-completion">Progress and completion</Link> cover two of its features.

## Buying a course

A paid course is bought on Stripe's page, and the student is enrolled by Stripe's confirmation, never by the browser coming back.

```d2 title="A purchase"
direction: right
student: "Student portal"
core: "core-api"
table: "Core table"
stripe: "Stripe"
hook: "Stripe webhook API"

student -> core: "1. Buy now"
core -> table: "2. pending order"
core -> stripe: "3. create checkout"
student -> stripe: "4. pay"
stripe -> hook: "5. signed confirmation"
hook -> table: "6. order paid + enrolment"
```

1. core-api writes a `pending` order, then asks Stripe for a checkout page and sends the student to it. The amount is the course's own price, less a coupon if the student entered one, and never a figure sent by the browser. A coupon is claimed before the order is written, so its redemption limit holds when several students check out at once.
2. The student pays on Stripe. Discava never sees a card number.
3. Stripe posts a signed confirmation to the webhook API. The handler verifies the signature, then marks the order paid and creates the enrolment in one transaction.
4. Back on the course page, the portal waits for the enrolment to appear, usually within seconds.

Stripe may deliver a confirmation more than once, so the handler changes nothing the second time. A payment that can't be delivered, such as for a course unpublished in the meantime, is refunded automatically.

The paid order then travels the change stream like any other write: the earnings feature records each instructor's share, and a daily run pays what is due. <Link path="design/payments">Payments</Link> and <Link path="design/instructor-payouts">Instructor payouts</Link> have the full design.

## Searching

Search reads from OpenSearch, which the stream keeps up to date.

- **The catalogue.** core-api's public search procedure sends the query and filters, and returns published courses ranked by relevance and rating. A second procedure suggests titles as the student types. A newly published course appears a few seconds after publishing.
- **Inside a course.** An enrolled student can search what was said in the course's videos. core-api decides which videos the student may watch from the table, and limits the query to them, so the index never decides access.
