## Who can do what

Access is decided in layers, and each layer assumes the one before it could fail.

| Layer | Enforces |
| --- | --- |
| **Cognito groups** | A user's role: `student`, `instructor` or `admin` |
| **Separate APIs** | Instructor and admin procedures are separate deployments. A student's token is rejected by instructor-api before any procedure runs |
| **Procedure rules** | The specific rule: this instructor owns this course, this student is enrolled in it |
| **Signed media** | A video or file is served only to a request signed for it. The signature is issued after an access check, such as enrolment |

A draft or archived course answers "not found" to anyone who shouldn't see it, so its existence isn't revealed.

## Protections per stage

Every protection is **on by default**. A stage's configuration can only turn things off, which `discava-development` does to stay cheap.

| Protection | What it does | Production | Development |
| --- | --- | --- | --- |
| **WAF** | Web application firewall on the portals, APIs, media and user pool | On | Off |
| **KMS encryption** | Customer-managed keys, with rotation, for the table, buckets, queues, logs and search | On | Off (AWS-managed encryption) |
| **MFA** | A second factor at sign-in | On | Off |
| **Deletion protection** | Refuses deleting the user pool and table | On | Off |
| **Retain on delete** | Keeps data if a stack is removed | On | Off |
| **Self sign-up** | Lets anyone create an account | On | Off |
| **Tracing** | Request tracing with X-Ray | On | Off |

Data is always encrypted at rest and in transit. The KMS setting decides whether the keys are yours to control and audit.

On a development stage with WAF off, the request limits, function concurrency and table throughput ceilings in the stage's configuration bound what a flood of requests can cost. With self sign-up off, an outsider can't get an account to reach the signed-in procedures.

## Least privilege inside the system

- Each Lambda function has its own role with only the permissions its job needs.
- Sensitive capabilities are isolated in dedicated functions. The key that signs lesson media requests is readable by one function in core-api and one in instructor-api, not by the function serving every other procedure.
- The Stripe key and webhook signing secret are in Secrets Manager. One admin-api function may write them. The checkout, webhook, payout-account and payout-run functions read only what they need, and no response, log line or audit record carries either.
- The Stripe webhook accepts a message only if its signature verifies against the stored signing secret. A payment is never trusted from the browser.
- No S3 bucket is public. The portals and media are reachable only through their CloudFront distributions.
- The page renderer serves public pages with read-only access to the table, and only the student portal's CloudFront distribution can invoke it.
- Each API answers cross-origin requests only from the portals that call it: all three for core-api, the instructor portal for instructor-api, the admin portal for admin-api. The local development addresses are also allowed.
- The search indices are written only by the indexing functions. The APIs can only read them.
- Functions get resource names from deploy-time environment variables, and credentials never appear in code or environment files.

## Checks before code is deployed

| Check | Where | Catches |
| --- | --- | --- |
| **Checkov** | Every build | Insecure infrastructure settings in the generated templates |
| **Trivy** | CI and before each deploy | Known vulnerabilities in dependencies, and committed secrets |
| **git-secrets** | Before each commit | Credentials about to be committed |
| **Table invariants** | End-to-end tests | Data left in a state that breaks a rule spanning several records |

## Keeping deployments in bounds

The deployment pipeline is itself an attack surface, so it is constrained:

- **No stored AWS credentials.** GitHub Actions signs in with a token issued for one run.
- **The deploy role trusts one environment** of one repository. Protecting that environment with required reviewers gates the deploy.
- **The deploy role can't create resources.** It can only ask CloudFormation to deploy stacks named for its stage.
- **The execution role is scoped** to the stage's resources by name.
- **A permissions boundary** caps every role a stage creates, so a deployed change can't grant itself more than the boundary allows.

## Reporting a vulnerability

Please don't open a public issue. Follow the security notification process in [CONTRIBUTING.md](https://github.com/AlexTo/discava/blob/main/CONTRIBUTING.md#security-issue-notifications).
