## Where configuration lives

Every stage is defined in one file: `packages/common/infra-config/src/stages.config.ts`. A stage lists settings per **component**:

| Component | What it is |
| --- | --- |
| `identity` | The Cognito user pool |
| `coreApi`, `instructorApi`, `adminApi` | The three APIs |
| `coreTable` | The DynamoDB table |
| `streamRouter` | The queues that carry table changes to their handlers |
| `studentPortal`, `instructorPortal`, `adminPortal` | The three websites |
| `lessonMedia`, `publicMedia` | The video and image buckets and their CloudFront distributions |
| `search` | The OpenSearch Serverless collection |
| `notifications` | The email sender |

**Every security setting defaults to on.** A stage only lists what it relaxes or sizes. `discava-development` turns most protections off to stay cheap, and `discava-production` states the hardened values outright.

Common settings:

| Setting | Meaning |
| --- | --- |
| `enableWaf` | Put a WAF web ACL in front of the component |
| `enableKmsEncryption`, `enableKeyRotation` | Encrypt with a customer-managed KMS key, and rotate it |
| `retainOnDelete`, `enableDeletionProtection` | Keep the data if the stack is deleted, and refuse accidental deletion |
| `throttleRateLimit`, `throttleBurstLimit` | API Gateway's per-method request limits |
| `reservedConcurrency` | The most requests an API's function runs at once |
| `maxReadRequestUnits`, `maxWriteRequestUnits` | The table's throughput ceiling |
| `min…CapacityInOcu`, `max…CapacityInOcu` | Search capacity. A minimum of 0 scales to zero when idle |
| `enableSelfSignUp`, `enableMfa` | Whether anyone can create an account, and whether MFA is required |

With WAF off, the throttles, concurrency and throughput limits are what bound the cost of a flood of requests. Raise them as real usage grows.

## Overriding without committing

Values that are specific to your account, such as domains and certificate ARNs, shouldn't be committed to a public fork. Any setting can instead be given as a variable named:

```
<STAGE>_INFRA_<COMPONENT>_<FIELD>
```

in upper snake case. For example, `coreApi.throttleRateLimit` on `discava-development` is `DISCAVA_DEVELOPMENT_INFRA_CORE_API_THROTTLE_RATE_LIMIT`.

Set it as a **variable on the stage's GitHub environment**. The Deploy workflow forwards every variable starting with the stage's prefix:

```sh
gh variable set DISCAVA_DEVELOPMENT_INFRA_CORE_API_THROTTLE_RATE_LIMIT \
  --env discava-development --body 5
```

The deploy role and region (`credentials`, `region`, `account`) can't be overridden this way.

## Custom domains

Each API, portal and media distribution can have its own domain. You need, for each:

- A **domain name** you control
- An **issued ACM certificate** covering it, in the right region
- A **DNS record** pointing at it, which you create after deploying

| Component | Variable for the domain | Certificate region |
| --- | --- | --- |
| Core API | `…_INFRA_CORE_API_DOMAIN_NAME` | The stage's region |
| Instructor API | `…_INFRA_INSTRUCTOR_API_DOMAIN_NAME` | The stage's region |
| Student portal | `…_INFRA_STUDENT_PORTAL_DOMAIN_NAMES` | `us-east-1` |
| Instructor portal | `…_INFRA_INSTRUCTOR_PORTAL_DOMAIN_NAMES` | `us-east-1` |
| Admin portal | `…_INFRA_ADMIN_PORTAL_DOMAIN_NAMES` | `us-east-1` |
| Lesson media | `…_INFRA_LESSON_MEDIA_DOMAIN_NAMES` | `us-east-1` |
| Public media | `…_INFRA_PUBLIC_MEDIA_DOMAIN_NAMES` | `us-east-1` |

Each also takes a matching `…_CERTIFICATE_ARN`. A domain is only applied when its certificate is set too. Portals and media accept several comma-separated domains; an API takes one.

**The easiest way to set these is to run the setup script again.** Give it a root domain and it suggests a subdomain for each component, finds a matching certificate in ACM, validates it and writes the variables:

```sh
./scripts/setup-stage.sh discava-development
```

Three rules to know:

- **Each API needs its own certificate naming exactly its domain.** Not a wildcard, and not one shared with the other API. Otherwise a browser can reuse one connection for both APIs and get errors from the wrong one.
- **Video playback needs a shared parent domain.** When lesson media has a custom domain, playback is authorised with cookies shared between the API and lesson media, so both must sit under one parent, given as `…_INFRA_LESSON_MEDIA_COOKIE_DOMAIN` (`example.com` for `instructor-api.example.com` and `lesson-media.example.com`).
- **DNS is yours to manage.** After the deploy, point each domain at its target: a CloudFront distribution for portals and media, the API Gateway custom domain for APIs. Until then the domains don't resolve, although the portals already use them.

Portal domains are picked up automatically as the APIs' allowed CORS origins and as Cognito's sign-in and sign-out addresses.

## Notification emails

Emails go out through SES. Verify a domain or address in SES, in the stage's region, then set:

| Variable | Example |
| --- | --- |
| `…_INFRA_NOTIFICATIONS_FROM_ADDRESS` | `notifications@example.com` |
| `…_INFRA_NOTIFICATIONS_SES_IDENTITY` | `example.com` |

With neither set, no email is sent and each one is recorded as skipped. In-app notifications work regardless. A new SES account is in the sandbox and only sends to verified addresses until AWS grants production access.

## Adding a stage

1. Add an entry to `stages.config.ts` next to the existing two, with the settings it relaxes.
2. Commit and push it.
3. Run `./scripts/setup-stage.sh <new-stage>` to create its roles and GitHub environment.
4. Run the Deploy workflow with the new stage's name.

Nothing else changes: the CDK app creates a stage for every entry in the file.

If you plan to deploy the new stage from your machine with environment overrides, also add its prefix to the `synth` target's `inputs` in `packages/infra/project.json`, so Nx's cache notices when an override changes.

## Going to production

`discava-production` is ready to deploy as it is. Before real users arrive:

- Run the setup script for it, and bootstrap CDK in `us-east-1` when asked (its WAF rules live there)
- <Link path="deploy/setup">Protect its GitHub environment</Link> with required reviewers
- Give it custom domains and a verified SES identity
- Review the request limits in `stages.config.ts` against the traffic you expect
