코어 테이블(`packages/databases/core-table`)은 키 기반 접근을 위해 만들어졌으며 "제목이나 설명이 이 텍스트와 일치하는 강의 찾기"를 위한 것이 아닙니다. [Amazon OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html)가 이를 위한 검색 계층이며, GSI를 더 추가하는 대신 코어 테이블 밖에 둡니다.

## 범위

하나의 컬렉션에 두 개의 인덱스가 있습니다.

| 인덱스 | 담는 것 | 검색할 수 있는 사람 |
|---|---|---|
| `courses` | 현재 **게시된** 모든 강의. 게시되지 않은 강의는 플래그를 붙여 두지 않고 문서를 삭제합니다 | 로그인 여부와 관계없이 누구나(`course.publicSearch`, `course.publicSuggest`) |
| `transcripts` | 수강 중인 학습자가 시청할 수 있는 동영상의 자막 트랙 구절 | 수강 중인 학습자, 하나의 강의 안에서(`transcript.search`) |

더 많은 콘텐츠 유형(강사, 공지사항)은 나중에 추가되며, 각각 별도의 인덱스와 프로시저를 갖고 여러 유형을 섞는 하나의 쿼리는 사용하지 않습니다. 매핑 유형은 OpenSearch 2.0에서 제거되었으므로 유형마다 인덱스가 하나입니다. 유형마다 고유한 가시성 규칙도 있으며, 따로 두는 것이 읽고 테스트하기 가장 쉽습니다.

## 비용: NextGen, zero-ETL이 아님

비용 때문에 두 가지 AWS 네이티브 대안을 채택하지 않았습니다.

- **동기화**: [DynamoDB용 OpenSearch Ingestion zero-ETL 통합](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/OpenSearchIngestionForDynamoDB.html)은 테이블 변경 여부와 관계없이 고정된 최소량이 있는 OCU 시간 단위로 청구되는 관리형 파이프라인을 실행하며, 로컬 개발에서 대응하는 것이 없습니다. DynamoDB Streams와 Lambda(아래)는 쓰기 사이에는 비용이 들지 않으며 로컬 이벤트 러너를 재사용합니다.
- **컬렉션 용량**: 기존 세대는 계속 청구되는 2 OCU의 고정 하한이 있습니다. 대신 컬렉션은 NextGen 컬렉션 그룹(`AWS::OpenSearchServerless::CollectionGroup`, `Generation: NEXTGEN`)에 두며, 그 하한은 스테이지별로 선택합니다(스테이지의 `search` 설정에 있는 `min{Indexing,Search}CapacityInOcu`).

| 스테이지 | 최소 OCU(색인 / 검색) | 효과 |
|---|---|---|
| `discava-development` | 0 / 0 | 테스터가 없을 때는 0으로 축소됩니다. 한동안 조용했다가 처음 검색하면 콜드 스타트로 약 10~30초 기다립니다 |
| `discava-production` | 1 / 1 | 콜드 상태에서 응답하지 않으며, 기존 세대의 하한보다도 낮습니다 |

NextGen은 일부 리전에서만 사용할 수 있습니다(작성 시점 기준: 미국 동부 버지니아 북부/오하이오, 미국 서부 오리건, 아시아 태평양 뭄바이/싱가포르/시드니/도쿄, 유럽 프랑크푸르트/아일랜드/스페인/스톡홀름). 스테이지의 배포 리전이 이 중 하나인지 확인하세요.

## 패키지

| 패키지 | 담는 것 |
|---|---|
| `packages/databases/search` | 클라이언트(`getOpenSearchClient`, `resolveIndexName`), 각 인덱스의 zod 스키마와 매핑(`src/indices`), 인덱스 매니페스트 생성기, index-sync(`src/index-sync`) |
| `packages/common/constructs` | `OpenSearchCollection`(범용: NextGen 컬렉션 그룹, 컬렉션, 보안 정책, `grantRead`/`grantWrite`, index-sync 커스텀 리소스)과 `SearchCollection`(Discava의 인스턴스) |
| `packages/events` | `src/search/search-indexing.ts`가 `courses` 인덱스를 테이블과 일치시키고, `search-reindex.ts`가 이를 다시 만듭니다. `transcript-indexing.ts`와 `transcript-reindex.ts`는 `transcripts`에 대해 같은 일을 합니다([트랜스크립트 검색](#트랜스크립트-검색) 참고) |
| `packages/apis/core-api` | `course.publicSearch`와 `course.publicSuggest`(`procedures/search.ts`, `helpers/search-query.ts`, `suggest-query.ts` 포함). `transcript.search`(`procedures/transcript.ts`, `helpers/transcript-access.ts`, `transcript-query.ts`, `transcript-snippet.ts` 포함) |
| `packages/common/web-utils` | `webvtt`: 트랜스크립트 패널과 트랜스크립트 색인기가 공유하는 WebVTT 파서 |

**Index-sync**는 없는 인덱스를 만들고 기존 인덱스에는 매핑을 적용합니다(`putMapping`). 인덱스를 삭제하지는 않습니다. 배포할 때마다 실행되므로 직접 삭제한 인덱스는 다시 생깁니다.

search 패키지는 의도적으로 `packages/databases/core-table`의 구조를 따릅니다. [awslabs/nx-plugin-for-aws#1267](https://github.com/awslabs/nx-plugin-for-aws/issues/1267)이 제안한 `ts#opensearch` 생성기(아직 `@aws/nx-plugin`에 없음)와 일치하도록 직접 만들었으므로, 업스트림에 기여하고 나중에 작은 차이만으로 다시 교체할 수 있습니다.

## 색인 파이프라인

```d2 title="A course change reaches the search index through the stream router"
direction: right

table: "Core table" {shape: cylinder}
router: "Stream router"
queue: "search-indexing queue"
index: "Search indexing"
search: "courses index" {shape: cylinder}

table -> router: "stream"
router -> queue: "SEARCH_STREAM_FILTERS"
queue -> index
index -> table: "read course and rating"
index -> search: "index / delete"
```

코어 테이블의 스트림에는 읽는 주체가 하나 있습니다. <Link path="design/stream-event-router">스트림 라우터</Link>이며, 각 변경을 그것에 등록된 모든 기능의 큐로 보냅니다. 검색 색인은 그런 기능(`search-indexing`) 중 하나이며 자체 큐와 실패 큐가 있으므로 이 기능의 실패가 다른 기능을 막지 않습니다.

이 기능의 필터 `SEARCH_STREAM_FILTERS`(`core-table/src/helpers/search-stream.ts`)는 `course` 또는 `courseRating` 레코드의 모든 삽입과 변경, 그리고 `course`의 삭제를 통과시킵니다. 커리큘럼 편집과 개별 리뷰는 문서를 바꿀 수 없으므로 라우팅되지 않습니다.

`search-indexing.ts`는 변경을 어떤 강의가 바뀌었는지 알아내는 데에만 사용하고, 그 강의를 테이블이 지금 가진 상태로 읽습니다.

- 배치의 서로 다른 `courseId`마다 키로 한 번씩, 일관되게, 평점 집계와 함께 읽습니다.
- 강의가 `'published'`이면 문서를 기록합니다(`toCourseDocument`로 만들고 `CourseDocumentSchema`로 검증). 게시되지 않았거나 없으면 문서를 삭제합니다.
- 문서의 ID는 강의의 `courseId`이므로 재생되거나 재시도되거나 순서가 뒤바뀐 레코드도 중복 없이 같은 문서로 수렴합니다.

새로 만든 인덱스는 비어 있는 상태로 시작합니다. 스트림은 인덱스가 존재한 뒤에 일어난 변경만 전달하므로, 그 전에 게시된 강의는 다음에 기록되거나 인덱스를 다시 만들 때까지 검색되지 않습니다.

### 강의 문서

`courseId`, `title`, `description`, `imageKey`, `status`, `publishedAt`, `updatedAt` 외에 문서는 세 가지 선택적 필드 그룹을 가집니다.

| 그룹 | 필드 | 매핑 |
|---|---|---|
| 카탈로그 | `categoryId`, `tags`, `level`, `language`, `durationHours` | `keyword`(`tags`는 배열), `durationHours`는 `integer` |
| 평점 | `ratingCount`, `ratingAverage`, `ratingScore`, `ratingBoost` | `integer`와 `float`. 평점이 없는 강의는 1로 설정된 `ratingBoost`만 가집니다 |
| 가격 | `priceAmount`(최소 단위), `priceCurrency` | `integer`, `keyword` |

`title`과 `description`은 `english` 분석기를 쓰는 `text`이므로 "design"이 "designing"을 찾습니다.

문서는 카테고리의 이름이나 슬러그가 아니라 `categoryId`를 저장합니다. 이름을 바꿔도 문서는 건드리지 않으며, 응답을 만들 때 `category` 레코드에서 이름과 슬러그를 찾습니다.

### 배포된 스테이지 재색인

`src/search/search-reindex.ts`는 이벤트 소스도 API 경로도 없는 비공개 Lambda입니다. 게시된 강의를 페이지 단위로 읽어 스트림 색인기가 쓰는 것과 같은 `toCourseDocument`로 `_bulk` 기록한 다음, 더 이상 게시되지 않은 강의의 문서를 삭제합니다. 인덱스를 다시 만든 뒤, 색인 버그가 있었을 때, 또는 필드를 추가하는 배포 후에 실행하세요.

```sh
pnpm nx run @discava/tooling-deploy:reindex-search --stage=discava-development
```

색인한 강의 수와 제거한 오래된 문서 수를 출력합니다. 두 번 실행해도 같은 문서가 남습니다.

- 컬렉션의 데이터 접근 정책이 스택의 Lambda 역할만 지정하므로 자체 역할로 실행됩니다. 개인의 AWS 로그인은 데이터 플레인에서 403을 받습니다.
- `grantWrite`의 `aoss:WriteDocument`가 삭제도 포함합니다.
- 제한 시간은 5분입니다. 한 번의 호출로 처리하기에 너무 큰 카탈로그라면 Lambda가 스스로에게 넘겨야 합니다.

로컬에서는 `pnpm nx run @discava/e2e:seed-local-courses`가 instructor API로 강의를 만들고 게시하며, 스트림이 이를 색인합니다.

### 카탈로그 필드 롤아웃

`courses` 매핑에 필드를 추가하는 것은 가산적입니다. index-sync의 `putMapping`이 배포 시 새 인덱스 없이 라이브 인덱스에 그대로 적용합니다. 카탈로그 필드도 이렇게 추가되었습니다. 기존 속성을 바꾸거나 제거하는 것은 호환되지 않는 변경이며 대신 #270의 버전이 있는 인덱스가 필요합니다.

그런 배포 전에 게시된 강의는 다음에 기록될 때까지 새 필드의 값이 없으므로, 배포 후에 **재색인을 한 번 실행**하세요(위 명령).

## 검색 프로시저

`course.publicSearch`는 직접 작성한 검색 플러그인(`src/middleware/search.ts`의 `createSearchPlugin`)과 코어 테이블 플러그인을 추가하는 `publicSearchProcedure`(`src/init.ts`) 위에 만들어집니다. `connection` 생성기에 아직 tRPC와 OpenSearch 조합이 없어서 플러그인은 직접 작성했습니다.

`course.publicList`처럼 공개이며, 로그아웃한 호출자도 검색할 수 있습니다. 가시성은 두 번 강제됩니다. 색인 시점(위)과 쿼리에서이며, 쿼리는 색인된 모든 강의가 이미 게시 상태이더라도 항상 `status: 'published'`로 필터링합니다. 그러면 한쪽의 버그만으로 호출자와 초안 또는 보관된 강의 사이가 뚫리지 않습니다.

`buildSearchRequest`(`helpers/search-query.ts`)가 하나의 요청을 만듭니다.

- **텍스트**: `title`과 `description`에 대한 `multi_match`. 어떤 단어든 일치할 수 있으며 일치하는 단어가 많을수록 순위가 높습니다. 텍스트가 없으면 게시된 모든 강의가 일치합니다.
- **순위**: 기본 정렬에서는 텍스트 쿼리의 점수에 강의의 `ratingBoost`가 곱해지므로, 평점이 좋은 강의가 관련도가 같은 평점이 낮은 강의보다 위에 옵니다. 텍스트가 없으면 최근에 게시된 순입니다. `rating`과 `newest` 정렬은 둘 다 대체합니다.
- **필터**: 카테고리, 태그, 수준, 언어, 기간은 `post_filter`에 들어가므로 히트가 완전히 필터링됩니다. 최소 평점은 쿼리 자체에 들어가므로 모든 패싯 수가 이를 반영합니다.
- **패싯**: 패싯마다 하나의 `filter` 집계가 있으며 자기 자신을 제외한 모든 필터를 적용하므로, 그 수는 다른 값을 고르면 얻게 될 결과를 보여 줍니다.

응답은 검색과 병렬로 읽은 `category` 레코드에서 각 히트의 카테고리 이름을 채웁니다. 8초를 넘기는 요청은 tRPC `TIMEOUT`이 되므로, 콜드 상태의 컬렉션은 Lambda 자체의 제한 시간 전에 명확하고 재시도 가능한 오류를 줍니다.

## 제안

**스펙:** [`specs/20261119-195009-search-suggestions/`](https://github.com/AlexTo/discava/tree/main/specs/20261119-195009-search-suggestions/)

학생 포털의 검색 상자(`site-search.tsx`)는 입력하는 동안 일치하는 강의를 최대 10개 보여 줍니다. `course.publicSuggest`(입력 `{ q }`, 출력 `{ items: [{ courseId, title, imageKey? }] }`)는 `publicSearch`와 같은 파일의 `publicSearchProcedure` 위에 만들어집니다. 요청은 `buildSuggestRequest`(`helpers/suggest-query.ts`)가 만듭니다.

### 왜 `publicSearch`가 아닌가

`publicSearch`는 항상 다섯 개의 패싯 집계를 실행하고, 코어 테이블에서 모든 카테고리를 읽고, 전체 결과 카드를 반환합니다. 제안에는 이 중 아무것도 필요하지 않으며 훨씬 자주 호출됩니다. 별도의 프로시저는 `publicSearch`의 것을 느슨하게 하지 않고도 자체 입력 범위(3~200자)와 더 짧은 제한 시간을 가질 수 있습니다. `publicSearch`에 `mode` 플래그를 두는 방식은 채택하지 않았습니다. 하나의 프로시저가 두 가지 출력 형태를 가지면 타입을 지정하고 테스트하기가 더 어렵습니다.

### 쿼리

`title`에 대한 `match_bool_prefix`이며, 전체 검색과 같은 `ratingBoost`가 있는 `function_score` 안에서 같은 `status: 'published'` 필터를 사용합니다.

- 마지막 용어를 제외한 모든 용어는 (어간 처리된) 전체 용어로 일치시키고, 마지막은 접두사로 일치시킵니다. "pyth"는 "Python for Data Analysis"를 찾습니다.
- 요청은 `operator`를 설정하지 않으므로 용어들은 OR로 결합됩니다. 하나만 일치해도 충분하며 더 많은 용어가 일치하는 강의가 더 높은 점수를 받습니다. "java zzzz"도 Java 강의를 제안합니다.
- 히트는 점수, 그다음 `publishedAt` 내림차순, 그다음 `courseId` 순으로 정렬됩니다.
- 집계는 없고, `track_total_hits`는 꺼져 있으며, `courseId`, `title`, `imageKey`만 가져옵니다.

기존 `title` 필드를 쿼리하므로 매핑이 바뀌지 않으며 어떤 스테이지도 재색인이 필요하지 않습니다.

알려진 한계: 마지막 용어는 접두사가 적용되기 전에 어간 처리되므로, 어간이 색인된 어간의 접두사가 아닌, 입력하다 만 단어는 다음 글자를 입력하기 전까지 찾지 못할 수 있습니다. 이것이 너무 자주 발생한다면 후속 조치는 `standard` 분석기를 쓰는 `search_as_you_type` 유형의 `title.suggest` 하위 필드를 `multi_match` `bool_prefix`로 쿼리하는 것입니다. 이는 가산적(`putMapping`)이지만 스테이지마다 재색인이 한 번 필요합니다.

### 입력, 디바운스, 재사용

- 공백을 제거한 뒤 **3자 미만**이거나 200자를 넘으면 아무것도 전송하지 않습니다.
- 공백을 제거한 텍스트는 **300ms 디바운스**되므로(`useDebouncedValue`) 연속 입력은 마지막 텍스트에 대해 하나의 요청만 보냅니다.
- 쿼리는 텍스트를 키로 하므로 "javas"에 대한 느린 응답은 "javas" 캐시 항목에 들어가며 "javascript"의 목록을 절대 대체하지 않습니다. `staleTime`(60초) 안에 최근 텍스트를 다시 입력하면 그 응답을 재사용하고 아무것도 전송하지 않습니다.
- 폼을 제출하거나 행을 선택하면 대기 중인 디바운스가 취소되므로 이미 제출한 텍스트에 대해서는 요청이 발생하지 않습니다.

### 실패, 제한 시간, 스로틀

요청에는 `publicSearch`의 8초보다 짧은 **3초 제한 시간**(`SUGGEST_REQUEST_TIMEOUT_MS`)이 있으므로 콜드 상태의 컬렉션이 입력이 멈출 때마다 Lambda 동시성을 붙잡지 않습니다. `TimeoutError`는 `publicSearch`에서처럼 tRPC `TIMEOUT`이 됩니다. 포털은 429를 포함한 모든 오류를 "제안 없음"으로 취급합니다. 알림을 표시하지 않고 재시도하지도 않는데, 다음에 입력이 멈출 때 어차피 요청이 대체되기 때문입니다.

`course.publicSuggest`는 `PUBLIC_OPERATIONS`에 있지만 공유 `publicThrottle`을 사용하지 않습니다. 그 한도는 방문자별로 세지 않고 모든 호출자가 공유하며, core-api가 받는 가장 빈번한 요청에는 너무 빡빡합니다. `discava-development`에서는 두 사람이 동시에 입력하면 드롭다운이 조용히 작동을 멈추게 됩니다. 이 요청에는 두 개의 `coreApi` 스테이지 키 `publicSuggestThrottleRateLimit`과 `publicSuggestThrottleBurstLimit`로 설정하는 자체 스로틀이 있습니다.

| 스테이지 | 제안 스로틀(속도 / 버스트) | 다른 공개 작업 |
|---|---|---|
| `discava-development` | 5 / 10 | 1 / 3 |
| `discava-production` | 100 / 200 | 20 / 40 |
| 기본값(스테이지가 두 키를 모두 설정하지 않음) | 100 / 200 | 20 / 40 |

한 사람이 꾸준히 입력하면 초당 약 1건의 요청이 듭니다.

- 개발 환경의 5 / 10은 동시에 약 5명의 테스터를 처리하며, 익명의 폭주가 닿을 수 있는 범위를 작게 유지합니다. 그곳에서는 WAF가 꺼져 있으며 core-api의 예약된 동시성 10이 여전히 동시 요청을 제한합니다.
- 프로덕션의 100 / 200은 같은 순간에 입력하는 약 100명을 처리합니다. 요청은 코어 테이블 읽기가 없는 10개 히트 쿼리이므로 Lambda를 잠깐만 붙잡습니다. 스테이지의 다른 한도와 마찬가지로 실제 트래픽에 맞춰 올리세요.

어느 스테이지에도 IP별 속도 규칙은 없으므로, 다른 공개 작업과 마찬가지로 한 명의 과도한 호출자가 한도 전체를 쓸 수 있습니다.

## 트랜스크립트 검색

**스펙:** [`specs/20261120-002950-transcript-search/`](https://github.com/AlexTo/discava/tree/main/specs/20261120-002950-transcript-search/)

수강 중인 학습자는 강의 동영상에서 말한 내용을 검색하고 그 시점에서 동영상을 열 수 있습니다. 동영상 하나의 트랜스크립트를 보여 주는 패널은 <Link path="design/video-player">동영상 플레이어</Link> 페이지에 설명되어 있습니다.

### 왜 별도의 인덱스인가

`transcripts` 인덱스는 `courses` 안이 아니라 그 옆에 있습니다.

- **단위**: 한쪽은 강의, 다른 쪽은 구절입니다.
- **수명 주기**: 강의 문서는 강의가 게시되어 있는 동안 존재합니다. 구절은 동영상을 볼 수 있는 동안, 초안이나 보관된 강의에서도 존재합니다.
- **가시성**: `courses`는 공개이고 트랜스크립트는 수강 중인 학습자용입니다. 유료 강의 콘텐츠를 익명 호출자가 쿼리하는 인덱스 밖에 두면 공개 쿼리의 실수로 그것이 반환될 수 없습니다.
- **크기**: 트랜스크립트는 메가바이트 단위입니다. 강의 문서에 넣으면 강의를 편집할 때마다 다시 써야 하고 모든 카탈로그 검색이 이에 대해 점수를 계산해야 합니다.

Index-sync는 기존 매핑을 바꾸지 않고 배포 시 인덱스를 만듭니다.

### 구절, 그리고 히트가 시간이 되는 방법

문서는 하나의 자막 트랙의 한 **구절**이며, 연속된 큐를 한 칸 공백으로 이은 것입니다. 구절은 다음 큐를 넣으면 첫 큐의 시작으로부터 30초를 넘거나 600자를 넘을 때 닫힙니다. 첫 구절 이후의 각 구절은 이전 구절의 마지막 큐로 시작하므로, 두 큐에 걸친 문구는 항상 하나의 구절 안에서 찾을 수 있습니다.

문서는 텍스트, 시작과 종료 시간, 그리고 각 큐의 시작 시간과 텍스트 내 문자 오프셋(저장되지만 색인되지 않음)을 저장합니다. 이는 트랙당 동영상 한 시간에 약 130개의 문서입니다.

히트를 시간으로 바꾸는 방법은 다음과 같습니다.

1. 쿼리는 두 개의 사용자 정의 영역 문자를 태그로 사용하여 구절 전체를 하이라이트하도록 요청합니다(`transcript-query.ts`의 `MATCH_START`와 `MATCH_END`).
2. 프로시저는 태그가 붙은 첫 일치를 찾아 그 오프셋을 가져오고, 그것이 속한 큐를 찾습니다. 그 큐의 시작이 해당 순간의 시간입니다.
3. 스니펫은 같은 텍스트에서 잘라 내어 HTML이 아닌 `{ text, match }` 부분으로 반환합니다.

겹침 때문에 공유된 큐의 일치는 두 번 발견됩니다. 프로시저는 40개의 히트를 요청하고 동영상, 트랙, 큐 시작으로 중복을 제거하여 최대 20개를 반환합니다.

### `transcript-indexing` 기능

자체 큐와 실패 큐를 가진 별도의 스트림 기능입니다(<Link path="design/stream-event-router">스트림 라우터</Link> 참고). 강의 색인기가 읽어서는 안 되는 레슨 미디어 버킷을 읽으며, 잘못된 자막 파일이 강의 색인을 지연시켜서는 안 되기 때문입니다. `search-indexing`처럼 변경을 어떤 항목이 바뀌었는지 알아내는 데에만 사용하고(`transcript-actions.ts`), 그 항목을 테이블이 지금 가진 상태로 읽습니다(`transcript-sync.ts`).

| 레코드 | 효과 |
|---|---|
| `contentItem` INSERT | 이미 `captionTracks`가 있는 동영상을 동기화합니다 |
| `contentItem` MODIFY | `captionTracks`, `captionTracksRev`, `status`, `s3Key`, `previousS3Key`, `visibility`, `archivedAt`이 바뀐 동영상을 동기화합니다. 다른 변경(학생 카운터 등)은 아무것도 하지 않으며 아무것도 읽지 않습니다 |
| `contentItem` REMOVE | 해당 `contentItemId`의 모든 문서를 삭제합니다 |
| `lesson` 또는 `module` MODIFY | 표시 여부가 바뀌었다면 그 아래의 모든 동영상 항목을 동기화합니다 |
| `lesson` 또는 `module` REMOVE | 해당 `lessonId` 또는 `moduleId`의 모든 문서를 삭제합니다 |

**항목 동기화**(`syncItemTranscripts`):

1. 항목, 그 레슨, 그 모듈을 일관되게 읽습니다.
2. 필요한 문서를 계산합니다. 세 가지가 모두 표시되고 항목이 재생 가능한 버전이 있는 동영상이면, 그 버전의 모든 트랙의 구절이며 레슨 미디어 버킷의 WebVTT 파일로 만듭니다. 그렇지 않으면 필요한 문서가 없습니다.
3. 인덱스가 그 항목에 대해 가진 ID를 나열하고, 필요한 것은 `_bulk`로 기록하고 나머지는 삭제합니다.
4. 세 레코드를 다시 읽습니다. 문서가 의존하는 것이 바뀌었다면 한 번 더 동기화하며(재시도를 위해 실패하기 전까지 최대 3회), 그래서 한 항목에 대한 두 동기화가 겹쳐도 현재 상태로 끝납니다.

문서의 ID는 `<contentItemId>.<trackId>.<seq>`입니다(`transcriptDocumentId`). 따라서 중복되거나 늦거나 순서가 뒤바뀐 전달도 같은 문서를 기록하며, 새 `trackId`를 받는 교체된 트랙은 이전 것으로 오인될 수 없습니다.

**알려진 잔존 사례.** OpenSearch Serverless는 쓰기가 몇 초 뒤에 검색에 보이며 `refresh=wait_for`가 없습니다. 트랙을 추가한 뒤 몇 초 안에 교체하면 두 번째 동기화가 ID를 나열할 때 첫 동기화의 문서를 보지 못해 남겨 둘 수 있습니다. 검색은 트랙과 버전이 지금 테이블에 나열된 히트만 반환하므로(아래) 이 문서들은 표시되지 않습니다. 재구축이 이를 제거합니다. `_delete_by_query`에 의존하는 것은 없습니다.

기록하는 쪽(Transcribe의 완료, instructor-api의 자막 프로시저, 버전 교체)은 바뀌지 않으며 검색 때문에 실패할 수 없습니다.

### 재구축

인덱스는 모든 스테이지에서 비어 있는 상태로 시작하고 이후의 변경만 알게 되므로, 배포 전에 자막이 달린 동영상은 한 번 실행해야 합니다. 재구축은 위의 잔존 사례, 다시 만든 인덱스, 향후 분석기 변경을 위한 복구이기도 합니다.

```sh
pnpm nx run @discava/tooling-deploy:reindex-transcripts --stage=discava-development
pnpm nx run @discava/tooling-deploy:reindex-transcripts --stage=discava-development --course=<courseId>
```

`transcript-reindex.ts`는 `search-reindex.ts`처럼 이벤트 소스가 없는 비공개 Lambda입니다. 각 강의(하나, 또는 각 상태별 `course.query.byStatus`로 모든 강의)에 대해 커리큘럼을 읽고, 모든 동영상 항목을 동기화한 다음, 항목이 커리큘럼에 없는 해당 강의의 문서를 삭제합니다.

시간이 거의 다 되면 커서를 반환하고, 스크립트는 커서가 없어질 때까지 다시 호출한 뒤 합계를 출력합니다. `--stage` 없이 실행하면 로컬 스택에 대해 프로세스 내에서 실행됩니다. 두 번 실행해도 같은 문서가 남습니다.

### 검색 프로시저

`transcript.search`는 로그인한 사용자 전용(`courseSearchProcedure`)이며 `{ courseId, q, language? }`를 받고 `q`는 2~200자입니다. 매 호출마다 다음을 수행합니다.

1. 강의의 커리큘럼과 호출자의 수강 등록을 읽고 `contentItem.videoUrl`이 사용하는 함수인 `requireEnrolment`를 호출합니다.
2. 테이블에서 **시청 가능 집합**을 만듭니다(`watchableVideos`): 재생 가능한 버전이 있는 실질적으로 보이는 동영상 항목과, 각각의 버전 및 트랙 ID.
3. 직접 만든 필터로 인덱스를 쿼리합니다. 검증된 입력의 `courseId`, 시청 가능 집합에 속하는 `contentItemId`, 아래의 언어 규칙입니다. 집합이 비어 있으면 쿼리하지 않고 아무것도 반환하지 않습니다.
4. 버전이나 트랙이 시청 가능 집합에 없는 히트를 제외합니다.
5. 제목은 인덱스가 아니라 읽어 온 커리큘럼에서 가져옵니다.

인덱스는 테이블보다 몇 초 뒤처지며 잔존 문서를 가질 수 있으므로, 색인된 플래그를 신뢰하는 필터는 방금 숨겨진 동영상의 텍스트를 그 몇 초 동안 반환할 것입니다. 테이블로부터 필터를 만들면 이 틈이 닫히며, 브라우저가 보내는 어떤 것도 동영상을 집합에 추가할 수 없습니다. 이는 다시 "두 번 강제"하는 규칙입니다. 색인기는 시청 가능한 항목의 구절만 유지하고 쿼리는 시청 가능한 항목만 허용합니다.

비용은 검색당 커리큘럼 쿼리 한 번이며, 이는 `course.view`가 강의 플레이어의 모든 페이지에서 이미 치르는 비용입니다. 8초를 넘기는 요청은 강의 검색과 마찬가지로 `TIMEOUT`이 됩니다.

### 어느 트랙을 검색하는가

구절은 학생이 재생하는 버전의 모든 트랙(최대 10개)에 대해 만들어지며, 각각 `language`, `isDefault`, `trackLanguages`를 가집니다.

검색은 동영상마다, 브라우저가 보내는 언어(학습자가 기억해 둔 자막 언어)의 트랙이 있으면 그 트랙에서, 없으면 기본 트랙에서 찾습니다. 그러면 한 순간이 두 언어로 두 번 나열되지 않으며 결과는 학습자가 여는 트랜스크립트와 일치합니다. 자막 언어를 바꿔도 재색인이 필요하지 않습니다.

`text`는 `standard`로 분석되며 `english` 하위 필드가 있습니다. 모든 쿼리는 둘 다 일치시키고 모든 단어를 요구하므로, 영어 트랙은 강의 검색이 가진 어간 처리를 얻고 다른 언어는 전체 단어로 일치합니다. 구절 일치는 순위가 더 높습니다. 중국어, 일본어, 태국어는 글자 단위로 분리되며, 순위는 약하지만 구절을 여전히 찾습니다. 언어별 하위 필드는 가산적인 변경이 될 것입니다.

### 비용

스테이지 설정은 바뀌지 않습니다. 두 번째 인덱스는 컬렉션 그룹에 용량 하한을 추가하지 않습니다.

- **색인**은 동영상에 자막이 달리거나 트랙이 바뀔 때 짧은 폭주로 일어납니다. 트랙당 동영상 한 시간에 약 130개의 작은 문서를 `_bulk`로 한 번 처리합니다.
- **검색**은 키 입력마다가 아니라 제출 시에 일어나며, 하나의 강의로 필터링되고, 집계가 없습니다.
- **저장 공간**은 트랙당 동영상 한 시간에 약 150 KB의 소스이므로, 트랙이 두 개인 20시간짜리 강의는 약 5,000개의 문서와 6 MB입니다.
- **그 주변**: 라우팅된 `contentItem`, `lesson`, `module` 변경마다 SQS 메시지 하나, 동기화마다 트랙당 S3 GET 하나, 검색마다 커리큘럼 쿼리 하나.

용량 하한이 0인 스테이지에서는 한동안 조용했다가 처음 검색할 때 콜드 스타트가 발생해 시간 초과가 될 수 있습니다. 색인 쪽에서는 큐의 다섯 번 수신이 콜드 스타트보다 오래 가야 합니다.

### #270과의 관계

인덱스 추가는 index-sync가 이미 처리하는 경우이므로 여기의 어떤 것도 #270(기존 인덱스의 매핑 변경)과 충돌하지 않습니다.

- 모든 호출자가 `resolveIndexName('transcripts')`를 사용하므로, 논리적 이름이 버전이 있는 인덱스에 대한 별칭이 되어도 호출자는 바뀌지 않습니다.
- 이후의 가산적 변경은 `putMapping`을 거칩니다.
- 호환되지 않는 변경(`text`의 분석기, 필드의 유형)은 #270의 경우이며, 위의 재구축이 그것이 필요로 하는 "재구축 작업"입니다. 오래된 쓰기에 대한 방어는 버전과 함께 항목의 `captionTracksRev`를 사용해야 합니다. 문서는 `versionId`를 가지며 `captionTracksRev`는 그때 필드로 추가할 수 있습니다.
- 출시 전에는 호환되지 않는 변경이 "인덱스 삭제, 배포, 재구축 실행"입니다.

### AI 튜터(#289)가 의존할 수 있는 것

문서는 강의, 모듈, 레슨, 동영상, 버전, 트랙, 언어, 시간 범위를 가진 약 30초의 구절입니다. 따라서 검색은 레슨, 동영상, 강의로 범위를 좁힐 수 있고 "lesson X의 12:40"을 인용할 수 있습니다.

`watchableVideos`는 학습자가 볼 수 있는 동영상을 주고 `buildTranscriptSearchRequest`는 그것으로 필터링된 요청을 만듭니다. 튜터는 같은 두 가지를 호출하므로 학습자가 볼 수 없는 것을 검색할 수 없습니다.

검색은 어휘 기반(BM25)입니다. 튜터가 벡터 검색을 원하는지는 #289의 미결 사항입니다. 구절마다 임베딩과 `knn_vector` 필드가 필요하며, NextGen 검색 컬렉션이 이를 받는지 먼저 확인해야 합니다. 생성 시 설정이 필요하다면 인덱스를 다시 만들고 재구축하며, 출시 전에는 비용이 들지 않습니다.

## 로컬 개발

`pnpm dev`는 포트 9200에서 `opensearchproject/opensearch` 컨테이너를 실행합니다(`packages/tooling/local-dev/src/opensearch`, DynamoDB local 및 S3Mock과 같은 `runLocalContainer` 패턴). 단일 노드이고, 보안 플러그인은 비활성화되어 있으며, 메모리가 제한됩니다. `@discava/search`의 `dev` 타깃이 이를 시작하고 로컬 인덱스를 동기화합니다.

- 로컬 이벤트 러너(`packages/events/src/local/event-runner.ts`)는 배포된 스테이지와 같은 스트림 라우터, 기능, 색인 핸들러를 실행합니다.
- `pnpm nx run @discava/tooling-local-dev:reset-local-data`는 인덱스도 삭제합니다.

이미지는 `packages/databases/search/config.json`에서 `latest`가 아니라 3.x 릴리스로 고정되어 있습니다. [OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-overview.html)는 새 오픈 소스 릴리스로 컬렉션을 자동으로 업그레이드하며 OpenSearch 3.x와 호환되는 클라이언트를 요구하므로, 로컬 개발은 릴리스가 나올 때마다 따라가지 않고 그 계열에 머뭅니다. 고정 시점에 최신 릴리스였고 Serverless와 맞추기 위해 선택했으므로, 다른 로컬 이미지와 달리 2주 늦추지 않았습니다. Serverless가 더 새로운 마이너 버전으로 옮겨 가면 다시 고정하고, `sync-indices.ts`와 프로시저의 호출을 [지원되는 작업 목록](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-genref.html)에 비추어 다시 확인하세요.

## #1267과의 차이점

업스트림 `ts#opensearch` 제안(또는 이를 채택하는 PR)이 하나하나 확인할 수 있도록 여기에 남겨 둡니다.

- CDK에는 아직 `AWS::OpenSearchServerless::*`에 대한 L2 구성 요소가 없고 L1 `Cfn*` 리소스만 있습니다. `OpenSearchCollection`은 그 위에 데이터 접근 정책과 `grantRead`/`grantWrite`를 직접 구현합니다.
- 수혜자의 데이터 접근 정책 항목에는 리터럴 주체 ARN이 필요합니다(OpenSearch Serverless는 수혜자 자신의 IAM 정책이 아니라 거기서 ARN으로 인가함). 각 부여는 모든 수혜자에 의존하는 스택의 하나의 공유 정책이 아니라 수혜자의 구성 요소 경로로 이름이 붙은 자체 정책을 수혜자의 스택에 만듭니다. 공유 정책은 모든 역할의 ARN을 가져오게 되고, CloudFormation은 다른 스택으로 옮겨진 역할의 내보내기를 멈추는 스택의 배포를 거부하기 때문입니다.
- index-sync 커스텀 리소스 자체의 데이터 접근 부여는 `grantRead`/`grantWrite`가 채우는 것과 별개의, 즉시 적용되는 같은 스택의 정책입니다. 컬렉션 자체 스택의 배포 중 커스텀 리소스가 처음 실행되기 전에 존재해야 하는데, 지연된 스택 간 정책은 이를 보장할 수 없기 때문입니다.
- 모든 컬렉션은 자체 NextGen `AWS::OpenSearchServerless::CollectionGroup` 안에 만들어집니다([비용](#비용-nextgen-zero-etl이-아님) 참고). #1267보다 나중에 나온 리소스이며, 현재의 #1267을 기준으로 작성된 생성기는 대신 기존 방식의 상시 가동 컬렉션을 만들 것입니다.
- 인덱스 매니페스트를 생성하는 타깃은 `indices`가 아니라 `generate-indices-manifest`입니다. 이 워크스페이스의 다른 모든 타깃은 동사(`compile`, `bundle`, `pull-image`)이고, `indices`는 매니페스트 파일을 쓰는 것이 아니라 인덱스를 만들거나 나열하는 것처럼 읽히기 때문입니다.
