## 규칙

**모든 판매와 모든 환불은 한 번만 기록되며, 어떤 수익도 두 번 지급되지 않습니다.** 수익은 <Link path="design/payments">주문</Link>에서 만들어지는 추가 전용 원장이며, 정산은 별도로 계산한 금액이 아니라 원장 항목을 가져갑니다.

## 수익 규칙

core-table의 `helpers/revenue.ts`는 통화의 최소 단위로 하는 순수 정수 연산입니다.

- **수수료.** 플랫폼은 결제 금액에 대해 수수료를 가지며, 스테이지별로 베이시스 포인트(2000은 20%)로 설정하고 반올림(0.5는 올림)합니다. 판매는 기록될 때의 수수료를 유지하므로, 설정을 바꾸면 이후 판매에만 영향을 줍니다.
- **분배.** 강좌의 강사들은 판매를 똑같이 나눕니다. 분배는 정가, 결제 금액, 수수료에 각각 적용되며, 남는 단위는 ID 순으로 앞선 강사들에게 하나씩 돌아가므로 몫의 합은 항상 전체와 같습니다.
- **순수익.** 강사의 순수익은 결제 금액에 대한 몫에서 수수료에 대한 몫을 뺀 값입니다.
- **환불.** 환불은 환불된 금액에 대한 강사의 몫에서 그에 대해 반환된 수수료를 뺀 만큼을 되돌립니다. 각 단계는 새 환불 합계에 대한 몫에서 기록된 합계에 대한 몫을 뺀 값으로 계산되므로, 환불을 어떻게 나누어 진행하든 주문이 전액 환불되면 항목의 합이 정확히 한 번 맞습니다. 환불은 결제 금액을 넘을 수 없습니다.

## 원장

| 레코드 | 담는 내용 |
| --- | --- |
| `earningOrder` | 판매 하나에 대한 원장의 스냅샷과 지금까지 기록된 환불 합계 |
| `earningEntry` | 판매 또는 환불 단계마다 강사별로 한 줄: 총액, 할인, 환불, 수수료, 순수익, 지급 가능 시점, 이를 가져간 정산 |
| `earningDay` | 강사의 강좌, 통화, UTC 날짜별 항목의 합계 |

core-table의 `helpers/earning.ts`가 세 레코드의 유일한 작성자이며 예외가 하나 있습니다. 항목의 `payoutId`를 설정하거나 지우는 코드는 `helpers/payout.ts`뿐입니다. 판매와 각 환불 단계는 항목, 해당 일별 행에 대한 더하기, 주문의 카운터를 담은 **하나의 트랜잭션**이므로 보고서와 원장이 어긋날 수 없습니다.

항목은 구매자를 이름으로 지정하지 않습니다. 또한 주문이 결제된 Stripe 계정과 모드를 가지고 있습니다. [결제 계정 규칙](#결제-계정-규칙)을 참고하세요.

## 기록

기록은 <Link path="design/stream-event-router">스트림 기능</Link> `earnings-recording`입니다. `order`의 모든 변경을 받아 판매인 것에 대해 동작합니다. 다음 두 조건이 모두 성립하면 주문은 판매입니다.

- `paid`이거나, 사유가 `requested`인 `refunded`입니다.
- 금액이 0보다 큽니다.

전달 불가로 자동 환불된 주문은 판매가 아니었으며, 쿠폰이 가격 전체를 차감한 금액 0의 주문도 마찬가지입니다. 할인된 주문에서 항목의 총액은 정가이고 할인은 결제 금액과의 차이입니다.

라우터는 최소 한 번, 임의의 순서로 전달하며 핸들러는 이에 맞게 만들어져 있습니다.

- **모든 주문 이미지는 필요한 모든 것을 담고 있으므로** 어느 하나만으로도 판매를 기록하고 환불 합계를 최신으로 만들 수 있습니다. 어떤 레코드도 다른 레코드를 기다리지 않습니다.
- **중복은 아무것도 바꾸지 않습니다.** 판매의 항목은 존재하지 않는다는 조건으로 생성되며, 원장이 이미 도달한 환불 합계는 아무것도 기록하지 않습니다.
- **순서는 중요하지 않습니다.** 늦게 도착한 오래된 이미지는 더 높은 기록된 합계를 발견하고 아무것도 하지 않습니다.
- **실패하면 배치를 재시도합니다.** 적용할 수 있는 것은 모두 적용한 뒤 배치가 예외를 던지며, 적용된 것은 두 번째에는 아무 일도 하지 않습니다.

판매의 항목은 주문이 결제된 지 `holdDays` 후에 지급 가능 상태가 됩니다. 환불의 항목은 즉시 지급 가능 상태가 되므로 다음 정산을 줄입니다.

## Earnings 페이지의 조회

instructor-api는 호출자 자신의 수치를 제공하며 강사 ID를 입력으로 받지 않습니다.

- `earnings.report`는 최대 366일 기간의 일별 행을 합산합니다. 범위 쿼리 한 번이며 통화와 강좌별로 묶습니다.
- `earnings.lines`는 한 강좌의 항목을 페이지 단위로 넘기며, 레코드의 다른 것이 호출자에게 전달되지 않도록 필드별로 구성합니다.
- `payout.overview`는 어떤 정산에도 포함되지 않은 항목을 통화별로 **보류 중**, **계정 설정 대기 중**, **지급 준비됨**, **보류됨**으로 분류하고 강사의 정산을 나열합니다.

## 정산 계정

강사는 Stripe Connect Express 계정으로 지급받습니다.

- `payout.startOnboarding`은 계정을 멱등하게 만들고 Stripe의 온보딩 링크를 반환합니다.
- `payout.account`는 Stripe에서 계정 상태를 읽고 바뀌었으면 `payoutAccount`에 저장합니다. Stripe에 연결할 수 없으면 저장된 상태를 `stale`로 표시하여 반환합니다.
- `payout.dashboardLink`는 온보딩이 끝난 뒤 강사의 Stripe Express 대시보드로 로그인하는 링크를 반환합니다.

| 상태 | 의미 |
| --- | --- |
| `not_started` | 아직 계정 없음. 저장된 것이 없음 |
| `in_progress` | Stripe 양식이 완료되지 않음 |
| `active` | Stripe가 이 계정으로 이체와 지급을 보낼 수 있음 |
| `restricted` | Stripe가 추가로 필요한 것이 있음 |

플랫폼의 연결이 활성 상태가 아니면 여기서는 어떤 것도 Stripe를 호출하지 않습니다. 연결이 없으면 `payout.account`는 `unavailable`로 응답합니다.

## 정산 실행

`Payouts` 스택의 Lambda 함수 하나가 EventBridge 스케줄에 따라 하루에 한 번 실행됩니다. 이 함수는 Stripe 키를 읽을 수 있고 다른 시크릿은 읽을 수 없습니다.

1. **결제 계정에 묶기.** 실행은 연결의 현재 계정과 모드에 대해서만, 그 계정에 속하는 것으로 확인된 키로만 동작합니다.
2. **복구.** 이전 실행이 마무리하지 못한 정산을 먼저 끝냅니다. 아직 `collecting` 또는 `releasing`인 정산은 항목을 돌려주고, `pending`인 정산은 아래 설명대로 정리합니다.
3. **활성 계정이 있는 각 강사에 대해** Stripe에서 계정을 다시 읽습니다. 더 이상 활성이 아닌 계정은 새 상태를 저장하고 건너뜁니다.
4. **통화별로** 어떤 정산에도 포함되지 않은 지급 가능 항목을 합산합니다. 합계가 스테이지의 최소값보다 작거나 0을 넘지 않으면 기다립니다.
5. **수집, 봉인, 전송.** 정산은 `collecting`으로 만들어지고, 항목은 99개씩 배치로 연결되며(트랜잭션은 100개 항목을 담습니다), `pending`으로 봉인됩니다. 그런 다음 정산 ID를 멱등성 키와 전송 그룹으로 하여 Stripe에서 이체를 만들고 정산을 `sent`로 표시합니다.

| 상태 | 의미 |
| --- | --- |
| `collecting` | 항목을 연결하는 중 |
| `pending` | 봉인됨. 이체가 존재할 수도, 아닐 수도 있음 |
| `sent` | Stripe가 이체를 수락함 |
| `releasing` | 항목을 돌려주는 중 |
| `failed` | Stripe가 이체를 거부함. 항목은 다시 열림 |

### 두 번 지급되지 않는 이유

- 항목은 정산이 없다는 조건으로 연결되므로 겹치는 두 실행이 둘 다 가져갈 수 없습니다.
- 정산은 **Stripe가 이체를 확실히 거부한 경우에만**(잘못된 요청이나 권한 오류) `failed`로 표시되고 항목이 다시 열립니다. 타임아웃, 5xx, 속도 제한, 알 수 없는 것은 모두 정산을 `pending`으로 둡니다.
- 복구는 다시 시도하기 전에 전송 그룹으로 `pending` 정산의 이체를 찾아봅니다. 있으면 정산을 전송됨으로 표시합니다. 없으면 같은 멱등성 키를 다시 사용합니다.
- 실행은 마무리되지 않은 정산을 건드리기 전에 선점하며, 최근 15분 안에 다른 실행이 작업한 정산은 그대로 둡니다.

한 강사의 실패가 다른 강사를 막지는 않지만, 운영자가 알 수 있도록 실행은 여전히 실패로 끝납니다. Stripe가 저장된 키를 거부하면 이후 호출이 성공할 수 없으므로 실행은 즉시 멈춥니다.

## 결제 계정 규칙

수익은 주문이 결제된 Stripe 계정과 모드에 속하며, 돈은 그 계정 안에서만 움직입니다. 관리자가 계정이나 모드를 전환한 뒤에는 다음과 같이 됩니다.

- 이전 계정에서 아직 지급되지 않은 수익은 **보류**됩니다. 실행은 이에 대해 아무것도 보내지 않으며, Earnings 페이지는 강사에게 플랫폼에 문의하라고 안내합니다.
- 각 강사의 정산 계정은 결제 계정별이므로 정산을 다시 설정해야 합니다.
- 다시 전환하면 이전 수익은 전과 같이 지급 가능해집니다.

## 불변 조건

core-table의 `helpers/invariants/earnings.ts`는 모든 엔드투엔드 시나리오 뒤에 다음을 검사합니다. 항목이 주문과 일치하고, 환불이 결제된 금액을 넘지 않고, 일별 행이 항목의 합과 같고, 정산 금액이 항목과 같고, 각 정산 계정이 올바른 형태입니다.

## 로컬 개발

Stripe 대역은 Connect 부분을 다룹니다. Express 계정, 온보딩 링크, 대시보드 링크, 이체입니다.

- `POST http://localhost:2024/payout-run`은 정산 실행을 한 번 실행합니다. 선택 사항인 `{ "graceSeconds": n }` 본문은 15분의 복구 유예 시간을 대체합니다.
- `LOCAL_PAYOUT_RUN_INTERVAL_SECONDS`는 타이머로 실행합니다.
- `GET /stripe/test/transfers`는 생성된 이체를 나열하며, `POST /stripe/test/transfers/fail-next`는 다음 이체가 선택한 방식(예: `rejected` 또는 `timeout`)으로 실패하게 합니다.

## 한계

- 세금 처리, 청구서, 세금 양식은 없습니다.
- 통화 변환은 없습니다. 통화마다 자체 잔액과 자체 정산이 있습니다.
- 분쟁과 지급 거절(chargeback)은 기록되지 않습니다.
- 보류된 수익은 플랫폼이 수동으로 지급합니다. 이를 새 계정으로 옮기는 것은 없습니다.
