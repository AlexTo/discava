워크플로는 `.github/workflows/`에 있습니다. 배포에는 **CI**와 **Deploy** 두 가지가 중요합니다.

## 파이프라인

```d2 title="What runs when"
direction: right
pr: "Pull request"
main: "Push to main"
checks: "PR Checks"
ci: "CI" {
  build: "Build\n(lint, test, build)"
  trivy: "Trivy scan"
  docs: "Deploy Docs"
  build -> docs
}
deploy: "Deploy"
manual: "Run workflow\n(manual)"
pages: "GitHub Pages"
aws: "AWS stage"

pr -> checks
main -> ci
ci -> deploy: "passed and\nAUTO_DEPLOY_STAGE set"
manual -> deploy
ci.docs -> pages
deploy -> aws
```

## 워크플로

### CI (`ci.yml`)

`main`에 푸시할 때마다, 그리고 직접 실행할 때 동작합니다.

| 작업 | 하는 일 |
| --- | --- |
| **Build** | 모든 프로젝트를 린트, 테스트, 빌드합니다. 빌드는 CDK 앱을 합성하고 Checkov로 템플릿을 스캔합니다. 빌드가 커밋된 파일을 바꾸면 실패합니다 |
| **Trivy** | 의존성의 알려진 취약점과 저장소의 시크릿을 스캔합니다 |
| **Playwright cache** | 엔드투엔드 테스트가 쓰는 브라우저를 저장해, 풀 리퀘스트가 더 빨리 시작되게 합니다 |
| **Deploy Docs** | 이 사이트를 GitHub Pages에 게시합니다. `main`에 푸시할 때만 실행되며, 더 새로운 커밋이 도착했다면 건너뜁니다 |

CI는 AWS 접근이 필요 없습니다. 다만 Trivy 작업이 쓰는 선택 사항인 Docker 로그인 역할은 예외입니다.

### Deploy (`deploy.yml`)

두 가지 방식으로 실행됩니다.

- **수동**: 스테이지 이름을 지정합니다. 실행한 위치의 커밋을 배포합니다.
- **`main`에서 CI가 통과한 뒤**: 저장소 변수 `AUTO_DEPLOY_STAGE`가 설정된 경우. CI가 검증한 커밋을 배포하며, 그 후 `main`이 앞으로 나아갔다면 건너뜁니다.

같은 스테이지를 이미 배포 중인 실행이 있으면 그것을 기다립니다. 겹치지 않습니다.

이 작업은 스테이지 이름의 GitHub 환경에서 실행됩니다. 그래서 스테이지의 변수를 쓸 수 있고, AWS 배포 역할이 이를 신뢰합니다. 단계는 <Link path="deploy/first-deploy">첫 배포</Link>에 나와 있습니다.

### PR Checks (`pr-checks.yml`)

`main`으로 향하는 풀 리퀘스트에서 실행됩니다. 변경이 영향을 주는 프로젝트의 린트, 테스트, 빌드, 로컬 스택에 대한 엔드투엔드 테스트, 저장소 고유의 몇 가지 검사를 합니다. AWS 접근이 필요 없습니다. 다만 선택 사항인 Docker 로그인 역할은 예외입니다.

### 메인테이너 자동화

프로젝트 자체의 개발 프로세스를 지원하는 것들입니다. 포크에서는 그대로 두거나 **Actions** 탭에서 비활성화해도 됩니다.

| 워크플로 | 하는 일 |
| --- | --- |
| `agent-*.yml` | 스펙 기반 프로세스를 진행합니다. 스펙 풀 리퀘스트와 `openhands/…`라는 이름의 브랜치에 대해 동작합니다 |
| `archive-specs.yml` | `main`에서 `specs/*/tasks.md`가 바뀌면, 끝난 스펙을 보관하는 풀 리퀘스트를 준비합니다 |
| `post-merge-verify.yml` | `discava-development`에 대한 Deploy 실행 뒤, 배포된 각 풀 리퀘스트마다 테스트 이슈를 엽니다. 포크에서 풀 리퀘스트를 머지하는데 이 이슈들을 원하지 않으면 비활성화하세요 |
| `cache-cleanup.yml` | 풀 리퀘스트가 닫힐 때 그 Actions 캐시를 삭제해, GitHub의 할당량 아래로 유지합니다 |

## 변수와 시크릿

워크플로가 읽는 모든 것입니다. 필요한 변수는 설정 스크립트가 대신 설정합니다.

### 저장소 변수

| 변수 | 설정 주체 | 용도 |
| --- | --- | --- |
| `AUTO_DEPLOY_STAGE` | 설정 스크립트, 선택한 경우 | `main`에서 CI가 통과할 때마다 배포할 단 하나의 스테이지. 설정하지 않으면 수동 배포만 가능 |
| `AWS_DOCKER_LOGIN_ROLE_ARN` | 설정 스크립트 | Docker가 Amazon ECR Public에 로그인해 이미지 가져오기에 속도 제한이 걸리지 않게 함. 설정하지 않으면 익명으로 가져옴 |
| `AGENT_APP_LOGIN` | 메인테이너 전용 | 메인테이너 자동화가 리뷰를 신뢰하는 GitHub App. 포크에서는 설정하지 않음 |
| `DOCS_SITE`, `DOCS_BASE_PATH` | 직접, 선택 사항 | 문서 사이트를 게시할 위치. 예: `https://docs.example.com`과 `/`. 설정하지 않으면 저장소의 GitHub Pages 주소 |

### 환경 변수, 스테이지마다 한 세트

| 변수 | 설정 주체 | 용도 |
| --- | --- | --- |
| `AWS_REGION` | 설정 스크립트 | 배포가 로그인하는 리전 |
| `AWS_DEPLOY_ROLE_ARN` | 설정 스크립트 | 워크플로가 맡는 역할 |
| `AWS_EXECUTION_ROLE_ARN` | 설정 스크립트 | CloudFormation이 리소스를 만들 때 쓰는 역할 |
| `<STAGE>_…` | 설정 스크립트 또는 직접 | 사용자 지정 도메인 같은 <Link path="deploy/configuration">구성 재정의</Link>. 스테이지 접두사로 시작하는 모든 변수가 전달됩니다. 예: `DISCAVA_DEVELOPMENT_INFRA_…` |

### 시크릿

| 시크릿 | 필수 | 용도 |
| --- | --- | --- |
| `CODECOV_TOKEN` | 아니요 | 테스트 커버리지를 Codecov에 업로드 |

**AWS 시크릿은 없습니다.** 워크플로는 GitHub가 그 한 번의 실행을 위해 발급한 토큰으로 AWS에 신원을 증명합니다.

## GitHub가 AWS에 로그인하는 방식

1. Deploy 작업이 GitHub에 OIDC 토큰을 요청합니다. 토큰의 subject에는 저장소와 환경이 들어 있으며, 기본값은 `repo:<owner>/<repo>:environment:<stage>`입니다.
2. GitHub용 AWS OIDC 공급자가 토큰을 검증합니다.
3. 배포 역할의 신뢰 정책은 정확히 그 subject만 허용하므로, 내 저장소에서 그 환경으로 실행되는 작업만 이 역할을 맡을 수 있습니다.
4. 작업은 그 실행 동안만 유효한 자격 증명을 받습니다.

그래서 환경의 보호 규칙이 곧 배포 관문입니다. 그 환경에서 작업을 실행할 수 있는 사람이 스테이지를 배포할 수 있습니다.

## 일부러 둔 두 개의 역할

| 역할 | 사용 주체 | 할 수 있는 일 |
| --- | --- | --- |
| **배포 역할** | 워크플로 | 스테이지의 에셋을 업로드하고, `<stage>-*`라는 이름의 CloudFormation 스택을 만들거나 갱신합니다. 리소스를 직접 만들 수는 없습니다 |
| **실행 역할** | CloudFormation | 스테이지의 리소스를 만듭니다. 이 역할이 만드는 모든 IAM 역할은 스테이지의 권한 경계를 달아야 합니다 |

둘을 나누면 침해된 워크플로가 그 스테이지의 CloudFormation 배포로 할 수 있는 일 이상을 할 수 없고, 배포된 어떤 것도 경계가 허용하는 것보다 많은 권한을 스스로 부여할 수 없습니다.
