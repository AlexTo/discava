## 规则

**每笔销售和每笔退款都只记录一次，任何收入都不会被支付两次。** 收入是一个只追加的账本，由<Link path="design/payments">订单</Link>构建，而付款取用的是账本条目，绝不是另外计算出的金额。

## 收入规则

core-table 中的 `helpers/revenue.ts` 是纯整数运算，使用币种的最小单位。

- **费用。** 平台对实付金额收取一笔费用，按阶段以基点设置（2000 即 20%），四舍五入。一笔销售沿用记录时的费用：更改该设置只影响之后的销售。
- **分成。** 一门课程的讲师平均分享一笔销售。分成分别应用于标价、实付金额和费用，多出的余数单位按 ID 顺序依次分给前几位讲师，每人一个，因此各份之和总等于整体。
- **净额。** 讲师的净额是其实付金额份额减去其费用份额。
- **退款。** 退款退还讲师在退款金额中的份额，减去其中退回的费用。每一步都按新的已退款总额的份额减去已记录总额的份额计算，因此无论退款被拆成几步，订单全额退款后各条目之和恰好准确。退款上限为实付金额。

## 账本

| 记录 | 内容 |
| --- | --- |
| `earningOrder` | 账本中一笔销售的快照，以及迄今记录的已退款总额 |
| `earningEntry` | 每位讲师每笔销售或每个退款步骤一行：总额、折扣、退款、费用和净额、何时释放，以及取走它的付款 |
| `earningDay` | 一位讲师在某门课程、币种和 UTC 日的条目之和 |

core-table 中的 `helpers/earning.ts` 是这三者的唯一写入者，只有一个例外：`helpers/payout.ts` 是唯一设置或清除条目 `payoutId` 的代码。一笔销售以及每个退款步骤都是**一个事务**，包含条目、对它们的日行的累加和订单的计数器，因此报表和账本不会不一致。

条目从不记录买家。它还带有其订单支付时所用的 Stripe 账户和模式：见[支付账户规则](#支付账户规则)。

## 记录

记录是一项<Link path="design/stream-event-router">流功能</Link>，即 `earnings-recording`。它接收对 `order` 的每项变化，并处理其中属于销售的那些。当以下两点都成立时，订单是一笔销售：

- 它是 `paid`，或是原因为 `requested` 的 `refunded`；
- 它的金额大于零。

因无法交付而被自动退款的订单从来不是销售，用优惠券抵扣全部价格的零金额订单也不是。对于有折扣的订单，条目的总额是标价，折扣是它与实付金额的差额。

路由器至少投递一次且顺序任意，处理器就是按此构建的：

- **每个订单镜像都带有它所需的一切**，因此任何一个都足以记录销售并更新其已退款总额。没有记录需要等待另一条。
- **重复不会改变任何东西。** 销售的条目在“它们不存在”的条件下创建，账本已经达到的已退款总额不会再记录任何内容。
- **顺序无关紧要。** 较旧的镜像迟到时会发现已记录的总额更高，因而什么也不做。
- **失败会重试该批次。** 所有能应用的都会应用，然后批次抛出异常，而已应用的内容在第二次时是空操作。

销售的条目在订单支付后的 `holdDays` 天释放。退款的条目立即释放，因此会减少下一笔付款。

## 收入页面的读取

instructor-api 提供调用者自己的数据，不接受讲师 ID 作为输入。

- `earnings.report` 对最长 366 天的时间段汇总日行：一次范围查询，按币种和课程分组。
- `earnings.lines` 分页浏览一门课程的条目，逐字段构建，因此记录上的其他内容不会到达调用者。
- `payout.overview` 把尚未被任何付款取走的条目按币种分为**保留中（on hold）**、**等待账户设置**、**可付款（ready）**和**已冻结（held）**，并列出讲师的付款。

## 付款账户

讲师的款项付到 Stripe Connect Express 账户。

- `payout.startOnboarding` 以幂等方式创建账户，并返回 Stripe 的入驻链接。
- `payout.account` 从 Stripe 读取账户状态，并在状态改变时存入 `payoutAccount`。如果无法连接 Stripe，它返回已存储的状态并标记为 `stale`。
- `payout.dashboardLink` 在入驻完成后，返回登录讲师 Stripe Express 仪表板的链接。

| 状态 | 含义 |
| --- | --- |
| `not_started` | 还没有账户。没有存储任何内容 |
| `in_progress` | Stripe 表单尚未完成 |
| `active` | Stripe 可以向其发送转账和付款 |
| `restricted` | Stripe 还需要更多信息 |

除非平台的连接处于启用状态，否则这里没有任何内容会调用 Stripe。没有连接时，`payout.account` 回答 `unavailable`。

## 付款运行

`Payouts` 堆栈中的一个 Lambda 函数，通过 EventBridge 计划每天运行一次。它能读取 Stripe 密钥，除此之外不能读取任何其他密钥。

1. **绑定到支付账户。** 运行针对连接当前的账户和模式工作，并且只使用已证明属于该账户的密钥。
2. **恢复。** 先完成之前的运行留下的未结算付款：仍处于 `collecting` 或 `releasing` 的付款会归还其条目，`pending` 的付款按下文所述结算。
3. **对每位有 active 账户的讲师，** 再次从 Stripe 读取账户。不再是 active 的账户会存储其新状态并被跳过。
4. **按币种，** 汇总尚未被任何付款取走的已释放条目。低于该阶段最低额，或不大于零的总额会继续等待。
5. **收集、封存并发送。** 付款以 `collecting` 创建，条目以每批 99 个附加（一个事务最多容纳 100 项），然后封存为 `pending`。接着在 Stripe 中创建转账，以付款 ID 作为其幂等键和转账组，并把付款标记为 `sent`。

| 状态 | 含义 |
| --- | --- |
| `collecting` | 正在附加条目 |
| `pending` | 已封存。它的转账可能存在，也可能不存在 |
| `sent` | Stripe 已接受转账 |
| `releasing` | 正在归还其条目 |
| `failed` | Stripe 拒绝了转账。它的条目重新开放 |

### 为什么不会重复付款

- 条目在“它没有付款”的条件下附加，因此两个重叠的运行不可能都取走它。
- 只有在 **Stripe 明确拒绝**转账时（无效请求或权限错误），付款才会被标记为 `failed`，其条目才会重新开放。超时、5xx、速率限制或任何无法识别的情况，都会让付款保持 `pending`。
- 恢复时，会先按转账组查找 `pending` 付款的转账，再决定是否重试。如果它存在，付款被标记为已发送。如果不存在，则再次使用相同的幂等键。
- 运行在处理未结算付款之前会先认领它，并且不碰最近 15 分钟内被另一个运行处理过的付款。

一位讲师的失败不会阻止其他人，但运行仍会以失败结束，让运维人员看到。如果 Stripe 拒绝保存的密钥，运行会立即停止，因为之后的调用都不可能成功。

## 支付账户规则

一笔收入属于其订单支付时所用的 Stripe 账户和模式，资金只在该账户内流动。管理员切换账户或模式后：

- 旧账户中未支付的收入会被**冻结**。运行不会为它们发送任何内容，收入页面会告诉讲师联系平台。
- 每位讲师的付款账户是按支付账户区分的，因此他们需要重新设置付款。
- 切换回去后，旧收入会像以前一样可以付款。

## 设置

按阶段，在 `stages.config.ts` 的 `payouts` 下。见<Link path="deploy/configuration">阶段配置</Link>。

## 不变量

core-table 中的 `helpers/invariants/earnings.ts` 在每个端到端场景之后检查：条目与其订单一致、退款从不超过已支付的金额、日行等于其条目之和、付款金额等于其条目之和，以及每个付款账户格式正确。

## 本地开发

Stripe 替身涵盖 Connect 部分：Express 账户、入驻链接、仪表板链接和转账。

- `POST http://localhost:2024/payout-run` 运行一次付款运行。可选的 `{ "graceSeconds": n }` 请求体会替换 15 分钟的恢复宽限期。
- `LOCAL_PAYOUT_RUN_INTERVAL_SECONDS` 让它按定时器运行。
- `GET /stripe/test/transfers` 列出已进行的转账，`POST /stripe/test/transfers/fail-next` 让下一笔转账以选定的方式失败（例如 `rejected` 或 `timeout`）。

## 限制

- 不处理税务、发票或税表。
- 没有货币兑换：每种货币有各自的余额和各自的付款。
- 不记录争议和拒付。
- 被冻结的收入由平台手动支付。没有任何机制会把它们转移到新账户。
